# EnergyIQ report workbench design

Scope: the EnergyIQ shell and report workflows (AI Chat, Knowledge, Project configuration, Skills & Tools). Product truth remains in `CONTEXT.md` and `docs/energyiq/`; this file records visual rules only.

## Direction

An operating workspace for Singapore energy teams, typically used in a bright office on a laptop. Light mineral-grey work surfaces reduce the expanse of pure white. Graphite navigation holds project context; evergreen identifies actions and selections. White is reserved for writing, inspecting data and reading report documents.

## Palette and hierarchy

- Navigation: `#262d2b`, raised navigation `#36403b`, selected `#3b5046`, text `#f0f4ef`, secondary `#b9c5bc`.
- Work surfaces: canvas `#eef1ee`, chat `#f3f5f2`, header `#f8faf7`, editor `#ffffff`.
- Action: `#176b59`, hover `#115444`; selection uses pale green with dark green text.
- Text: `#252c29`, secondary `#58645d`; dividers `#d7ded9`.
- Report preview: grey-green surround and unmodified white document. Embedded report content retains its own stylesheet and sandbox.

The scoped source is `apps/web/src/app/energyiq/energyiq-theme.css`; do not change the global DataFoundry palette to extend this design. Status colours retain their semantic meaning. Never use colour as the only state signal.

## Typography and components

Use the existing local system UI font stack, including its CJK fallback. This is an operational application, not a display-font surface. Page titles are 24px, the new-conversation question scales from 25–34px, reading text is 16px, controls 13–14px, supporting metadata 12–13px. Avoid expanding explanatory copy when a clear action can carry the meaning.

Use `EnergyIcon`: 24-unit viewBox, 1.8px stroke, round caps and joins. Most controls use 16–19px icons and visible labels; decorative SVGs are hidden from assistive technology. No additional icon dependency.

Navigation and controls use 8px radii; editors and report thumbnails use 12–16px radii. Skill entries are open rows with dividers, not nested cards. Align report thumbnails and Skill content at the top. Preserve explicit disabled, selected, loading and error states.

## Interaction and responsive behaviour

Hover changes surface or border. Press moves a control by at most 1px. Focus uses a visible 2px outline with 3px offset. All new transitions are 140ms and stop under reduced motion. Existing activity transitions keep their reduced-motion fallback.

At widths below 768px the sidebar becomes a rail with an overlay; report previews use the existing full-screen dialog. AI Chat uses a white, centred transcript with an independently scrolling history and a fixed composer dock; the mobile composer also stays available. Choosing a starter fills and focuses the composer without submitting it. The report library becomes one column. All existing APIs, upload handling, permissions, report identities and Skill approval behaviour remain authoritative.

## Top bar and account controls

A 64px graphite top bar spans the work area and aligns with the sidebar's brand row. It holds project context: the project switcher on the left; the notification bell and account avatar on the right. The project switcher stays visible when the sidebar is collapsed. The bell lists new action results for the active project and links to that action in the Action plan; opening the result marks it read. Search is not shown until a real search exists. The sidebar keeps page links, recent reports and conversations.

The account avatar opens a downward menu containing Personal information and Sign out, with Admin console shown only to administrators. Personal information is a read-only identity dialog. Admin console lazily loads the existing workbench into a large modal and keeps section navigation local to that modal. The standalone admin route remains available. Dropdown portals inside a native dialog stay within that dialog's top layer. Escape closes menus/dialogs and restores focus; menu items support arrow keys.


### Analysis navigation
- Name the conversational workbench Energy advisor (nav item "Ask the advisor"); keep New conversation as its separate creation action. Do not lead navigation or buttons with "AI": buttons that open it say "Ask the advisor" or "… with the advisor". Content written by the model keeps its small "AI-generated" label so readers always know its source.
- Primary navigation uses plain, professional names a first-time facility manager understands: Overview, Analysis, Reports, Facility, Ask the advisor, Advisor guidelines. Each item carries a one-line hover description. Internal terms (Explorer, configuration, Skills, Scope) stay out of customer navigation.
- The account menu (top right) has Personal information, Admin console (administrators), User guide and Sign out. User guide (`/energyiq/guide`) is a plain-language page: what each page is for (with links), step-by-step "How do I…" tasks (administrator-only tasks are labelled), how to read the charts, a glossary and common questions, with a search box that filters all of it. Update it when a page or workflow changes.
- The sidebar groups pages like a utility console: Overview, Analysis and Reports are direct links; Action plan and Energy consumption are no longer in the sidebar (the Overview headline leads to Analysis, whose savings plan and the notification bell open individual actions) (Devices covers the whole site, one board or one device) but stays reachable from links that open a specific scope and dates; Facility expands to Floor layout, Devices, Project notes, Operating hours, Holidays, Electricity rate and Holidays (each opens that tab through `?tab=`, and the page keeps the URL in step); Energy advisor expands to Ask the advisor and Advisor guidelines. The section holding the current page opens automatically; a section with one visible page renders as a plain link. The current page is a solid evergreen fill with white text. When collapsed, the rail flattens sections into one icon per page, separated by dividers.
- Group sessions under AI Analysis and recent HTML deliverables under Knowledge. Previewing a report preserves the current analysis draft; referencing it is explicit.
- Keep the next-message date range and available-data coverage visible. Use direct preset buttons and a date-range disclosure without nested dropdowns.
- Project background and default documents belong to Project configuration; recurring report instructions belong to Knowledge. Preserve settings revision checks across both entry points.

### Navigation revision after visual feedback
AI Analysis and Knowledge return to flat links, with a separate Conversations list below. Do not nest report titles under Knowledge. A recent-report thumbnail shelf on the new-analysis start page is a proposed next step, not implemented or accepted yet.

### Approved recent-report surfaces
The sidebar holds page links only. Reports are listed on the Reports page; conversations are chosen on the Energy advisor page from a compact picker labelled with each conversation's first question and date, with a New conversation button while viewing an earlier one. New analysis shows up to three recent report previews, hidden once the conversation has turns. Completed report replies include a thumbnail. All reuse sandboxed, script-disabled lazy thumbnails; desktop opens the right preview and mobile uses the existing modal. Opening alone does not reference a report or erase the draft.

## Facility editing

Saving is publishing: every save on the Facility page (locations, meters, operating hours, holidays, electricity rate, choosing a version) is made live straight away through `POST /projects/:id/setup/apply`, which publishes with the project's current settings exactly as Review & Publish would. The page header says "All changes are live", or "Some changes aren't live yet" with the plain reason and a Make live now button. The admin console keeps its own Review & Publish. Project notes carry a "Things the advisor should know" section (dated facts: after working hours, must stay on, recent change, coming up, note) that the advisor reads in every answer and report and can add to from chat when the user confirms. The advisor receives every available reading up to about 13 months before and after the chosen dates, so questions about other periods can be answered.

Facility edits happen on the page, not only through AI. Floor layout is one workspace: Locations on the left; on the right the floor plan (areas in one colour per distribution board, rooms, equipment groups inside rooms, an entrance and a pin for every placed device) above the selected location's details. Selecting a location highlights its boards on the plan and fades the rest; clicking an area or a pin selects that board in Locations and highlights the meter row, which has "View usage ›" to open it on Devices. A space with no meters of its own lists the boards inside it instead of "0 meters". The plan can be hidden per browser. Administrators choose Edit layout, which opens a full-width editor, to drag and resize areas and rooms (rooms, groups and devices move with their area), add areas, rooms and an entrance, drag devices from the side list onto the plan (or Place then click), and use "Place the rest in their board's area", which puts each device in the room its name mentions ("Director Room Power" → Director room), in its board's equipment group, or in the free space of its board's area. Pin labels drop what the surroundings already say ("Showroom TV 1" in the Showroom reads "TV 1"). Undo, arrow-key nudge and Delete work as expected. Saving writes the layout to the spatial reference block in Project notes (schema unchanged, with `layout.devices` added), so Project notes and the energy advisor see it immediately. Floor layout: edit a location's name, area and occupants, add a location at the next level, remove a location with no meters, and edit a meter's name, location, type and whether it counts in totals. Each save updates the shared setup draft immediately. Renaming keeps confirmed meter totals; moving or re-counting a meter shows a "Check meter totals" bar with the same checks as the admin checkpoint. Operating hours, Holidays, Electricity rate: administrators edit weekly hours in the card; saving creates a pending calendar version. Holidays: a summary strip (count per category and Next up), an Apple Calendar-style month view (large day cells, number top-right, weekends shaded, today filled; each holiday or break is one bar spanning its days and wrapping onto the next week, up to three lanes then "+N more") with a Year overview toggle, and a sticky side panel that lists the year's entries by month or shows the add/edit form. Click a day, drag across days, or click a bar. Category is required: Public holiday, School holiday, Closure or Special hours. School holidays are saved as school breaks in the academic calendar (term time is split around them; opening hours unchanged); the others are dated calendar exceptions with an hours choice: Closed, Normal hours (the day is only labelled and keeps each weekday's usual hours) or Custom hours. Public holiday and Closure default to Closed; Special hours defaults to Custom. Unsaved changes show a sticky dark bar with the number of changed days. Customers see all changes only after Review & Publish. "Edit with AI" links remain alongside.

## Theme

A theme control sits in the top bar next to the notification bell: Light (default), Dark or Match system, remembered per browser. The choice sets `data-energyiq-theme` on `<html>` before first paint, so a saved dark choice never flashes light. Dark mode keeps the same layout and hues: surfaces go to near-black greens, text to light grey-greens, and status and brand colours keep their meaning. Shared tokens (`--surface`, `--border`, `--foreground`…) carry it for token-based components; `energyiq-theme.css` remaps the fixed Tailwind colours and chart axes, grids and tooltips; each EnergyIQ CSS module ends with a generated dark block (`node apps/web/scripts/energyiq-dark-theme.mjs`, checked by a test) that mirrors the light cascade with zero added specificity. After editing a module's colours, re-run the script. Report documents in the preview keep their own light styling.

## Analysis page

Step 6, "Next month's forecast", estimates the next calendar month: a normal open day and a normal closed day from the period's complete readings, applied to the published operating hours, holidays and closures, and priced with the saved rate periods. It shows a day-by-day chart of the analysed period followed by each expected day of next month (used, expected open day, expected closed day, with a divider where the month starts), expected kWh and cost as a range, the month's open/closed day count, the change against the analysed period, any named days, and a warning with a link when no rate covers part of the month. Overview carries the same estimate as one line under the headline. Health check cards carry their next step: each unusual date opens that day in step 2, the closed-share and always-on cards jump to step 3, the change card to step 2, and missing readings link to Facility → Devices.

The Overview ends with "The full report": a fixed-format site energy report built in the browser from the same readings as Analysis, for the same dates as the published priorities (the latest four weeks when none are published). It copies the structure, story and chart detail of the reference Tuya Office report (17 Aug – 5 Sep 2026): masthead, a headline finding with its key phrase in brand orange (#FF4E16), a lede and four key figures, then 1 Property profile & circuit map (the saved floor layout drawn as a schematic with each zone's 30-day estimate, or a zone table without one), 2 30-day estimate & electricity bill (per official circuit, weekday avg × 30·5/7 + weekend avg × 30·2/7 at the published tariff, with two donuts by space and by load), 3 Benchmark (daily bars, weekday orange and weekend slate, paler for days with missing readings, with weekday-average and base-load-only-day lines), 4 Weekday operating-hour pattern (average kW by hour, operating band, arrival ramp, lunch dip, peak and evening linger annotated, plus which circuits cause the lunch dip) and 5 Abnormality screening by circuit (weekday operating vs after-hours baselines, flags at ≥30% and ≥0.15 kWh/h, one plain finding per circuit and a "Reading the screen" callout with the monthly saving). Circuits are named by place and what they feed ("Office area lights", "Shared area equipment & sockets", "3 LED displays"), never by panel code; codes such as DB1 L1 Light appear only as small grey detail under table rows and in brackets in section 1. The Overview heading is this report's headline finding plus one money sentence, and the priority cards swap panel codes and 24-hour times for the same plain names and am/pm. Every figure and sentence comes from `site-report-model.ts`; charts are hand-built SVG so the downloaded HTML needs no scripts or internet access. The report stays white paper in dark mode.

Analysis sits under Overview in the sidebar and has two layers on a white surface. The top layer is a decision summary for non-technical readers, told as a story in money: "The short version" (spent in the period, how much of it was used while the site was closed, and the yearly saving as a range) followed by five numbered steps. 1 Where the money goes (bill by area and by type of use). 2 When the energy is used (open hours, weekday evenings and nights, weekends, public holidays as one bar with values printed, plus an average weekday or weekend hour by hour split into always-on, used while open and left on after closing, with closed hours shaded; operating hours come from Facility → Operating hours, Monday to Friday 08:00–18:00 is assumed and said when none are saved). 3 What stays on when the site is closed (each circuit inside each space, the unmetered rest of each space, or each type when there is no circuit detail; equipment whose name suggests it must run around the clock is marked "Check first"). 4 Health check (Good, Watch, Act with an icon and a word, never colour alone, and the thresholds printed). 5 Savings plan (numbered actions, "Start here" on the first, each with the formula power × closed hours a year × rate, confidence, effort, and an optional cost to fix that gives a payback). Savings are always a range: the lower figure only asks equipment to stay as low as it already goes on its quietest nights (10th percentile of complete nights), the higher figure assumes it is switched off whenever the site is closed; payback uses the lower figure; the total counts each circuit once and leaves out "Check first" items. The second layer, "Detailed analysis", keeps the approved NetZero prototype sections for facilities and energy teams: Live dataset, Daily Total Trend with the anomaly list, Executive Summary (Key Highlights with breakdown and peak dialogs, Consumption Breakdown, Energy Distribution, Summary of Findings), Day Profile Analysis with the level heatmap, Time-based Behavioral Analysis and Circuit Category Analysis. All figures come from the same server engine as Energy consumption on one data snapshot: the chosen dates (default latest four weeks), the equal-length period before, each space (up to eight) and all history for the overnight benchmark. Time-of-week colours use validated categorical slots (open blue #2a78d6, weekday evenings yellow #eda100, weekends violet #4a3aa7, public holidays orange #eb6834), with always-on in neutral grey; type colours follow the prototype (Lighting #4F9B86, Power Load #5B8BCF, Air-con / Ventilation #9A8DBF, Other #8B95A5).
