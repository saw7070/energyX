# 三 Agent MVP 执行手册

## 1. 适用与不适用

适用于当前三个执行 Agent：

- Agent 1：Energy Data Foundation；
- Agent 2：Structured Template，产品主线；
- Agent 3：AI Analyst，增强功能。

不适用于 Preschool、Tuya、Water、AI 修改模板或通用平台扩建。

## 2. 开工前提

1. 正式仓库只有 D:\Projects\energyiq-datafoundry；
2. 当前结构化模板工作先形成可识别 checkpoint；
3. 三个 Agent 使用独立分支/worktree，或严格遵守文件 Owner；
4. 禁止 reset、clean、覆盖式 checkout 和批量格式化；
5. 三个 Agent 共用同一个 Ngee Ann Project、Scope 和测试 Period；
6. Agent 2 是产品集成 Owner。

共同测试 Period 由 Agent 1 自动选择数据完整度最高的连续 7 天，并从中选择一个完整单日验证 15 分钟/小时曲线。它只用于开发对账和回归测试，不限制正式用户的 Yesterday、Last 7 days、Previous month 或 Custom 时间选择，也不等同于异常检测使用的历史基线。

## 2.1 MVP 完成边界

第一版 MVP 必须同时完成：

1. Data Foundation：Ngee Ann 真实数据稳定并形成 golden result；
2. Structured Template：正式 Overview、Save、History、Rerun 和精简 Explorer 可用；
3. AI Analyst：可信问数、Evidence、Task Console 和基础图表可用。

Overview 与 AI 的深度协同属于紧随其后的下一阶段，不阻塞第一版 MVP。不得用“单个页面已经显示”替代上述三项共同验收。

## 3. Agent 1：Energy Data Foundation

目标：给另外两个 Agent 提供一份稳定、可信、可重复的 Ngee Ann 分析结果。

现在做：

1. 确认真实 Excel 已正确生成 15 分钟 facts；
2. 选择数据最完整的固定测试 Period；
3. 固定总用电、Level 比较、Circuit 排名、分类、小时曲线、峰值、基础异常和 Data Health；
4. 保证重复查询结果一致；
5. 提供 golden fixture 和测试证据；
6. 处理运行中 API 与 DuckDB 测试冲突；
7. 输出 Agent 2 和 Agent 3 可共同消费的结果。

不做：

- 前端；
- Tuya/Water；
- 新 Runtime、Receipt、Task Console；
- 通用指标平台；
- 完整历史 Snapshot 重放。

验收：同一 Scope/Period 稳定返回完整结果，相关测试可复现。

## 4. Agent 2：Structured Template

目标：完成第一个客户可见 MVP，是产品主线和最终集成 Owner。

现在做：

1. 保留并整理现有 Renderer/Preview 工作；
2. 给 Ngee Ann 正式发布 Template Revision，不使用 compatibility default；
3. 用 Agent 1 结果完成七个 Overview 模块；
4. 支持通用时间选择；
5. 先验收 Interactive Overview；
6. 再实现 Save、Saved Analysis、History 和 Rerun；
7. 精简 Explorer，只保留层级、读数、用量、功率、来源和 Data Health。

Saved Analysis 第一版只包含手动保存、只读历史、History 列表和使用最新数据 Rerun。PDF、定时报告和邮件发送进入后续 backlog，不阻塞 MVP。

不做：

- AI；
- 数据算法；
- 通用 Admin；
- 自由画布；
- Preschool 泛化。

验收：Admin 可发布；Boss/FM 可查看真实 Overview、保存、复跑和核查 Explorer。

## 5. Agent 3：AI Analyst

目标：复用 DataFoundry 原生 Agent，完成 Ngee Ann 可信问数和受控图表。

现在做：

1. 确认 Provider 可调用，不输出 Key；
2. 验证现有 AI 页面、Context、scoped datasource 和 Task Console；
3. 不建设新 Runtime/Harness；
4. 增加 Energy instructions；
5. 首先使用 DataFoundry 原生 inspect/preview/read-only SQL、验证和 Evidence 链路，不预先开发 Energy Tool；
6. 跑通十个 Boss 核心问题，并与 Agent 1 golden result 对账；
7. 生成 bar/line/pie Chart Artifact；
8. 验证答案、图表、Tool Result 和 Evidence 一致。

不做：

- Deep Agents；
- 新 Task Console；
- 新 Knowledge/MCP/模型管理；
- 多 Agent；
- AI 修改模板；
- 任意前端代码执行。

验收：相同 Ngee Ann Context 下能回答十个 Boss 问题，显示查询过程和可信图表。

十个 Boss 问题：

1. 当前周期总用电及相对上一周期变化；
2. 是否高于自身历史正常水平及差值；
3. 工作日、周末和公共假期模式差异；
4. 用电最高的 Level/区域/房间；
5. 在可靠面积/人数元数据下的归一化表现；
6. 主要 Circuit 和贡献度；
7. Light、Load、Aircon、Other 构成；
8. 峰值时间和贡献 Circuit；
9. 非营业时间用电与可避免浪费；
10. 最优先处理的三个问题、Evidence 和数据可信度。

费用问题只有在 Tariff 已配置时回答；Carbon、Forecast 和 Water 不进入本轮 MVP。

模型选择：MVP 默认使用 DeepSeek `deepseek-v4-pro`；Qwen `qwen3.7-max-2026-06-08` 作为跨 Provider fallback，`deepseek-v4-flash` 作为低成本/低延迟候选。API Key 只能通过 DataFoundry 加密的 Model Configuration 本地录入，不得写入本文、`.env` 示例、源代码或 Git。2026-08-03 在聊天中暴露的 Qwen/DeepSeek Key 必须在验证后撤销并重新生成。

真实调用已确认两枚 Key 和三个模型可用，但当前根 `@ai-sdk/openai 3.x` 与被旧 CopilotKit 提升到根的 `ai 5.x` 存在模型协议 v3/v2 错配。Mastra 1.46 的 `chat` 依赖实际要求 AI SDK 6。Agent 3 应让 Mastra 主链显式锁定 AI SDK 6、CopilotKit 子树保留 AI SDK 5，并使用对应版本的官方 DeepSeek/Alibaba/OpenAI-compatible Provider；不自研模型协议或重写 Runtime。

只有常见确定性指标经过原生查询仍反复不能与 Overview 对齐时，才增加调用现有 `executeEnergyScopeAnalysis` 的薄 Tool；不得复制算法或建设第二套分析引擎。

## 6. 并行节奏

第一轮：

- Agent 1 固定真实数据结果；
- Agent 2 完成正式发布和 Overview 结构；
- Agent 3 验证 Provider、现有 Run 和 Task Console。

三个 Agent 从第一轮同时开工，不要求 Agent 2、3 等待 Agent 1 完全结束。Agent 1 交付 golden result 后，Agent 2、3 再完成最终数字对齐。三个 Agent 严格遵守文件 Owner；共同热点由 Agent 2 窄集成。

第二轮：

- Agent 1 交付 golden result；
- Agent 2 接入同一结果完成 Overview；
- Agent 3 接入同一结果完成十个 Boss 问题。

第三轮：

- Agent 2 完成 Save/Rerun 和 Explorer；
- Agent 1 补 Data Health；
- Agent 3 补 Evidence 和 Chart Artifact。

第四轮：

- 只做 Context/Evidence 协同；
- 不做 AI Template Proposal。

## 7. 共同验收

相同：

    Project + Scope + Period

必须满足：

1. Agent 1 的 golden result；
2. Agent 2 Overview；
3. Agent 3 AI answer/chart；

三者数字、单位和范围一致。

AI Analyst 第一版只把以下输出纳入验收：

- line：时间趋势；
- bar：Level/Circuit 横向比较；
- pie：Light、Load、Aircon、Other 构成；
- table 与 Evidence：明细和可追溯依据。

Heatmap、Quadrant、Bell Curve 等复杂图表不阻塞 AI Analyst MVP；需要时先由结构化模板承担，后续再扩展受控 Catalog。

## 7.1 验收责任

| 责任人 | 验收内容 |
| --- | --- |
| 产品负责人 | 产品动线、功能范围和最终 MVP |
| Charles | Overview 模块内容、决策价值和表达，不审核每个技术细节 |
| Agent 1 | 数据数字、口径、完整度和质量 |
| Agent 2 | 客户界面、整体集成和共同验收组织 |
| Agent 3 | AI 回答、图表、Tool Result 和 Evidence 一致性 |

## 8. 状态回报格式

每个 Agent 每轮只回报：

1. 已完成；
2. 验证证据；
3. 下一步；
4. 阻塞；
5. 修改文件；
6. 是否触碰共同热点。

## 9. 失败模式

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 三个 Agent 同时改同一文件 | Owner 不清 | 暂停，由 Agent 2 或对应模块 Owner 窄集成 |
| 又开始建设平台能力 | 偏离案例目标 | 回到 Ngee Ann 共同验收 |
| Overview 与 AI 数字不同 | 使用了不同计算 | 以 Agent 1 golden result 为准 |
| AI 能聊天但无真实 Tool | 只验证了界面 | 不算完成，必须有 Task Console 和结果 Evidence |
| Overview 能显示但没有正式 Revision | 使用兼容兜底 | 不算完成，必须正式发布 |

## 10. 新需求处理规则

开发中只立即处理：

1. 阻塞 Ngee Ann Data Foundation、Structured Template 或 AI Analyst 任一主链路的问题；
2. 导致三条链路数字、单位、Scope 或 Period 不一致的问题。

复杂图表、通用指标、PDF、定时报告、Preschool、Tuya、Water 和 AI 修改模板等其他发现只进入 backlog，不在本轮顺手扩建。
