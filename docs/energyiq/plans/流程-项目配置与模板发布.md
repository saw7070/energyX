# 项目配置、数据接入与模板发布流程

## 1. 总流程

~~~text
Create Workspace/Project
→ Configure Profile
→ Define Tiers bottom-up
→ Create Nodes and attributes
→ Import Excel or connect Tuya API
→ Confirm source label → Physical Meter mapping
→ Configure roles, categories, topology and virtual formulas
→ Validate readings and Interval Facts
→ Configure calendar, tariff, metrics and rules
→ Create Project/Tier Template Draft
→ Preview with real period
→ Validate and Publish
→ User reruns Overview / Explorer / AI Analyst
~~~

Admin 可随时 Save Draft。只有 Validate 和 Publish 执行完整门槛；这样未录完的项目不会因为中间状态而被阻止保存。

## 2. Profile

配置：

- Workspace；
- Project name；
- timezone，默认 Asia/Singapore；
- resources，首期 Electricity，Water 可选；
- 数据日更新目标；
- Project status；
- provisional/confirmed 标识。

Project 是最高分析根，不创建 Company Tier。

## 3. Tiers & Nodes

Structure 分成两个连续子步骤：

1. **Tier Setup**：定义最低有意义 Tier 的 alias，需要更高业务范围时使用 Add parent tier；
2. 解释每层的独立分析、比较、导航、权限、属性或直接挂表意义；
3. Review 后执行 `Lock Tier Structure & Continue`，它只是 Draft 检查点；
4. **Hierarchy Builder**：从顶层节点开始，沿已锁定 Tier 自顶向下创建真实父子树；
5. 配置面积、代表人数、营业时间和用途；
6. Validate Structure 后进入 Data & Meters；
7. 第五阶段 Review & Publish 统一发布 Hierarchy Revision 及其他正式配置。

MVP UI 支持 2–4 Tier，模型保留 5–7。跳 Tier 暂不开放。

Tier Setup 与 Hierarchy Builder 不同时编辑。锁定后 Tier Definition 缩为右侧只读结构示意图，主区域使用可展开的 Hierarchy Tree 配置真实父子节点。树允许每个分支拥有不同数量的子节点；选择父节点后，操作按钮明确写成“在该节点下添加下一层节点”。

每个 Node 行右侧的 `+` 提供三类上下文动作：

1. 添加下一 Tier 节点，新增后继续停留在当前父节点以支持连续创建；
2. 携带当前 Scope 进入 Meter Mapping，为当前 Scope 配置 Physical Meter；
3. 常见 Circuit 一对一场景可使用 `Add Circuit & Configure Meter` 快捷操作；Virtual Meter 仍在 Mapping Confirm 阶段可选创建，不单设 Tab。

Node 名称在同一父节点和同一 Tier 内唯一；不同父节点允许同名。自动新增、改名、移动父节点和服务端发布校验使用同一规范化口径。

## 4. 数据接入

### 当前：Excel

Excel 是首期主入口：

1. 上传文件并计算 SHA；
2. 预览 Sheet、字段、时间范围和行数；
3. 机器做确定性字段识别；
4. admin 确认 Device Name、Time、Active Energy；
5. 创建 Import Batch，保留原文件；
6. 解析 Raw Reading；
7. 显示未知 label、重复时间、空值和覆盖率。

### 后续：Tuya API

Tuya Connector 使用同一 Source/Import Batch 契约：

1. 认证与连接测试；
2. 读取设备和数据字段；
3. 每日按窗口拉取；
4. 记录分页、限流、重试和原始响应；
5. 输出与 Excel 相同的 Raw Reading。

API 和 Excel 不各自实现差分、质量、虚拟表或指标。

数据模型允许一个 Project 保留多个 Source 记录，但 MVP 不提供复杂的数据源编排：Excel 是当前人工接入方式；Tuya API 可用后成为主来源并替代日常 Excel 导入。只有在迁移核对或补历史数据时短暂保留两者并存，且同一 Meter/时间区间只能有一个权威输入，避免重复生成官方 Fact。

## 5. Meter Mapping

Mapping 只允许选择 Structure 已创建的 Scope。发现缺少 Floor、Room、Circuit 等节点时，标记未映射并通过 `Return to Structure` 补充，不能在 Mapping 中临时改变层级。

首次流程：

~~~text
Import Excel
→ detect source labels
→ map each label to an existing Scope
→ configure Resource, Category and Coverage
→ review Official Aggregation Route
→ optionally create Virtual Meter
→ Confirm Mapping
~~~

admin 为每个 source label：

- 创建或选择 Physical Meter Point；
- 选择挂载 Scope；
- 选择 resource；
- 选择 overall、load、aircon、light、other；
- 选择 whole scope、partial、reference only，对应 total、component、standalone；
- 查看映射会不会造成重复计算。

逐行 Mapping 完成后，系统按 `scope + resource + category` 给出正式聚合建议，admin 在 Confirm Mapping 统一选择直接总表、虚拟总表、选定 components 或下级 Scope roll-up。Overall 总进线表存在时优先作为全用能正式口径；分类表只做构成和差异校验。

首期不使用 LLM 自动映射。机器可以复用已确认规则和做重复劳动，但发布必须由人确认。

## 6. Raw Reading 到 Interval Fact

处理顺序：

1. 标准化时区和数值；
2. 按 meter + timestamp 去重和排序；
3. 保留累计读数；
4. 相邻有效读数做差；
5. 用实际区间时长计算 average rate；
6. 检查负差/复位、缺口、异常跳变和不规则间隔；
7. 生成可追溯 Interval Fact；
8. 再执行虚拟表和正式聚合。

重传同一文件必须幂等。重叠批次出现不同值时记录冲突，由确定性策略选择规范值，不能静默覆盖。

## 7. Attributes、Calendar 与 Tariff

- 新加坡公共假日按年份版本化；
- 营业时间按 Project 默认、Node 覆盖；
- occupant_count 首期允许代表性日均/24 小时人数；
- comparison_area_m2 用于归一化；
- Tariff 必须按 Project 和生效时间配置；
- 未确认值标记 provisional；
- 缺数据时隐藏对应模块，不用 mock 伪装成正式结论。

## 8. Metrics & Rules

首期 Metric：

- total usage；
- daily average；
- peak rate/time；
- own-history change；
- same-tier rank；
- kWh/m²、kWh/person；
- off-hours usage/share；
- coverage 和质量事件。

首期规则：

- 用能异常；
- 人均异常；
- 单位面积异常；
- 非营业时段异常。

阈值可由 admin 在有限表单中配置。规则输出必须保留 Fact、Baseline、Impact、Possible Cause、Action 和 Evidence。

## 9. Template Draft

每个 Project 创建：

- 一个 Project Overview Template；
- 每个 Tier Definition 一个 Tier Template。

AI 可读取已发布层级、映射、属性、数据覆盖和 Component Catalog 生成一次 Draft。admin 只调整受控模块的启用、顺序、标题和有限参数。

如果数据条件不满足：

- 缺面积：隐藏 EUI；
- 缺人数：隐藏 per-person；
- 缺费率：隐藏 cost；
- 样本少：隐藏 Bell curve；
- 历史不足：Forecast 只能标 Preview 或隐藏。

## 10. Preview、Validate 与 Publish

admin 选择真实 Project、Scope 和时间段预览。Validate 至少检查：

- Tier ordinal 和父子关系有效；
- 单节点无意义 Tier 已处理；
- 没有孤立 Meter；
- 映射和 source label 完整；
- 总表与分表不重复；
- 虚拟公式无环且单位兼容；
- Metrics 与 Components 已注册；
- 建议均能生成 Evidence；
- 未确认元数据在 UI 中明确；
- 模板不包含任意 SQL、React、HTML 或自由 Prompt。

Publish 产生不可变 Hierarchy、Formula、Metric/Rule 和 Template Revision 引用。只把 Published Project 暴露给 user。

## 11. Analysis Run 与复跑

用户选择 Yesterday、Last 7 days、Last 30 days 或 Custom，系统创建 Analysis Run，至少保存：

- Workspace、Project、Scope、Tier；
- from、to、timezone；
- Template Revision；
- Hierarchy/Formula/Metric/Rule/Calendar/Tariff Revision；
- Data Snapshot；
- 结果 Artifact；
- Evidence Bundle；
- 发起者、状态和时间。

相同版本和 Snapshot 必须可确定性复跑。使用新数据运行时创建新 Run，不覆盖旧报告。

## 12. 未来 AI 修改模板

~~~text
Conversation
→ Template Change Proposal
→ Schema and permission validation
→ Diff
→ Preview
→ Human approval
→ New Template Revision
~~~

AI 无权修改历史 Run，也无权自动发布。
