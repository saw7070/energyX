## 3. 三条公共验收 Seam

### Seam A：Published Overview

- minimum 与 full 必须绑定同一 Project、Scope、Snapshot、Project Release、Report-time policy revision；不允许跨项目或旧身份残影。
- 默认只展示 `Conclusion / Why / Action`；`Evidence / Uncertainty / Verification` 本地展开，正文不重复、不截断事实、不用复杂句堆叠。
- 普通 Overview GET 必须 `0 Provider / 0 mutation`，读取发布后的不可变投影；没有新 Snapshot/Release 时不重算。

### Seam B：AI Analyst

- 直接入口、顶栏入口、Overview Explore/Ask AI 都由服务端解析到该 Scope 的有数据窗口，Preschool 当前应落到 June 1–30 的 exact Snapshot/Release，而不是最新 30 天空表。
- 新 Session 和仍可解析的历史 exact Session 可发送；历史 Snapshot/Release 不可解析时保留原消息只读，并提供明确的“在当前数据继续”新 Session，不静默改写旧会话。
- 点击发送后立即展示 `Preparing`，区分上下文准备与 Provider first-token；优先复用发布时物化的 Overview/Analysis Context Package，普通读取不触发 Provider。
- Skill 状态必须区分 `available` 与 `actually used`，Run Evidence 能证明本次加载的 Skill 与版本。

### Seam C：Project Release / Saved Analysis

- Tuya 与 Ngee Ann 的 Section、标题、窗口和证据来自 Release Manifest 与确定性事实，不能硬编码示例结论。
- 新 Release 不修改旧 Saved Analysis；旧 Snapshot/Release 能打开则按原身份只读恢复，不能打开则诚实 unavailable。
- Project 切换后上一项目的 DOM、Session、AI Artifact、Snapshot/Release 身份不能残留。

开发可以并行，`main` 合并必须串行：

1. AI Analyst 最小可用切片（若与其他 owned paths 无交叉）；

## 6. 发布前验收

### 自动化与独立复审

- 三条公共 Seam 全部通过；root、Contracts、Data Gateway、API、Web production build 与 docs strict/link/diff-check 通过。
- Review 固定 exact base/head/merge-base，Standards 与 Spec 双轴分别给出 P0/P1/P2。
- CI green 只说明仓库门通过，不等于浏览器、Provider 或生产验收。

### 浏览器与账户

- 独立 admin 与 user 账户验证 Preschool、Ngee Ann、Tuya 的可见性与切换隔离。
- 每项目验证 direct URL、顶栏、Overview minimum→full、AI Analyst 发送/历史/fork、Saved Analysis。
- 记录首屏 minimum、full、AI Preparing、Provider request 和 first token 的实际耗时；禁止只凭主观“快”。

### Provider 与写入边界

- 登录、切换、Overview 读取、Saved 读取、AI 上下文解析前后，Provider counter 与 Metadata/Shared Storage mutation 均保持不变。
- 只有显式 AI Run 可调用 Provider；需记录 run/model/timestamps/error/first-token，不把普通 GET 冒充 Provider 验收。

## 7. 不可变 Release、回滚与终态

1. 从已合并 exact main 的 clean checkout 构建完整不可变 Artifact；Build Host 与 Release Host 双 verify SHA/Manifest/Node/BUILD_ID。
2. 发布前创建并验证 Shared Storage/Metadata 备份；原子切换 current；API/Web/nginx、health/ready/login/三项目页面全部复核。
3. 生产重复执行浏览器、多账户、Provider/写入边界与性能观测；任一 identity、串数据、普通 GET 写入、服务健康或资源门失败，回滚到已验证 previous physical Release。
4. 将最终 exact main、artifact SHA、生产 Release、浏览器/Provider/回滚证据写入 `records/`；完成后把本文状态改为 `completed`。

## 8. 夜间状态协议

每次状态更新使用同一格式：

`任务 → Session → Issue/PR → base/head/merge-base → owned files → RED/GREEN → tests/CI → browser → Provider → deployment → P0/P1/P2 → next action`

允许的状态依次为：

`NOT-STARTED → RED → GREEN-LOCAL → REVIEW → CI → MERGE-READY → MERGED → BROWSER-ACCEPTED → DEPLOYED → RELEASE-ACCEPTED`

不得把 `GREEN-LOCAL`、`CI` 或 `MERGED` 写成“已上线”。本文由主 Session 单 Writer 维护；Agent 通过结构化消息回报，不并发编辑。

## 9. 停线条件

- origin/main 或 PR head 漂移且尚未重审；
- 用户数据、账户、Snapshot、Release 或 Provider 边界不明确；
- 发现跨项目残影、历史 Saved 被改写、普通 GET 触发 Provider/写入；
- 生产锁、staging、备份、依赖层或 Release identity 不满足 Runbook；
- 相同 P0/P1 连续无法闭合。此时保留现场和证据，不靠删除锁、放宽契约或跳过测试继续。
