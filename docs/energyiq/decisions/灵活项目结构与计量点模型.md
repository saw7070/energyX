# 灵活 Tier、项目节点与计量点模型

## 决定

EnergyIQ 不预设 Company → Estate → Block → Floor → Room → Area → Circuit 的固定层级。每个 Project 根据硬件安装、客户业务和真正需要的比较范围，自底向上配置自己的 Tier Definition。

Project 是配置和分析根，不计入空间 Tier：

~~~text
Workspace
└── Project
    ├── top scope node
    └── top scope node
~~~

因此即使一个 Project 有多个 Estate，也不需要增加 Company Tier；Project 本身就是多个顶层节点的汇总范围。

## Tier 的编号与展示

- Tier 1 是最低有独立业务意义的层，不固定为 Circuit；
- Tier 2、Tier 3 依次向上；
- 计算与 API 使用 tier_definition_id、ordinal 和 scope_id；
- UI 使用管理员配置的 alias 和节点 display_name；
- 客户不会看到 “Tier 1-1” 作为主要名称。

示例：

| 内部 | Alias | 节点显示 |
| --- | --- | --- |
| Tier 1 | Circuit | Office Load 1 |
| Tier 2 | Room | Room 01 |
| Tier 3 | Block | Block A |

## 什么时候需要一层

只有当该层具有独立分析、汇总、导航、权限、数据绑定或属性意义时才创建。典型判断问题：

1. 用户会单独选择它看结果吗？
2. 它会与同级对象比较吗？
3. 它有面积、人数、营业时间、用途等自己的属性吗？
4. 物理或虚拟计量点会直接挂在它上面吗？
5. 它未来可能成为权限或发布边界吗？

多个子节点并不自动要求增加父 Tier。反过来，只有一个节点也可以保留为一层，只要它具有上述独立意义。

只有单节点、无属性、无独立用途的 Tier 可以保存为未完成 Draft；Validate/Publish 时警告，并要求管理员删除或填写保留原因。

## 配置方式

Tier Definition 自底向上确认，真实节点树在 Tier 锁定后自顶向下创建：

~~~text
Define lowest meaningful tier
→ Add parent tier
→ Review and lock Tier Structure in Draft
→ create top-scope node instances
→ add child node instances down the tree
→ configure attributes
→ attach meter points
→ Validate
→ Review & Publish Project Configuration
~~~

Tier Structure Lock 只是 Draft 内的配置检查点，不产生客户可见版本。正式发布统一发生在第五阶段 Review & Publish。

MVP 重点支持 2–4 Tier。数据库和服务接口保留 5–7 Tier，但不为每个深度单独制作页面。跳 Tier 分支也只保留数据模型可能性，MVP 不在 UI 开放。

Admin 界面必须区分两件事：

- **Tier definitions**：纵向列出每层的 ordinal、业务别名、说明和节点数量；
- **Hierarchy tree**：以可展开树展示真实 Node 的 `parent_id` 关系。

两者属于 Structure 阶段的连续子步骤，而不是同屏同时编辑：

1. **Tier Setup**：编辑 ordinal、alias、说明与独立业务意义，确认后锁定；
2. **Hierarchy Builder**：主区域编辑真实树，右侧只读显示已锁定 Tier 小图；需要修改层数或顺序时必须通过显式影响检查。

锁定后修改 alias 不自动改写已有 Node display name。已有 Node 后增删或重排 Tier 必须检查影响；完成 Meter Mapping 后，MVP 不允许普通内联修改 Tier 深度或顺序。

真实节点不能按 Tier 横向并排成等宽列，因为不同父节点可以拥有不同数量的子节点。例如 Level 6 可以有 9 个 Circuit，Level 7 可以有 12 个；某个 Block 可以有 3 个 Room，另一个 Block 可以有 7 个。管理员从树中选中节点后再编辑名称、父节点、面积、人数等属性，并在选中父节点时添加下一层子节点。父节点缺失或层级不合法的节点集中显示为待分配项，不能在界面中静默消失。

### Node display name 唯一性

- 唯一范围是 `Project + Tier + immediate parent`；
- 同一 Level 下不能出现两个同名 Room，同一 Room 下不能出现两个同名 Circuit；
- 不同父节点下允许重名，例如 Level 1 和 Level 2 都可以有 `Room 1`；
- 比较时忽略大小写、首尾空格和连续空格，`Room 1`、` room 1 `、`ROOM  1` 视为同名；
- 自动新增、人工改名和更换父节点都必须即时检查；Validate/Publish 在服务端再次兜底；
- 连续新增子节点后继续保留原父节点上下文，方便在同一分支批量创建。

每个树节点右侧提供 `+` 上下文入口：添加下一 Tier 直接修改空间树；Physical Meter 和 Virtual Meter 入口携带当前 Scope 跳到 Meter Mapping。计量点不因此成为空间树子节点，空间树和计量拓扑仍分别存储。

在当前节点使用 Meter 入口，永远表示该 Meter Point 代表当前节点。下层计量点必须先创建或选择下层 Scope，再挂到该 Scope；常见的一对一 Circuit 场景可以提供 `Add Circuit & Configure Meter` 快捷操作，但底层仍保存两个独立对象。

## 样板结构

### Ngee Ann

~~~text
Project: Ngee Ann Polytechnic
└── Tier 2 / Level
    └── Tier 1 / Circuit
~~~

Level 6 与 Level 7 直接属于 Project。现有 Block Test 是历史演示包装，目标配置中移除。

### Preschool

业务目标：

~~~text
Project
└── Tier 3 / Block
    └── Tier 2 / Room
        └── Tier 1 / Circuit
~~~

但 Charles 数据只给出 Centre × Circuit，未给出可信 Block/Room 对应关系。当前 Centre → Circuit fixture 可继续做数据验证，正式三层节点必须由管理员确认，不能根据 circuit label 自动猜测后直接发布。

## 同级比较与切片

选定一个祖先 Scope 后，只比较它下面同一 Tier Definition 的子项：

- Project 下比较各 Block；
- 某 Block 下比较各 Room；
- 也可以在 Project 范围内比较所有属于某 Tier 的节点，但必须说明祖先范围和聚合方法；
- 子项不与祖先总量直接比较。

比较前检查：

- 资源与业务分类一致；
- 节点可比，且没有重复计量；
- 时间范围与时区一致；
- 数据完整度达到门槛；
- 面积/人数差异显著时使用归一化指标；
- 样本少时不画 Bell curve 或宣称分布异常。

通用切片引擎接收 ancestor_scope_id、target_tier_id、time_range、metric_id 和 category，而不是针对 Room/Floor/Block 写不同代码。

## 计量点可以挂在任意节点

Meter Point 与空间树分离。一个物理总表可以直接挂在 Level 或 Block，同时更细的分表继续挂在 Room 或 Circuit：

~~~text
Level 7
├── Total Office Light     [physical, total, light]
├── Total Office Load      [physical, total, load]
└── Room 701
    ├── Lighting           [physical, component, light]
    └── Socket Load        [physical, component, load]
~~~

这不会把总表变成一个空间 Tier，也不会要求 Meter Point 只能位于叶子。

## 空间树与计量拓扑必须分开

**空间树**回答“用户在看哪里”。  
**计量拓扑**回答“哪些表构成哪个总量、哪些表参与公式”。

如果合成一棵树，会导致：

- 总表被误当成父空间；
- 总表和分表重复相加；
- 虚拟表公式被误当作导航层级；
- 同一节点无法同时表达多个业务分类或正式聚合口径。

## 正式聚合口径

对 scope + resource + category：

1. 优先使用配置为 official 的有效物理总表；
2. 没有物理总表时，可使用已发布虚拟总表；
3. 再没有时，才聚合明确标记为互不重叠的 component；
4. standalone 默认不进入总量。

不按名称猜 “Total”，也不把正式总表与下级 component 再次相加。all-category 总量由 load、aircon、light、other 的正式且不重叠口径构成。

若存在覆盖整个 Scope 的总进线表，使用 `category = overall`：

1. Overall 正式总表优先作为该 Scope 全部用能；
2. load、aircon、light、other 只用于构成分析和总分差异校验；
3. 不得把 Overall 与分类总表再次相加；
4. 没有 Overall 时，才汇总互不重叠的分类正式口径。

## 虚拟计量点

虚拟表以 Interval Fact 为输入，支持受控加减：

~~~text
Block C = Estate Total - Block A - Block B
~~~

发布校验：

- 输入存在且在允许的 Project 范围内；
- 资源、单位和时间粒度兼容；
- 依赖图无环；
- 不能重复引用同一事实；
- 缺失输入标记 incomplete；
- 负值生成质量事件；
- 公式快照自动记录输入、系数、生效时间和发布人。

配置通常一次完成，因此 MVP 不提供复杂版本管理页面，但历史 Analysis Run 必须保留当时公式快照。

## 电、水与碳

Electricity 和 Water 共用 Project、Tier、Node、Meter Point、Topology、Formula、Import Batch、Interval Fact 与质量模型：

- 电：累计 kWh → 区间 kWh，可派生 average kW；
- 水：累计 m³ → 区间 m³，可派生平均流量；
- 水只在项目配置后展示；
- 碳由电量和版本化排放因子未来派生，不作为当前物理计量资源。

## MVP 明确不做

- 客户编辑空间树；
- AI 自动映射并直接发布；
- 跳 Tier 配置 UI；
- 为 5–7 Tier 单独硬编码页面；
- 未配置 Water 的空页面；
- Carbon 报告。
