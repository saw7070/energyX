# 目标与状态

让用户第一眼看到值得处理的问题、明确行动和有依据的收益；报告保留分析细节与呈现自由。本文记录 9 月 17 日确认的首版产品方向与开发准备。accepted 表示产品方向确认，不表示代码已实现或生产已切换。下文明确标注的暂缓项不作为首版阻塞。

已确认方向：先探索并产生候选 Insight–Action，再与项目清单对比维护；首版正式 Insight 与 Action 一对一；最多展示三条真正有价值的重点。候选数量不限制为三条，不为凑数编造价值。

首版维护最多 6 个活跃 Insight–Action 对，Key Points 从这 6 个中精选最多 3 个。报告引用本次有证据支持的正式记录；首页展示当前最值得关注的正式记录。两者使用同一事实来源，首版同次发布优先保持所选重点一致，不为实现两套排名增加复杂度。

## 为什么调整

Charles 反馈自动报告细节丢失、文字冗长、价值不直接。不能只压缩摘要或装修首页；分析需要明确设备、时段、可执行行动，以及成立条件下的节电、费用或运营价值。

| 选项 | 优点 | 局限 |
| --- | --- | --- |
| 先写 HTML，再提取建议 | 保持报告生成自由 | 容易事后拼凑建议，证据与行动不一致 |
| 本期候选直接成为首页 | 新鲜、简单 | 重复建议、忽略行动状态，跨期不连续 |
| 独立探索 → 清单对比 → 发布报告与精选 | 兼顾探索、长期管理和用户价值 | 需要候选与正式对象映射、版本及发布一致性 |

本轮采用第三种作为首版目标；原有生成链路在验证通过前保留。

## 建议执行流程

1. 冻结本次全部可用项目数据的截止日期，以及项目资料、Skill 版本。全部数据交给 Agent 工具读取，不把原始数据全塞进模型上下文。Agent 先探索数据、项目资料和方法，产生本期候选；不预先要求复述旧清单。
2. 每个候选包含：具体对象与时段、观察事实、证据引用、可能解释及不确定性、一个主要行动、预期价值与计算条件。推测不能写成已确认原因，持续用电不能直接认定漏电。
3. 对照有权限读取的项目 Insight–Action 清单：匹配已有、提出新增、补充证据、发现冲突。匹配依据包括对象、现象、运行条件和行动目标，不能只看标题相似。
4. Agent 读取已有实施状态和反馈后修订建议。不得把已实施措施再次写成尚未执行，也不得自行覆盖人的反馈。无法确定同义关系时保留待核对，不自动破坏性合并。
5. 从合并后的本期有效候选中选择报告重点，生成自由排版的 HTML。报告可以保留其他图表、平面图和背景，不是三个卡片的机械拼接。写报告时出现新证据可回到候选修订。
6. 联合审阅报告与结构化交付物：数字、对象、条件、行动与精选一致。通过后发布正式版本，并保留本次候选到正式 ID 的对应关系。失败保留草稿，不替换上一版首页。
7. 发布后重新评选项目首页 Key Points。对外刷新前应让报告、正式记录和所引用版本均可访问；技术实现可重试，但不能出现半套发布。

“独立探索”不等于永远不读历史。先形成独立候选，再带入已有清单和反馈，既减少初始角度限制，也避免重复建议。

## 产物怎么管理

| 产物 | 归属与保存方式 | 用途 |
| --- | --- | --- |
| 本期候选 | Run 下的结构化草稿；记录证据、采纳/淘汰原因 | 自由探索，不直接污染正式清单 |
| 正式 Insight–Action | Project 下稳定 ID、版本与状态；一对一 | 跨期去重，保存进展和最新证据 |
| Report | 保存本期 HTML、窗口和引用的正式记录版本 | 历史报告不可随清单变化被重写 |
| Key Points | 保存所选正式 ID/版本、排序、评选时间和选择理由 | 是清单的精选视图，不复制出另一套事实 |

一个正式 Insight 可被多份报告引用；每份报告通过关联记录保存当期证据。Insight–Action 一对一，不等于 Report–Insight 一对一。

相同问题新一期出现时补充证据，不复制行动。已有多个 Action 的历史 Insight 如何兼容仍需方案，不在本次文档工作中删除或强制拆分。不能为了凑一对一把同一事实无意义复制数次；真正不同的目标才拆分。

## 报告三条与首页三条

- 报告三条：本期产生或重新验证、与本期数据相关的正式记录；允许包含旧问题的新进展。
- 首页三条：项目清单中当前有效、对当前用户可见、最值得关注的记录；可保留仍未处理的跨期重点。
- 先应用权限、证据有效性、状态筛选，再由 Agent 排序。优先具体可行、收益有依据、时效重要的机会；安全风险必须有相应证据。
- 首页可有少于三条；等待数据时表达“观察中”，不是承诺已节省。已解决问题通常退出待处理重点，其结果仍在历史记录可查。
- 金额展示需已知电价及适用条件；不能可靠估算时显示明确非金额价值或待确认项。多个行动收益重叠时不直接相加。

## 首版更新规则

- 一次认可的报告分析成功发布后，重新评选 Key Points；首版沿用报告周/月周期。
- 用户反馈时立即更新行动状态；效果报告完成后重新判断优先级和成果。
- 每日取数不必触发完整分析；只刷新数据状态。安全实时告警是另一项能力，不声称月报能替代它。
- 并发分析保存各自草稿；正式合并时检查版本，防止旧任务覆盖新反馈。合并和发布需幂等，失败保留上一成功版本。
- 首版每次正式分析重新检查最多 6 条活跃记录；不要仅沿用旧结论。更复杂的证据有效期、独立每周精选和手动置顶暂缓。

## Skill 的改进方式

把跨期验证有效的分析方法、用户价值判断和表达习惯写入 Skill；项目事实放项目资料，当期结论放 Insight。不是每次发现就自动创建或修改一个 Skill。淘汰无价值候选保留简短理由，避免反复提出；人评审通过的经验再沉淀。

## 六个活跃槽位与筛选

- 最多 6 个活跃 Insight–Action 对；首页最多选 3 个。槽位是展示和持续跟进的上限，不是数据库记录总数的限制。
- 节电省钱、运营改善、有依据的风险和新探索均可入选。同一角度通常考虑 2–3 个候选，但不是强制配额，不凑满六条或三条。
- 每次候选先与已有内容匹配。重复问题更新同一正式记录的证据和来源，保留行动历史；新候选更有价值时可以替换低优先级活跃项，记录替换原因，旧项进入历史，不删除。
- 不确定是否同义时先保留草稿，不强行合并。首版无需建设复杂语义合并工作台。
- 选择关注收益依据、行动可执行性、时效和用户理解成本。纯统计描述、反复泛泛建议不占首页。

## 数据范围与时效

首版不向普通用户提供分析日期选择，Agent 可以访问全部已有项目数据，用历史理解规律和建立基准。一次运行使用统一数据截止日期，所有结果标明各自实际计算窗口。

近期有效性默认以最新可用完整 7 天为检查窗口；数据更新正常时对应最近一周。若数据已陈旧，明确显示实际截至日期，不将历史结论描述为当前问题；不足七天则如实说明。历史数据全量可用不等于每个指标必须按全历史平均，也不能消除迟到数据、缺口和口径问题。

不为首版扩建时序平台或重新实现底座；复用现有项目数据读取与快照能力。每日 API 同步与报告更新分别运行：同步不自动意味着已完成新分析。

## 行动、Effects 与退出

| 用户看到的状态 | 处理方式 |
| --- | --- |
| 待处理 | 展示问题、行动和条件性预期收益，参与 6 选 3 |
| 观察中 | 用户确认已执行后等待可比读数，停止重复催促相同行动；未完成观察仍保留跟进记录 |
| 已评估 | 展示实际观察变化；问题消失可退出活跃槽位，效果不明显则修订建议继续跟进 |

这些是用户展示状态，开发时映射现有 Action/feedback 状态，不新建平行状态系统。用户确认执行不等于问题解决，观察变化不自动等于因果节能。

Effects 先复用原行动下的反馈记录与报告，不开独立模块。退出活跃槽位不取消后台观察、不删除历史或打断既有报告引用。

报告可连续关注同样问题，但必须交代最新证据或进展。持续未解决的重要问题可以保留；不能为了新鲜感换题，也不能无新证据长期重复“建议检查”。

## 首屏展示与首版边界

新增 Key Points 入口，目标作为普通用户首屏。最多三个清晰卡片：左侧问题标题加一句证据/解释，右侧一个行动及预计收益。英文展示，金额和节电量突出；金额未知不编造，安全异常不得夸大为故障。

Reports、Explorer、AI Analysis 保留作为后续深入入口。详情页重新设计、普通用户自主分析、个人精选、复杂并发分析产品体验、独立 Effects 页面、预测自动校准暂缓。既有服务端权限、基本幂等和发布失败保留旧版本继续有效。

首版由管理员触发或既有定时报告更新共享清单，不让任意聊天自动改动共享首页。只有明确发布且权限符合的项目分析才更新清单和 Key Points。

## 开发顺序与验收清单

下列均为待开发/待验证，不代表已完成。

- [ ] P1：核对现有 Insight、Action、report run 和 Skill 接口；补充最小候选与正式 ID 映射、六槽位及精选版本契约，复用现有业务对象。
- [ ] P2：调整分析 Skill/提示与结构化产物：具体对象、证据、一个行动、收益依据；用 Tuya 全部可用数据实际跑一次，近期验证候选，不能人工硬写三个卖点替代生成能力。
- [ ] P3：串通候选去重、最多六个活跃项及最多三个精选；保存来源报告、数据日期、替换原因；报告与精选联合检查通过才更新首页。
- [ ] P4：实现英文 Key Points 首屏，显示真实生成内容；少字、收益醒目、左右对应，无有效内容时显示清楚的空状态。
- [ ] P5：再跑一次分析，验证重复发现不增生、已反馈行动不被覆盖、历史引用可回查、生成失败保留旧版；用另一数据截止日期验证时效变化。
- [ ] P6：展示给 Charles，判断是否至少有可理解、值得执行的机会；有效方法写入 Skill，无价值候选退出展示。报告精简重复文字但保留设备、位置、时间、数字和证据细节。

实施优先级：内容价值与真实链路 → 首屏展示 → 复跑验证。可在 P2 期间用已有真实内容推进前端结构，但首屏验收必须使用本轮正式输出。新增 1 对 1 约束不强制破坏历史一对多记录，历史保留、首版新发布遵守约束，后续再决定迁移方法。

验收底线：0–6 条活跃记录，0–3 条精选；新正式 Insight 与 Action 一对一；无重复虚增、无编造金额或真实节能、无删除历史；用户能读懂“哪里有问题、做什么、可能得到什么”。三条是价值目标，不是凑数要求。

关联：[已有小闭环设计](2026-09-16-Insight行动模拟与经验闭环.md)。旧文的“先报告后整理、允许一对多”描述为先前设计/实现；新开发以本文首版方向为准。生产实现状态另看验收记录，不从 accepted 推断完成。

## 四指标与 PDF 首屏实现
- 固定四指标：记录用电量、估算电费、营业时段外用电占比、完整同步 15 分钟最高平均功率。来源为对应报告冻结 analysis CSV 与配置版本，不使用模型数字、不混入新数据。覆盖率可见。
- 复用 operational policy 计算器和保存的版本；层级已改变时不回退到新规则。按报告版本更新，API 首次读取计算，进程内缓存最多 32 份；新报告使用新输入，并非独立的每日首页刷新任务。
- 三条重点引用 Insight–Action。新增可选 category/cause 和生成指令；旧报告不强行补原因或安全结论。
- 深绿总览、四指标、整张重点卡、右上收益、下方行动入口及展开证据。首版顶部为中性标题，不伪造 AI 总结，不相加重叠收益。
- 现场问答按钮及事实保存、个性化 AI 顶部总结待接入；Review action 仍进入已有行动页。

## 现场问答与顶部总结接入
- key-point-candidates 支持 summary 和每条 question，跟随候选验证后存入同一个不可变发布版本。旧报告不凭空补 AI 总结；仍有通用现场提问入口。被过滤的重点不继续使用原始顶部总结。
- 现场问答保存到 Action 的独立 site notes 历史，保留问题、回答、记录人及时间，使用 requestId 去重，不修改行动状态、设备、配置或实际效果。
- UI 和 Agent 共用 site-notes API。Agent 工具 action_record_site_note 只能记录用户明确提供的信息；不能将回答推断为执行。
- 共享 Action 的现场信息由项目成员查看；私有 Action 保持原有所有者限制。页面明确提示共享范围。
- 后续报告 project-actions.json 包含最近现场信息；主动更新模拟时同样带入。回答不会自动触发新模拟，也不会覆盖旧模拟。
