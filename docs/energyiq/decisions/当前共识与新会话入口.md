## 1. 60 秒结论

EnergyIQ 是一个面向能源管理决策的产品，不是通用 BI，也不是每次由 AI 临时生成页面的全 Agent 系统。它由三条用户主线组成：

1. **Overview**：项目专属、可确定性复跑的决策看板，先给异常和行动建议，再给图表与证据；
2. **Project Explorer**：按项目真实空间结构下钻，核查 Scope、Meter、来源读数、区间派生值和数据健康；跨节点比较与决策判断统一放在 Overview；
3. **AI Analyst**：直接复用 DataFoundry 的可信问数工作台，处理模板没有覆盖的追问，并展示 Task Console、Evidence 与 Trace。

**Data Map** 是第四个客户入口，首期只读。**Admin** 是独立的项目交付与平台运维后台。

当前路线是“数据底座 + 双功能 + 协同”：先让 Ngee Ann 的结构化模板形成客户可见闭环，同时让 Data Foundation 封口真实结果、AI Analyst 复用 DataFoundry 原生能力完成可信问数；二者各自跑通后再做上下文和 Evidence 协同。结构化模板是核心，AI Analyst 是增强。Excel 是当前验证与导入主通道；Tuya API 恢复后更换 Source Adapter，后续计算链不变。每天同步一次即可，但事实粒度保留 15 分钟。

## 2. 产品边界

### 2.1 要解决的问题

- Tuya 或 Excel 数据接入后，可靠地把累计读数转换为区间能耗；
- 针对项目实际结构做项目、层级、节点和回路分析；
- 主动指出高耗能、异常时段、人均异常、单位面积异常和非营业时段浪费；
- 用可追溯 SQL、指标版本、数据批次和规则版本支撑结论；
- 让客户选择 Yesterday、Last 7 days、Last 30 days 或 Custom 后复跑同一模板；
- 对模板没有覆盖的问题，允许用户继续用自然语言问数。

### 2.2 当前不追求

- 秒级或 5 分钟实时流处理；
- 客户自由拖拽搭建任意 BI 页面；
- AI 绕过审核直接修改并发布正式模板；
- 复杂 RBAC、设备级权限或四套角色页面；
- 机器学习异常检测、正式 Forecast、碳排核算；
- 一开始就把 5–7 Tier 的全部配置体验做完。

## 3. 租户、账号与角色

### 3.1 组织边界

- **Partner**：Tuya 等合作方，位于客户 Workspace 之外。
- **Workspace**：客户组织和数据隔离边界。一个物业管理公司通常对应一个 Workspace。
- **Project**：Workspace 内一个可独立配置、发布和分析的项目。一个 Workspace 可以有多个 Project。
- **Project 不是空间 Tier**。它是抽象的分析与配置根，因此不需要再创建 Company Tier 来统一最高层。
- 一个 Project 可以直接聚合多个 Estate、Block、Level 或 Room 等顶层空间节点。

### 3.2 MVP 权限

仅保留两类真实权限：

| 权限 | 人员 | 能力 |
| --- | --- | --- |
| user | FM、Boss | 查看已发布项目、运行 Overview、下钻 Explorer、使用 AI Analyst、只读 Data Map |
| admin | 我方人员，首期也可包含 Tuya 实施人员 | user 全部能力，加账号、项目、数据、层级、计量、规则、模板、发布与平台技术配置 |

FM 与 Boss 的权限相同，只是默认动线不同。出现真实的 Project/Scope 隔离需求后，再增加细粒度 ACL；出现 Tuya 不能访问平台级配置的边界后，再拆 partner_admin。

MVP 中用户默认可以查看其 Workspace 内全部已发布 Project。用户可属于多个 Workspace。正式 Project 数据和发布报告属于 Workspace 共享；个人对话和临时文件默认个人私有。

## 4. 客户信息架构与使用动线

### 4.1 顶部导航

客户界面默认英文：

- Overview
- Project Explorer
- AI Analyst
- Data Map

Project selector 与主导航位于同一顶栏。Water 只在项目已配置时出现；Carbon 仅预留。

### 4.2 Boss 动线

登录后优先进入 Overview：

1. 选择 Project；默认查看最新自然月 Report Edition，历史月份可按 Edition 切换；
2. 先看 Executive Action Summary、异常影响和数据新鲜度；
3. 再看自身历史、同级归一化比较、峰值时段与非营业浪费；
4. 点击证据进入 Explorer；
5. 需要继续解释时点击 Investigate with AI，完整上下文带入 AI Analyst。

### 4.3 FM 动线

FM 可从 Overview 的异常进入 Explorer，也可直接打开 Explorer：

1. 在项目树选择节点或计量点；
2. 查看来源提供或确定性派生的累计读数、区间能耗、平均功率、覆盖率和时间曲线；
3. 核查 Data Freshness、Connectivity（如 API 提供）、Flatline 和质量事件；
4. 核查总表、分表、虚拟表、Source Binding 与 Import Batch/Data Snapshot；
5. 带范围、时间、资源和版本进入 AI Analyst。

Explorer 不再承担同级比较、业务异常、节能建议或成本结论。这些由 Overview 的模板和规则生成；Explorer 只负责验证支撑它们的数据与计量。

Explorer 已确认的交互规则：

- Meter 显示自身健康；Scope 显示问题数量，只有 Official Aggregation Route 受影响时标红，否则子表问题使 Scope 标黄；
- Flatline 默认检查所有 Physical Meter，admin 可带原因静音；Virtual Meter 显示 Derived 并继承输入健康，缺输入为 Partial；
- 单表摘要固定为 Latest reading、Last data received、24h energy、24h average power、Peak interval-average power 和 Coverage；
- user 导出规范化 CSV，admin 另可下载原始 Excel/API payload；
- MVP 只做 Explorer 页面告警与 Admin Issue List，不做邮件、短信或推送；
- Overview/Explorer 双向保留 Project、Scope、Period、Resource 与 Run/Release/Snapshot；具体 Circuit 证据可直接选中 Meter，返回 Overview 时回到最近的模板 Scope；
- 树上 `Current data health` 使用最新同步状态，主区 `Selected-period quality` 使用当前所选时间段，二者不可混用。

不建设第二套完整聊天弹窗。页面只提供轻量入口，正式追问进入 DataFoundry 完整工作台。

## 5. 动态空间 Tier

### 5.1 核心规则

- 每个 Project 由 admin 自底向上配置 Tier Definition。
- Tier 1 是最低的有独立业务意义的空间/业务层，不写死为 Circuit。
- 计算使用稳定的 tier ordinal、tier id 和 scope id；客户展示使用 admin 配置的 alias 与节点名称，例如 Circuit、Room、Floor、Block、Estate。
- MVP 主攻 2–4 Tier；数据模型预留 5–7 Tier。
- Project 可有一个或多个顶层节点，Project 本身提供总汇总，不额外创建 Company Tier。
- 空间树与计量拓扑分开保存。
- Admin 中 Tier Definition 纵向说明层数和别名；真实 Node 使用可展开的 Hierarchy Tree，不按 Tier 横向并排。不同父节点可以拥有不同数量的子节点。
- Structure 分为连续的 Tier Setup 与 Hierarchy Builder：Tier Definition 自底向上确认并在 Draft 内锁定，真实节点树再自顶向下创建；Tier Lock 不等于正式发布。
- Node display name 在同一 immediate parent 和同一 Tier 内唯一，忽略大小写及多余空格；不同父节点允许同名。自动新增、改名、移动父节点和发布均校验。
- 树节点右侧 `+` 可新增下一 Tier，或携带当前 Scope 进入 Physical/Virtual Meter Mapping；Meter 不作为空间树 Node 保存。

### 5.2 什么时候增加一层

不是“下面有多个节点，上面就必须增加一层”。只有该层具有至少一种独立意义时才增加：

- 需要独立分析或汇总；
- 需要作为导航范围；
- 未来可能成为权限边界；
- 可以直接绑定计量点；
- 有自己的面积、人数、营业时间、用途等属性；
- 需要与同级对象比较。

只有一个节点且没有独立属性或用途的 Tier 可以暂存为 Draft，但在 Validate/Publish 时警告。管理员可以明确说明“保留原因”后继续发布。

### 5.3 比较语义

- 比较发生在同一选定祖先范围内、同一个 Tier Definition 的节点之间；
- 子项与子项比较，不把 Tier 2 的子项直接与 Tier 4 总量比较；
- 默认展示总能耗，也可按 load、aircon、light、other 分类；
- 面积或人数不同的节点，效率结论优先使用 kWh/m² 或 kWh/person；
- 元数据不足、节点类型不一致、样本过小或数据质量差时，只做描述或不展示，不强行得出效率结论；
- 增加 Tier 后继续使用同一切片引擎，不为 Room、Floor、Block 分别硬编码分析逻辑。

### 5.4 跳 Tier

数据模型可以预留父子 ordinal 不连续的能力，但 MVP 配置界面不开放跳 Tier。真实项目出现后再设计其模板、比较和校验语义，避免当前系统无端复杂化。

## 6. 节点属性与有效期

每个有业务意义的 Tier 节点可配置标准属性和少量自定义属性。首期标准属性：

- comparison_area_m2；
- occupant_count，先允许填写 24 小时代表性人数；
- operating schedule；
- 用途/业务类型；
- timezone 继承与覆盖。

Project 可提供默认值，节点可以覆盖。面积、人数、营业日历和费率应预留有效期；“按分析时间使用当时的人数和面积”是指历史复跑读取该时间段当时生效的值，而不是当前最新值。

## 7. 计量点、总分表与虚拟表

- Meter Point 是可查询的逻辑计量对象，可以是 physical 或 virtual。
- 实体表可以挂在任意节点，包括 Floor、Block 等父节点，不要求只挂叶子。
- 业务分类首期为 overall、load、aircon、light、other。overall 表示覆盖整个 Scope 全部用能的总进线表。
- Meter Kind 区分 physical/virtual；Meter Role 区分 total、component、standalone；Official Aggregation Route 单独配置，三者不能混成一个角色字段。
- 某个 scope/resource/category 只能有一个正式聚合口径；配置了物理总表时优先使用物理总表，不能再与其子表重复相加。
- 若没有总表，可显式选择互不重叠的子表聚合。
- 若存在 Overall 总进线表，正式全用能使用 Overall；Load、Light、Aircon、Other 只用于构成和总分差异校验，不再与 Overall 相加。

虚拟表使用受控线性公式，例如：

~~~text
Unmetered Block = Estate Total - Block A - Block B
~~~

公式允许引用物理表或已发布虚拟表，但必须无环、单位相同、时间粒度一致。输入缺失则结果不完整；负值产生质量事件，不静默改成 0。公式发布时系统自动保存不可变快照，首期不需要复杂的人工版本管理界面。

Electricity 与 Water 共用计量框架，只替换资源、单位和派生指标。Water 未配置时不展示。Carbon 后续由能源事实和版本化排放因子派生。

## 8. Excel、API 与事实层

### 8.1 两种来源的分工

- 目前 Tuya API 有问题，Excel 是实际接入和验收入口；
- Tuya API 恢复后成为每日主同步入口；
- 两者只实现不同 Source Adapter，统一输出 Raw Reading，不维护两套指标逻辑；
- 一个 Project 在模型上可保留多个 Source，但 MVP 不做复杂编排。Excel 是当前入口，Tuya API 恢复后替代日常 Excel；迁移期同一 Meter/时间区间只能选一个权威输入；
- Tuya API 是业务 Connector，不包装成 MCP；
- 当前不让大模型自动猜字段或节点映射。

### 8.2 当前 Excel 契约

现有 Ngee Ann 文件主要字段：

| 字段 | 含义 |
| --- | --- |
| Device Name | 数据源标签，需由 admin 映射到 Physical Meter Point |
| Time | 读数时间 |
| Active Energy | 累计有功电能，不可直接求和 |

系统先做确定性字段识别，再让 admin 确认。一个源 label 首期映射一个物理计量点。

### 8.3 存储与处理

原始与处理后数据都保存：

1. 保存不可变原始文件/API 响应、Import Batch 和 SHA；
2. 保存累计 Meter Reading；
3. 按 meter + time 排序和去重；
4. 相邻有效读数做差，生成 Interval Fact；
5. average_kw = interval_usage / 实际经过小时数，不能永远假设乘 4；
6. 再生成日、scope、category 和虚拟表聚合。

重传必须幂等。重复时间、重叠导出、负差/复位、间隔缺失、时间不规则和异常跳变都产生可追溯质量状态。每天拉取一次不改变 15 分钟事实粒度。

当前实现中，Raw 层保留重叠来源作为证据；Normalized 与 Interval Fact 对同一 Meter Point/时点选择覆盖结束时间更晚的来源。Excel 时间若因序列浮点误差落在整分钟前后 1 秒内，会先归一到整分钟。分析某个 Scope 时优先使用直接挂载计量；若没有，则对每个子分支使用最近一层可用计量，避免总表与分表重复相加。

分析时间统一使用 Project timezone 和左闭右开区间 [from, to)。界面自定义结束日期包含当日，后端转换为次日 00:00 的排他上界。

Project Explorer 默认使用 `Latest complete data day`：Project timezone 下最近一个整日事实已进入 `Available` 的日历日，并显示覆盖率。每日同步错过 1 次为黄色 Delayed，连续错过 2 次为红色 Stale；连续 3 个日历日有新时间戳但累计读数不变为黄色 Flatline。Tuya 契约未明确 heartbeat/online/last_seen 前，Connectivity 保持 Unknown。

Overview 首次进入默认 Last 7 days，Explorer 默认 Latest complete data day。完整周期预设不包含尚未结束的今天。数据过期或所选 Period 无数据时，预设语义保持不变，页面显示空状态、最近同步时间和 `View latest available data`，只有用户点击后才切换到最近可用区间。

## 9. 指标、比较与异常

一次可信计算至少固定：

- workspace_id；
- project_id；
- scope_id；
- tier_definition_id；
- time range；
- resource；
- metric_id / metric_version；
- hierarchy、formula、data snapshot、rule、calendar、tariff 和 template 版本。

当前 Metric Registry 已落地 9 个受控 Metric Revision，Rule Registry 已落地 5 个受控 Rule Revision。Project 级选择是 Draft；Enabled 与当前项目数据条件下的 Ready 分开。已支持：

- 区间总耗能、日均、峰值及峰值时间；
- 同一范围自身历史同类时段比较；
- 同一祖先下同 Tier 节点横向比较；
- 可靠元数据下的 kWh/m² 与 kWh/person；
- 非营业时段耗能与占比；
- 分类构成和数据完整度。

四象限可以使用 X = kWh/person、Y = kWh/m²；热力图可以展示 Tier A × Tier B、Tier × Time 等切片。Bell curve、分位数和四象限只在样本量与可比元数据足够时启用。

确定性异常首期只做：

1. 用电量高于自身历史基线；
2. 非营业时段持续用能；
3. 峰值时段异常；
4. 可靠元数据下的人均/单位面积归一化异常。

这些是 **Energy Behaviour Exception**，统一在 Overview 呈现。读数延迟、过期、Flatline、复位、单位冲突和覆盖问题属于 **Data Health Alert**，统一在 Explorer 呈现。Flatline 只说明“时间戳继续到达但累计读数不变”，可能是真实零耗能或疑似卡表，不能单独证明设备离线。

异常基线默认取同一 Scope 最近 4 个同类型、同长度完整周期的平均值，Project Calendar 区分 Workday、Weekend、Public Holiday；不足 4 个可比周期时只展示描述性变化，不判异常。`Compare with previous period` 单独使用紧邻当前区间、长度相同的前一时段，不能冒充异常基线。后续基线优先级仍是自身历史 → 配置目标/规则 → 可靠归一化同级 → 同级绝对值描述。

异常阈值进入 Project Rule Revision 并由 admin 配置，不得硬编码；未确认阈值只能为 `Provisional`。业务异常按额外耗电量和影响范围排序，首期只用 `Attention` / `High priority`，与 Data Health 的黄色/红色分离。确定性规则选择 Action Template，AI 只能润色，不得改变数字、优先级或事实强度。

每条 Evidence 固定包含 Scope、Period、当前值、历史基线、差值、贡献 Circuit、数据质量、Query/SQL，以及 Data Snapshot、Metric/Rule/Template/Release 版本。

每条建议遵循：

~~~text
Fact → Baseline → Impact → Possible Cause → Recommended Action → Evidence
~~~

缺少排班、门禁、设备状态或 FM 反馈时，只能写“可能原因”和“建议核查”，不能宣称已经确认灯没关或水没关。

## 10. 项目专属模板与复跑

- 不使用一张模板覆盖所有 Project；
- 使用受控 Component Catalog 和参考 Preset；
- 每个 Project 有一套 Project Overview Template；
- 每个 Tier Definition 有一套共享的 Tier Template，同 Tier 的节点共用，不做首期 per-node override；
- admin 可开关模块、调整顺序、设置规则阈值和营业时间，但不是自由画布，也不开放任意 SQL；
- 项目层级、硬件、属性和数据确认后，可由 AI 生成一次结构化 Draft；
- admin 预览、调整并发布不可变 Template Revision；
- 用户在 Interactive Analysis 中选择时间、范围和展示控件后自动刷新，不创建 Analysis Run；
- 已保存结果冻结当时的数据批次、结果和版本；Rerun 使用最新可用数据创建新结果，不覆盖历史。

Managed Overview 是默认客户报告模式：以自然月 Report Edition 组织稳定管理问题，各 Section 引用服务端解析的命名窗口并显示精确范围。Interactive Analysis 是独立探索模式，可切换 Project、Scope、Resource、Yesterday、Last 7 days、Previous week、Previous month 或 Custom；其模块共享一个用户选择的主 Period。两种模式不得互相冒充，任意日期筛选不能覆盖 Managed Overview 的自然月业务语义。

Overview 的默认粒度为单日 Hour、2–31 天 Day、更长范围 Week；用户仍可使用 Template 允许的粒度。Peak 始终指最高 15 分钟区间平均功率并展示时间，不称为瞬时功率。Coverage `<95%` 时只显示可得的部分图表与 `Partial data` 警告，隐藏业务异常和建议，并禁用 Save analysis / Generate report；Explorer 保持可核查。

第一版 MVP 只有 `Save analysis` 创建正式 Analysis Run。普通切换时间/Scope、下钻、展开、对比和 AI 追问只进入请求/Session Trace，不创建 Run 或 Query Receipt。保存 AI 正式结果、Generate report 和定时报告属于后续扩展；届时可复用同一 Run 语义。

Interactive Analysis 与正式 Run 必须调用同一确定性计算模块；正式 Run 只是额外冻结所用数据批次、结果 Artifact 和版本 Evidence。MVP 不建设任意历史 Snapshot 重放平台。Project Release 与 Template Revision 不修改、不删除；回滚通过重新激活历史 Release 并记录审计完成。

Interactive Analysis 的 Project、Scope、Resource、Period、granularity、comparison 和分类筛选等视图状态进入 URL，刷新或分享后可恢复；URL 不承载权限，服务端必须重新解析 Membership、Project Release 与可信 Context。恢复链接及未保存交互均不创建 Run，也不进入 Runs History，只保留请求日志；AI 交互另外保留 Session Trace。

`Save analysis` 产生 Workspace 共享的不可变 Run，并记录创建人和创建时间，同一 Workspace 的 FM/Boss 均可查看。第一版 user 只做手动保存、只读查看和 Rerun；PDF、每日/每周/每月 Scheduled Report 与邮件发送后置。

保存分析默认标题为 `Project · Scope · Period`，用户可修改标题和备注，但不可变 Run 内容不变。历史结果以只读 `Saved analysis` 打开；`Explore with these settings` 只把原参数带回 Interactive Analysis。Rerun 使用原配置和最新 Available 数据创建带 `rerun_of_run_id` 的新 Run，不覆盖旧结果。

Runs History 第一版展示 Name、Project、Scope、Period、Saved by、Saved at 和 Data status，并按 Project/Scope/作者筛选。后续 Generate report 只从同一 Run Artifact 生成站内 HTML/PDF；Scheduled Report 同样复用 Run，不另建第二套结果模型。

模板是受控 Schema，不允许任意 HTML、React、SQL 或 Prompt。将来 AI 对话修改模板时，只生成 Template Change Proposal，经过 Schema 校验、Diff、预览和人工发布后形成新 Revision，绝不自动覆盖正式模板。

受控 Schema 不代表从零重写 BI：Metric/Chart/Dashboard 分层与网格筛选吸收 Superset 的成熟结构，时间指标与比较结构来自 Rill 的验证模式，筛选范围与派生下钻采用 Metabase 的成熟交互原则；当前普通图表直接使用 Recharts，未来复杂多维热力图局部接入 ECharts，Admin 需要拖拽缩放时接入 React Grid Layout，AI 审批交互继续使用 CopilotKit。只提取成熟结构或直接复用前端组件，不引入第二套客户账户、权限、语义层和 Dashboard 运行时。完整边界见[项目专属模板与决策型分析](决策-项目专属模板与决策型分析.md#open-source-capability-reuse)。

Agent 以后可以按 `EnergyIQ Template Schema` 创建和调整 Catalog 中的模块实例，包括顺序、Section、受控宽高、图表 preset、标题、Top N 和交互；不能生成任意 React、ECharts option、SQL 或计算公式。Catalog 没有对应 Renderer 时，Agent 必须返回不支持并提出开发需求。模板变更只生成绑定 base revision 的 Proposal，经过校验、Diff、固定快照 Preview 和 admin 人工发布。

Catalog 由 EnergyIQ 自己定义并版本化，但不应退化为每张图一条写死配置：固定决策模块保证 Action/Evidence 可信，KPI、Time Series、Ranking、Composition、Heatmap、Quadrant、Distribution 和 Table 等通用模块通过受控输入槽位绑定 Metric、Dimension、Time Grain、Comparison 与 Filter。Schema 规定合法拼装结构，Catalog 规定具体模块能力，Template Revision 是项目实际组合，Render Plan 是当前 Context 下的临时执行结果。未来 Agent 可在这套有限语法内进行 L1 模板编排和 L2 分析组合；新 Metric、算法或 Renderer 仍需 developer/admin 发布 Catalog Revision。

新加坡节假日和 `08:00–18:00` 营业时间可作为 `Provisional` 配置展示。未确认的 Tariff、面积和人数指标仅在 Admin Preview 中出现，客户正式页面隐藏。Forecast 暂缓；正式发布至少需要约 3 个月完整历史并回测，最好有 6–12 个月。

## 11. Admin 产品

Admin 不是另一张 BI 看板，而是“把一个项目交付为可分析产品”的流水线。

### 11.1 Project Setup

Project 状态：

~~~text
Draft → Data connected → Mapping valid → Template ready → Published
~~~

正式 Admin 导航为：

~~~text
Overview

Access
├── Organisations
└── Users

Projects
├── Project Overview
├── Structure
├── Data Sources
├── Meter Mapping
├── Data Map
├── Templates
├── Knowledge
└── Assets

AI Operations
└── Runs & Traces

Harness Configuration
├── Harness Overview
├── Models & Routing
├── Skills & Methods
├── Tools & MCP
└── Context & Instructions
~~~

左侧 Project 是可展开的选择器；选中 Project 后，其配置项表现为子 Tab。`Project Overview` 显示 `Basics → Structure → Data & Meters → Analysis → Review & Publish` 五阶段进度和下一步动作，专业页面承担实际配置。Structure 内先用 Tier Setup 自底向上定义 alias，再锁定 Draft 并在 Hierarchy Builder 自顶向下创建真实树。Draft 可随时保存；Tier Lock 不是发布，正式 Validate/Publish 统一位于第五阶段。

顺序约束为 `Structure → Data Sources → Meter Mapping → Data Map → Templates / Knowledge / Assets → Review & Publish`。Virtual Meter 是 Meter Mapping 内的可选项，不单独设 Tab；它默认不参与官方汇总。

Meter Mapping 只能绑定 Structure 已存在的 Scope；缺节点时返回 Structure 补充。逐行确认 source label、Scope、resource、category 和 coverage 后，再统一复核 Official Aggregation Route，并可选创建 Virtual Meter。

### 11.2 全局配置与运维

复用 DataFoundry 的底层能力，而不是重做。导航上按管理员任务分为 Access、AI Operations 与 Harness Configuration：

- Accounts / Workspace Membership；
- Data Sources；
- Data Map；
- Knowledge；
- Assets；
- Models & Routing，包括 server-owned Model Profile、revision、visibility 和 fallback 顺序；
- Skills & Methods，分别表达 formal Skill 与 Method/SOP，不建立第二套 Store；
- Tools & MCP，把 registered/declared 与 Run 中 called/succeeded 分开；
- Context & Instructions，显示容量来源、组成层和 revision/fingerprint，不开放 raw Prompt 编辑器。

当前未接通的 Access 与 AI 页面保留在信息架构中，但必须明确标记 Later；不能用可点击空页面冒充已完成功能。

用户可以看到知识引用和自己的 My Assets；平台配置仍由 admin 管理。Knowledge 不是只有向量库，它包含原文、解析、切块、全文/向量检索、版本、作用域和引用。确定性能源 Fact、映射和规则不能放进 Knowledge Base 代替结构化数据。

Operations 后续逐步加入：同步/导入失败、复跑统计、用户典型 query、模型与 token 用量、AI Session Trace、异常 Workspace/Project 记录。普通 Runs/Trace GET 只返回 redacted manifest/status，不 decrypt、不写 audit。**目标能力、当前未实现**的 `View conversation` action 将允许 Project Admin 查看 exact Project 下客户本来可见的 user/assistant transcript，并在隐私说明中告知；它不返回 System Prompt、动态 Context、Knowledge 原文、Tool arguments/results、Provider options、secret、内部路径、隐藏推理或完整模型请求。Project Admin 永远不能调用 Protected Request raw reconstruct；Protected Request Payload、server-internal reconstruct/verify 与 audited access 均为 proposed target，当前生产事实仍是 hash-only。

### 11.3 Data Link / Data Map 的使用边界

DataFoundry 的 Data Link 可以继续作为语义关系与可视化基础。其语义层由数据源 schema/字段/关系、字段 profile、管理员定义的业务说明，以及带来源和置信度的推断关系组成。

EnergyIQ 的使用规则：

- Tier、Scope、Meter Binding、Metric、total/component 和虚拟公式属于权威配置，必须由结构化 Admin 数据提供；
- Data Link 可以发现或建议表/字段/Knowledge 之间的关系，但 inferred 不能覆盖 configured；
- user 在 Data Map 只读查看来源、关系和可信级别；
- admin 才能确认、纠正和发布关系；
- Agent 使用正式分析时只依赖已确认关系，推断关系只能作为探索线索；
- 模型、数据源、MCP 和 Skill 由项目运行配置选择，user 不需要手工挑选。

## 12. DataFoundry 复用边界

最终边界是：Energy Data Foundation / DuckDB 是数据事实底座，Project Recipe 是确定性计算器，Project Renderer 是 Boss/FM 的 Overview；DataFoundry 只作为可替换的 AI Analyst Runtime，不接管 Overview 的指标计算或页面渲染。

唯一账户、唯一 Session 和同一套问数工作台。直接复用：

- Auth、Workspace 基础、Session；
- Chat、Streaming、Artifacts、Preview；
- Task Console、Evidence、Trace；
- Files / My Assets；
- Knowledge、Data Sources、Data Link / Data Map；
- Models、Skills、Tools、MCP。

EnergyIQ 新增：

- customer Workspace 与 Project 交付语义；
- Tier Definition、Project Node 和 Node Metadata；
- Meter Mapping、Meter Topology、Virtual Formula；
- Raw Reading、Interval Fact、质量与每日同步；
- Energy Query Context；
- Metric/Rule/Component Catalog；
- Project/Tier Template、Analysis Run 和 Evidence。

不使用 iframe，不复制出第二套 DataTasksApp，也不建立第二套账户和配置数据库。EnergyIQ 的 AI Analyst 路由直接复用现有 DataTasksApp；Overview 只通过版本化 `EnergyAnalysisRequest` 与之交互，不依赖 Mastra/AG-UI 的内部实现。

DeepSeek V4 Flash 已完成 provider 和真实 Ngee Ann 问数实测，但同一 Scope/Period 曾分别返回 235.85078 kWh/640 条与正确的 247.981288 kWh/672 条，不能将“Run completed”当成可信问数通过；受控图表还暴露 `TIMESTAMP`/`TIMESTAMPTZ` 时区错配、Chart Artifact 触发依赖模型参数、requirements commit adapter 不一致及 60 秒超时。正式打通前只补 System Model Binding、Energy Query Compiler/Validator、Deterministic Chart Spec 和协议收口四个薄层，不新建 Runtime、Task Console 或 Provider 系统。详见[实测记录](../records/2026-08-03-DeepSeek-V4-Flash与DataFoundry实测记录.md)和[最终方案](决策-Overview改造与AI-Analysis打通最终方案.md)。

## 13. 两个样板 Project

### 13.1 Ngee Ann Polytechnic

目标空间结构：

~~~text
Project: Ngee Ann Polytechnic
└── Tier 2 alias: Level
    └── Tier 1 alias: Circuit
~~~

Project 不计入 Tier。现有 bootstrap 中的 Block Test 是历史演示包裹节点，目标模型应移除并将 Level 6 / Level 7 直接挂到 Project。总 Light、总 Load 和分回路可同时挂在 Level，但正式聚合不能重复相加。

同事的 Net-Zero 原型可吸收：真实 Excel 差分、总表与分表分开、Level/Circuit 模块、峰值与构成视图。不能直接吸收：硬编码设备分类、营业时间、费率、15% 阈值、建议文案和静态日期。

Ngee Ann Project Preset 的固定顺序为：`Action Summary → Data Status & Scope → Energy Overview → Level Comparison → Day Profile & Heatmap → Exceptions & Evidence → Recommended Actions`。Circuit Ranking 只作为 Level Comparison 或异常证据的下钻，不单独堆成长章节。

模块契约已经固定：Action Summary 最多 3 条并使用 `Problem → Impact → Action → Evidence`，无重要异常时显示 `No priority exceptions`；阻断质量问题先于并抑制受影响的能耗结论；Data Status & Scope 紧跟 Action Summary、不可关闭，并显示范围、区间、完整度、最近同步和版本。Ngee Ann 的两个 Level 只做描述性差异、自身历史和可用时的面积/人数归一化，不使用统计异常标签；每个 Level/分类的 Circuit 默认 Top 5、可展开全部。多日热力图默认 Date × Hour，单日默认 Level × Hour，并区分 Workday、Weekend、Public Holiday。Recommended Actions 首期只读，每条必须链接 Evidence、Explorer 或带上下文的 AI Analyst，不引入工单流程。

### 13.2 Preschool

已确认的目标业务结构是：

~~~text
Project
└── Tier 3 alias: Block
    └── Tier 2 alias: Room
        └── Tier 1 alias: Circuit
~~~

但 Charles 的现有数据契约只明确 30 个 Centre 与每个 Centre 的 9 个 Circuit，没有可信的 Block/Room 节点映射。Circuit 名称中出现 Living Room、Kitchen 等文字不等于已确认 Room 层。

因此：

- Charles 报告继续作为决策模块和视觉意图的模板种子；
- 当前 Centre → Circuit fixture 只用于数据与界面验证；
- 正式三层节点必须由 admin 根据真实项目结构和 Charles/硬件资料确认；
- 在映射完成前，不得把自动猜测的 Block/Room 当作已交付事实。

Preschool 的正式泛化只在 Ngee Ann 已于受控测试环境通过导入、发布、运行、Overview、Explorer、AI 和追溯完整验收后开始。
