# Charles 系统价值复核与两批数据连续演示决策

## 1. 背景

Charles 提出了一个合理而且必须正面回答的问题：

> 新数据进入后，再让 Claude 按统一模板生成一份新 HTML，不就可以了吗？EnergyIQ 作为系统的意义是什么？

独立判断是：**对单项目、低频、一次性报告，这条路线确实可行，而且可能更便宜。** 如果 EnergyIQ 最终只是把新数据改写成另一份静态 HTML，那么系统没有形成足以替代该流程的价值，Charles 的质疑成立。

EnergyIQ 的价值不能定义为“生成页面”，而必须定义为：

> 把模型的一次性分析能力产品化为一个可信、连续、可追问、可复核、可协作的能源分析与运营决策流程。

现有页面虽然已经具备真实 KPI、图表、AI Slot 和 Evidence，但 Charles 仍未直观看到上述差异。这不是靠继续解释架构能够解决的问题，必须用一条客户可见的连续数据演示证明。

## 2. 评估过的方案

| 方案 | 做法 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- | --- |
| A. 每批数据重新让 Claude 生成 HTML | 上传数据、重复 Prompt、输出一份新 HTML | 一次性效果快，适合临时报告 | 需要重复解释和人工核对；版本、Evidence、连续追问、权限和历史关系依赖人工 | 作为临时分析方式保留 |
| B. 只做固定 Dashboard 模板 | 数据更新后刷新 KPI 和图表 | 稳定、快速、易理解 | 如果只复读数字和图表，仍没有足够决策价值 | 不足以单独成为产品 |
| C. 固定 Renderer + 可信数据 + 连续 AI 分析 | 页面结构稳定；新 Snapshot 自动更新数字，AI 继续调查并关联前后发现 | 同时提供速度、可信度、连续性和决策闭环 | 必须跑通 Snapshot、Finding、Evidence 和交互链 | **采用** |

## 3. 决定

选择 **C：固定项目 Renderer + 可信 Snapshot + 连续 AI 分析**。

Charles HTML 继续作为视觉蓝图和人工验收参照，保留其有效的信息结构和视觉表达；不让 Agent 每次生成新的正式 HTML/React 页面。数据变化只生成新的可信 Snapshot、确定性 ViewModel 和版本化 AI 结果，不重新生成产品界面。

下一项北极星验收不是增加更多平台能力，而是完成一次 **两批数据连续演示**，直接证明：

1. 新数据进入后不需要重新写 Prompt 或重新生成页面；
2. 确定性数字和图表自动使用新 Snapshot；
3. 旧分析仍能说明当时对应的数据，而不会冒充当前结论；
4. AI 能识别新的、重复的、已缓解的或逐渐结构化的问题；
5. 每个重要结论都能回到同一 Snapshot 的 Evidence；
6. 用户可以从该 Finding 继续追问和调查。

如果这条演示不能成立，应暂停扩建 Overview/AI 平台，重新评估“系统相对一次性 Claude HTML 是否有足够价值”。

## 4. Charles 反馈揭示的当前产品缺口

### 4.1 信息组织没有从用户决策出发

页面不能按照“系统有什么模块”排列，而应按照用户理解和决策的顺序组织：

~~~text
发生了什么 → 为什么重要 → 为什么可能发生 → 应该怎么办
           → 做了预计怎样 → 不做预计怎样 → 如何验证
~~~

首屏应先给出最值得处理的 0–3 个决策主题，再用图表、数字和 Evidence 支撑。Level、Circuit、Heatmap 等是解释手段，不是页面故事本身。

### 4.2 文字不说人话且过长

主页面默认采用以下阅读预算：

- Finding 标题：一行，说清对象和变化；
- What：一句话说明发生了什么；
- Why it matters：一句话说明影响或暴露；
- Why likely：最多两个 Evidence 要点，未确认原因必须标为 Hypothesis；
- What to do：一到两个具体动作；
- Outcome：分别说明“做”和“不做”的预计结果；
- Verification：一个可观察指标和复核时间；
- 计算过程、SQL、Snapshot 和限制默认折叠到 Evidence。

删除复述标题、图表和 KPI 的长段落。技术术语只在 Evidence 层出现；主页面使用业务语言。

### 4.3 分析深度不足

AI Finding 不能只是把图表换一种说法。一个可展示 Finding 至少应完成以下工作中的两项，并说明不确定性：

- 比较 1d、7d、28d，识别短期变化、重复模式或结构性迹象；
- 在 Level、Centre、Circuit、Category、Day Type 或 hour-slot 中定位主要贡献者；
- 将 Actual 与可信 Baseline 对比并量化差异；
- 判断同一问题相对上一 Snapshot 是 New、Recurring、Resolved，还是在足够历史下呈现 Structural；
- 提出需要现场、排班、设备状态、天气或维护记录才能确认的原因假设；
- 给出调查顺序和可验证的下一步，而不是只给通用节能建议。

没有足够价值时允许显示 0、1 或 2 条。页面不再为了版式机械要求正好三条；原 #17 的 exactly-three 只保留为当时 Provider/tool-chain 验收证据，不再约束 #9 最终信息密度。

### 4.4 图表、数字和文字没有形成一个解释单元

每个决策主题应先选择最直观的表达，再补充短文字：

| 用户问题 | 优先表达 | 文字职责 |
| --- | --- | --- |
| 比上期高了多少 | 对比柱、斜率图或 variance bar | 解释影响和基线 |
| 何时开始变化 | 带基线/异常标记的趋势图 | 点出关键日期和持续性 |
| 哪个对象贡献最大 | 排名条形图或贡献堆叠图 | 解释集中度和调查顺序 |
| 哪些时段反复异常 | Heatmap 或 day profile 高亮 | 解释重复模式和运行语境 |
| 单个最重要数字 | KPI + delta | 不为单值强行画图 |

一张图只回答一个主要问题。文字解释“所以呢”和“下一步”，不复述坐标轴上已经可见的数字。

### 4.5 行动建议没有说明决策后果

每项行动至少包含：

- 建议做什么、针对哪个对象；
- 为什么先做这一步；
- **做了以后**预计观察到什么变化；
- **不做**可能继续承担什么暴露；
- 在什么时间、用哪个指标判断有效。

预计结果必须来自确定性 scenario、历史可比 Evidence 或明确列出的假设。没有依据时不得编造节省金额、百分比或 ROI，应改写为“预期方向 + 验证指标 + 观察周期”。

## 5. 两批数据连续演示

### 5.1 演示数据设计

从同一项目的真实数据中选择两个相邻、可复现的 cutoff：

- **Snapshot A**：截至较早完整日的数据；
- **Snapshot B**：在 A 的基础上追加后一批完整 interval facts；
- 两者使用相同 Workspace、Project、Scope、resource、Published Release、Mapping 和 timezone；
- B 只增加真实后续数据，不人工篡改 KPI 或 Finding；
- 优先选择 B 跨过一个真实有意义事件的 cutoff，使变化具有客户可见价值；具体日期由数据剖析后固定；
- 在隔离验收数据环境执行，不改写客户当前 Published Snapshot。

### 5.2 客户可见流程

~~~mermaid
flowchart LR
  A["导入第一批数据"] --> B["Snapshot A Overview"]
  B --> C["A 的 AI Finding 与 Evidence"]
  C --> D["追加第二批数据"]
  D --> E["Snapshot B 自动成为当前数据"]
  E --> F["确定性页面先更新"]
  F --> G["AI 显示 Analyzing"]
  G --> H["New / Recurring / Resolved / Structural"]
  H --> I["行动、做与不做的后果、验证方式"]
~~~

### 5.3 必须证明的差异

- Renderer/template revision 在 A、B 之间不变化，没有重新生成 HTML；
- 导入 B 后产生新的 Snapshot identity，A 的历史记录仍指向 A；
- 当前 Overview 的 KPI、图表、Data through 和 Data Status 使用 B；
- 确定性页面先显示，AI 异步显示 `Analyzing`，不会阻塞页面；
- AI 结果只引用 B 的 Evidence，不能混入 A 的数字；
- 同一问题跨批次合并为连续状态，不在多个 Horizon 或多个 Slot 中重复出现；
- 用户点击 Evidence 能看到 Scope、窗口、关键数字、查询结果、Snapshot 和限制；
- `Ask AI deeper` 从选中 Finding 和当前 B 上下文继续，不要求用户重新上传和解释全部数据；
- 另一名有相同授权的用户能看到相同确定性事实；跨用户共享 AI Artifact 不是本演示前置。

### 5.4 人工验收任务

Charles 应在不阅读技术说明的情况下，于 60 秒内回答：

1. 第二批数据进来后，最重要的变化是什么；
2. 为什么值得关注；
3. 系统认为的主要贡献者或原因假设是什么；
4. 建议先做什么；
5. 做与不做分别意味着什么；
6. 下一周期如何验证；
7. 这条结论依据的是哪批数据。

若他仍只能看到“新生成了一张内容很多的报告”，则本轮产品验收失败。

## 6. Preschool Appliance Ranking 边界

Product Owner 已确认 Preschool 是 Mock/Demo 数据集，并接受以下项目专属语义：

- 原始数据、Mapping 和 Evidence 的实体类型继续是 `Circuit`，不改写底层事实；
- 客户页面把这批数据的 `Power Meter / Circuit` 标签作为 Appliance 显示名；
- 原始工作簿/Profile 中的 `Appliance` 继续定义 Appliance Group；运行时 canonical facts 只保存规范化 category，因此服务端用已发布的精确别名合同校验 `Circuit label → Appliance Group/category`，不从字符串临时猜测；
- 当前发布 Mapping 中 30 个 Centre 均拥有同一组 9 个标签，且没有一个 Circuit 标签跨多个 Appliance Group，因此首版可以在本项目内比较；
- 该别名合同仅适用于 `preschool-demo`，不能推导成所有客户项目的通用 Circuit → Appliance 规则。

#12 因此交付一个服务端权威的 **Portfolio Appliance Ranking**：按 9 个已发布客户标签汇总当前 Snapshot 的 official component usage，返回总量、Portfolio share、Appliance Group、覆盖 Centre 数和 Evidence pins；React 只负责显示。事件级 `Leading Circuit` 在客户页面改称 `Leading appliance`，Evidence 仍保留原始 Circuit identity。

若后续真实项目的标签、映射或 taxonomy 不满足同样合同，模块必须显示 Unavailable 或使用该项目另行发布的别名 Mapping，不能按字符串猜测或在浏览器临时合并。

## 9. 明确停止项

- 不继续把 Overview 做成长篇 AI 摘要；
- 不为了版式机械生成三条 Finding；
- 不让 AI 生成或修改正式 Renderer/HTML；
- 不为两批演示建设通用 Scheduler、Cadence DSL、跨项目 Artifact 平台或历史 Snapshot 仓库；
- 不把 Preschool 项目专属的 Circuit-as-Appliance 别名推广成通用 taxonomy；
- 不把相关性写成已确认根因；
- 不编造节省金额、ROI 或行动效果；
- 不用更多底层平台工作替代 Charles 可见的连续价值演示。

## 10. 失效与复审条件

出现以下任一情况，重新评估本决定：

1. 两批数据仍不能稳定复现确定性数字或保持 Snapshot Evidence 一致；
2. 新数据进入仍需要人工重新生成或修改页面代码；
3. AI 只能复读图表，无法通过工具调查形成更深的可验证 Finding；
4. 用户不需要连续追踪、多人协作或 Evidence，只需要低频一次性报告；
5. Charles 无法在 60 秒内根据页面完成 5.4 的七项任务。

若第 4 条在真实客户中成立，应诚实收缩产品为轻量分析报告服务，而不是继续建设重型系统。
