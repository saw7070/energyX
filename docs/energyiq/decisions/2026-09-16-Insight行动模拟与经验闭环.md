# 产品目标与使用流程

> **最新确认：** 以下“AI 主导的小闭环与开发清单”覆盖旧版手填 Estimate 的产品设计。旧版实现和演示记录只说明历史状态，不代表本轮能力已经完成。

报告不止交付分析，还要帮助用户选择行动、验证效果，并让后续报告使用积累的经验。

**Report → Insight → Action → Simulation → 人执行 → 后续读数 → Feedback / Result report → 项目经验 → 下一轮报告与模拟。**

用户先读报告，在发现列表选择感兴趣的问题，再比较可选行动及预期效果。实施由人完成；用户记录时间、做法及偏差。系统等待可比较数据，生成反馈报告，回到对应发现和行动。报告与历史证据不可被新一期覆盖。

## 选择与边界

| 方案 | 结果 |
| --- | --- |
| 每份报告单独保存行动 | 同一问题反复出现，执行记录分散，不采用 |
| 项目维护 Insight，Insight 下维护多个 Action | 采用；报告保留每期发现的证据与引用 |

- Insight 是简短、持续维护的发现，不是整段报告；同一个 Insight 可以被多份报告支持。
- 一个 Insight 可以有多个 Action；应分清替代方案和可并行措施，不将重叠收益直接相加。
- Action 保存实施状态、执行记录、假设情景和反馈；不把“建议”当作“已执行”。
- 项目、workspace 和可见性沿用现有服务端权限；私人行动不得进入共享报告上下文。
- 同义去重由 Agent 提议，结合对象、现象和运行条件判断。确定性完全匹配可复用；相似但不确定的由用户明确关联。不能仅凭同一个电表就合并不同问题或不同措施。
- 不批量补提取旧报告。本次演示只选择明确的一份报告；新报告通过验证过的建议产物提供 Insight 信息。

## Simulation 与 mock 必须分开

**Simulation** 是行动前估算，例如可削减功率 × 减少小时 × 天数。保存假设、单位、适用条件、版本以及可选电价；不是实际效果。

**Mock demonstration** 是演示用的人为执行记录与执行后读数。单独保存，显著标为 Demo / simulated observations。不得写回原始电表、DuckDB、真实执行事件、实际节能统计或正式项目经验。模拟预期与 mock 观察值分别输入，允许两者不一致。

同一份 simulation 可面对实际观测或演示观测，但结果必须标识数据来源。演示反馈也走报告执行器，使用固定输入；不能写一份静态页面就声称整个 AI 闭环完成。

## 反馈与经验

- 最少需要可比较的完整天，执行当天排除；基线、观测窗口、计量范围分别冻结。现场占用、天气、其他同时发生的改变未控制时，只能说观察变化，不能直接归因。
- 反馈报告与 Action、Insight、来源报告关联。清单呈现最新结果与历史结果，保留所有版本。
- 数据库保存可追溯事实、计算结果、情景和来源；项目 experience Markdown 是这些记录的可读总结，不是另一份可任意覆盖的事实底座。
- 只在反馈报告成功后沉淀经验。真实经验进入后续项目报告；演示经验独立展示，不自动用于客户决策。
- 下一轮模拟可以参考经过验证的经验、调整假设，但不自动把一次观测当成可推广规律，也不自动改公共 Skill。需有适用条件和证据。
- 当前模拟先支持透明的功率/时长估算，不声称具备物理仿真、因果归因或通用预测模型。安全性、设备可关闭性和经济参数缺失时显示“需确认”。

## AI 主导的小闭环与开发清单（2026-09-16 最新确认）

### 产品决定

先自由生成英文 HTML 报告，再整理核心 Insight、证据与 Action。结构化产物用于维护项目清单，不约束报告版式。UI 默认突出一个主要 Action，数据模型保留一个 Insight 对应多个 Action；同一发现可关联多个报告，避免每期复制清单。

| 选项 | 决定与理由 |
| --- | --- |
| 用户填写功率、时长，由公式估算 | 不再作为默认入口；用户无法判断参数，难以体现产品价值 |
| AI 读取证据并提出方案，调用脚本计算 | 采用；用户只补充系统无法获知的现场信息 |
| 每次打开详情都重新生成 | 不采用；浪费资源且预测基准不稳定 |
| 首次生成、持久保存、明确更新 | 采用；可以复核执行时看到的预测 |

### 用户动线

1. 在 Insights & Actions 左侧看发现、右侧看建议，点击 Review action。
2. 首次进入详情，发起 AI 预评估；页面显示排队、分析中或失败重试。已有结果直接展示，刷新和重复进入不启动新任务。
3. AI 读取行动、来源报告证据、项目配置、对应历史数据及可见的执行记录。输出“建议怎么做、预计效果、依据、前提/待确认信息”。没有设备用途或可削减负荷依据时，不把全部夜间用电算成可节约量；调查类行动可以输出非量化评估。
4. 用户决定执行后，用自然语言说明实际做了什么。AI 解析执行日期、做法和影响范围；不要求填写设备 ID、功率等技术字段。保留原文和解析来源，只有关键歧义才追问。计划、假设和已经执行必须区分；模拟或单纯查看不能修改执行状态。
5. 记录执行后显示“正在观察效果”。数据每日更新后检查可比较读数是否充足，再自动生成反馈报告。3 天或 7 天只是可能的窗口，不是固定承诺；缺失数据不算零，执行日或部分执行日明确处理。
6. 结果归在 Action 下，并关联 Insight、来源报告、执行事件和当时预测版本。行动显示 New results，侧栏显示当前用户未读提示；阅读后消除该用户提示，不影响其他用户。
7. 暂不做预测模型自动校准或公共 Skill 自动演进。保留预测与实际对比需要的证据，为后续经验优化准备。观察变化不能自动等同于因果节能。

### 后台实现约束

- 复用当前 Pi 执行器、队列及 Action API，不另建业务平台。网页按钮和 Agent 工具调用同一服务端操作与权限检查。
- Estimate 属于 Action；Session/Run 是执行载体，不让用户选择。建议每个评估任务使用可追溯的后台会话，读取显式上下文，而非依赖原报告无限增长的聊天记录。执行记录与反馈也以 Action ID 关联。
- 首次生成使用服务端幂等控制；并发打开只产生一个活动任务。Update estimate 创建新版本；旧结果保持可读，更新失败不覆盖成功版本。变化的数据截止时间和配置版本可见。
- 保存建议、假设、计量范围、数据窗口/快照、计算方式、证据、模型与 Skill 版本、Run ID。AI 选择分析方法，工具执行数值计算；不能把无依据的模型数值包装成可靠模拟。
- 执行事件引用当时采用的 Estimate 版本；后续更新不追溯改写预测。解析不完整时保存待补充状态，不误启动观察任务。
- 就绪检查由数据更新事件或后台周期扫描驱动，可重试且不重复生成同一观察窗口的反馈。无数据、静态 CSV 和取数失败显示原因；不按经过的日历天数直接宣告结果就绪。
- 用户权限覆盖详情、上下文、后台会话、结果和通知。个人行动不进入项目公共上下文；通知按用户保存已读位置。

### 开发顺序与验收门

当前只确认方向并建立清单。下列未勾选项均不能视为已实现或已部署。

| 阶段 | 任务 | 依赖 | 验收条件 |
| --- | --- | --- | --- |
| A | 评估版本、执行说明和任务关联的存储/API；确认既有结构可复用部分 | 无 | 历史记录兼容，重复请求幂等，越权请求拒绝 |
| B | AI 预评估 Skill/prompt、数据工具、详情结果卡片及 Update 按钮 | A | Tuya 真实数据运行；无需填写技术参数；缺信息会问；重新打开不重复生成 |
| C | 自然语言执行反馈解析及必要追问 | A、B | “计划执行”和“已经执行”区分；日期不明不猜；保存原文和预测版本 |
| D | 数据就绪检查、反馈报告、行动和侧栏未读提示 | C | 不足时等待；补齐后自动触发一次；重试不重复；报告与行动双向可达 |

### 暂缓项与复审条件

本轮不接 SMS、不自动改公共 Skill、不实现通用物理仿真，不批量补提取旧报告。若需要天气/占用校正或现有工具无法支持某类行动，明确显示无法量化和缺少的依据，再评估扩展；不通过手工填一个节能数字掩盖能力缺口。
