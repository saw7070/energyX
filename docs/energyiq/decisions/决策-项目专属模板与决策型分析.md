# 项目专属模板与决策型分析

## 核心决定

模板采用四层：

1. **Component Catalog**：受控指标卡、比较、图表、异常和 Evidence；
2. **Template Preset**：Charles Preschool、Ngee Ann Level/Circuit 等参考组合；
3. **Project/Tier Template Revision**：项目正式发布的结构；
4. **Analysis Run**：固定范围、时间、数据和版本后的结果。

固定的是计算口径和页面 Schema，不是所有项目都显示相同层级和模块。

每个 Project 首期只有：

- 一个 Project Overview Template；
- 每个 Tier Definition 一个 Tier Template；
- 同 Tier 的节点共用模板；
- 不做 per-node override。

## 开源能力复用原则 {#open-source-capability-reuse}

自有 `EnergyIQ Template Schema` 不等于自研整套 Dashboard。决定采用三种复用方式：

1. **直接使用成熟前端能力**：图表、响应式布局、拖拽缩放等不自行重写；
2. **提取已验证的领域结构和交互模式**：转换成 EnergyIQ 受控字段，不复制外部平台内部对象；
3. **不引入重复运行时**：客户侧 Overview 不嵌入另一套账户、权限、语义层和 Dashboard 发布系统。

### Recharts 与 ECharts 分别是什么

两者都是**前端图表渲染库**，不负责数据接入、指标计算、模板发布、权限或复跑，因此不会替代 `EnergyIQ Template Schema`。

| 维度 | Recharts | Apache ECharts | EnergyIQ 选择 |
| --- | --- | --- | --- |
| 使用方式 | 用 React 组件组合 Line、Bar、Axis、Tooltip 等 | 用 `option`、`dataset`、`encode`、`visualMap` 等配置图表引擎 | 协议不暴露两者原生配置 |
| 擅长 | 普通 KPI、趋势、排名、构成、组合图；容易贴合现有 React UI | 高密度热力图、多维视觉映射、缩放、复杂交互和大量点 | 普通图继续 Recharts；复杂热力图局部接 ECharts |
| 当前仓库 | 已安装并在 Overview/Explorer 使用 | 未安装 | 不为假设需求提前引入第二个图表引擎 |

两者可以共存：Renderer 根据受控 `presentation.preset` 选择内部实现。模板只知道 `trend`、`ranking`、`day_hour_heatmap` 等 EnergyIQ 语义，不知道 `Recharts props` 或 `ECharts option`。当前只有 Recharts，一个 Renderer Registry 足够；只有真正加入 ECharts 这个第二实现时，才建立正式的 Adapter seam。

### 采用矩阵

| 来源 | 分类 | 提取或直接复用 | 在 EnergyIQ 中的落点 | 不照搬的部分 |
| --- | --- | --- | --- | --- |
| Recharts | **现在直接使用** | React 组合式基础图表 | 当前 KPI、趋势、排名、构成和简单比较 | 不把原生 props 写入持久化模板 |
| CopilotKit | **现在直接使用** | Chat、Streaming、前端 Tool、Generative UI、Human-in-the-loop | AI Analyst、Task Console，以及未来 Proposal 预览/确认 UI | 不把它当作指标、图表或 Dashboard 引擎 |
| Apache ECharts | **需求触发后局部使用** | Dataset/encode/visualMap、热力图、缩放与高密度交互 | 独立 `EnergyHeatmap` Renderer implementation；届时形成真实 Adapter seam | 不整体迁移现有 Recharts 模块，不保存原生 `option` |
| React Grid Layout | **Admin 需要拖拽时使用** | 响应式 12 列网格、拖拽、缩放、边界与序列化 | 模板布局编辑器，输出受控 `span/height/order` | 不开放自由像素、任意重叠和客户侧低代码编辑 |
| Superset | **不引入运行时，只吸收结构** | Dataset/Metric/Chart/Dashboard 分层、认证指标、Native Filter、网格和 Chart Preset | Metric Registry、Component Catalog、Template Section、全局 Filter、受控 Layout | Superset 服务、iframe、独立登录/RBAC、第二套 Dataset/Dashboard 真相源 |
| Rill | **不引入运行时，只吸收结构** | Metrics View 的 measure/dimension/time dimension、默认时间范围和 time/dimension comparison | Metric Definition、Time Grain、Comparison Spec 和项目 Preset | 客户维护 YAML、Rill runtime 和另一条部署链 |
| Metabase | **不引入运行时，只吸收结构** | Dashboard/Section/Card 筛选、点击下钻产生派生查询且不覆盖原问题 | Filter Scope、Drill Action、`Explore with these settings` | 通用 Query Builder、Embedding 和不受控查询改写进入 Boss 页面 |

“暂不使用”不等于永久否决。出现真实需求时按表中触发条件接入；在触发前只保留协议位置，避免维护两个图表引擎或两个 Dashboard 系统。

### EnergyIQ Template Schema 的稳定结构

目标协议只保存 EnergyIQ 的稳定语义：

~~~text
Template Revision
├── Section：页面章节和左侧导航
├── Placement：组件顺序、12 列 span、受控高度
├── Component Revision：数据要求、允许的图表 preset 和交互
├── Query Policy：允许的 resource、period、grain、comparison 和 filter
└── Interaction：下钻 Explorer、打开 Evidence、带上下文进入 AI
~~~

运行时另行组合，不写死在模板里：

~~~text
Template Revision
+ Component Catalog
+ Energy Query Context
+ Metric/Rule Result
+ Data Quality
= Render Plan → Renderer Adapter → 页面
~~~

`Render Plan` 是一次请求的临时结果，不是新的真相源。持久化协议不得暴露任意 CSS、React props、ECharts option、SQL 或 JavaScript。当前由共享 Renderer 内的受控 `view_key` dispatch 消化；以后组件数量继续增长时深化为 Renderer Registry，真的存在 Recharts/ECharts 两种实现时再建立 Adapter seam。Template Revision 不随图表实现变化而失效。

首期只开放有限视觉配置：章节名、模块开关和顺序、整行/半行/三分之一宽度、受控高度、允许的图表 preset、标题、图例、Top N 与信息密度。计算公式、Scope、规则和 Evidence 与视觉配置分离。

目标结构示意：

~~~json
{
  "schema_version": 2,
  "templates": [{
    "template_id": "project",
    "target_kind": "project",
    "sections": [{
      "section_id": "energy-overview",
      "title": "Energy overview",
      "navigation_label": "Overview"
    }],
    "components": [{
      "placement_id": "overview.consumption",
      "component_revision_id": "overview.consumption@1",
      "enabled": true,
      "section_id": "energy-overview",
      "layout": { "span": 12, "height": "compact" },
      "presentation": {
        "visual_preset": "cards",
        "density": "comfortable",
        "tone": "default",
        "show_legend": true,
        "limit": 10
      }
    }]
  }]
}
~~~

每个 Component Revision 已声明自己的 `allowed_presentation`、所需 Metric/Rule/Query 和适用 target；Interaction 仍是下一阶段。Admin 与未来 Agent 必须共用这组服务端限制。

### Agent 能做“新模块”的准确含义

Agent 可以创建的是**模块实例和模板组合**，不是未经审查的 React 代码：

- 可以从 Catalog 选择 KPI、趋势、排名、构成、热力图、四象限、异常、建议和 Evidence；
- 可以在组件允许范围内选择 metric、dimension、preset、顺序、宽高、标题、Top N 和交互；
- 可以组合出一个项目此前没有使用过的模块实例；
- 不能发明新的计算公式、任意 SQL、任意图表配置或新的 Renderer。

例如，Agent 可以把 `time.heatmap@1` 配置为 `Date × Hour + usage_kwh`。如果 Catalog 尚无该 Component/Renderer，它只能返回 `unsupported_component` 并提出开发需求，不能临时生成代码混入生产页面。

### Catalog、Schema、Template 与 Render Plan 的关系

四者职责不同：

| 对象 | 人话理解 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| Component Catalog | 可用积木仓库 | 定义有哪些模块、输入槽位、适用范围、允许配置、数据要求和 Renderer key | 不决定某个 Project 实际摆哪些模块 |
| EnergyIQ Template Schema | 拼装语法和安全规则 | 定义 Section、Placement、Binding、Layout、Presentation、Interaction 的合法结构 | 不包含某个模块的 React 实现，也不包含实际数据 |
| Template Revision | 按语法拼好的正式方案 | 为一个 Project/Tier 选择 Catalog Revision、绑定分析参数并排列页面 | 不保存查询结果，不随用户时间筛选变化 |
| Render Plan | 本次请求的施工单 | 将 Template、Catalog、Query Context、分析结果和 Data Quality 解析成可渲染模块 | 不持久化为新的模板或数据真相源 |

~~~mermaid
flowchart LR
    C["Component Catalog: available building blocks"] --> T["Template Revision"]
    S["Template Schema: composition rules"] --> T
    M["Metric / Rule Registry"] --> T
    T --> P["Render Plan Compiler"]
    Q["Project capabilities + Query Context + results"] --> P
    P --> R["Renderer Registry"]
~~~

Catalog 是 EnergyIQ 自己维护的权威注册表。它可以在内部使用 Recharts/ECharts 等开源实现，但 `component_id`、输入契约、版本、业务语义和允许能力由我们控制。只有 developer/admin 的受控发布流程可以注册新的 Component Revision；Agent 只能引用已经发布的 Catalog Revision。

Schema 只检查“句子结构是否合法”，Catalog 再检查“这个词是否存在以及能怎么用”。例如 Schema 允许 Placement 包含 `presentation.preset`，但具体 `quadrant` 是否允许、需要几个 Metric、接受什么单位，由所引用的 Catalog Revision 决定。最后还要用 Project capabilities 检查面积、人数、历史覆盖和可比较子 Scope 是否真实存在。

### 让 Agent 有想象力，而不是把 Catalog 写死

Catalog 应包含两类模块：

1. **固定决策模块**：Executive Action、Data Status、Exceptions & Evidence、Recommended Actions。其事实强度和证据结构必须固定；
2. **通用分析模块**：KPI、Time Series、Ranked Bar、Stacked Composition、Heatmap、Scatter/Quadrant、Distribution、Table。它们通过受控输入槽位产生大量组合。

通用模块不把 Metric 写死，而是声明允许绑定的槽位：

~~~json
{
  "component_revision_id": "comparison.quadrant@1",
  "input_slots": {
    "x_metric": { "kind": "metric", "allowed_units": ["kWh/person"] },
    "y_metric": { "kind": "metric", "allowed_units": ["kWh/m2"] },
    "dimension": { "kind": "dimension", "allowed": ["child_scope"] }
  },
  "allowed_presentation": {
    "preset": ["quadrant"],
    "show_labels": "boolean"
  }
}
~~~

Template Placement 再把它绑定成该项目的具体分析：

~~~json
{
  "component_revision_id": "comparison.quadrant@1",
  "analysis": {
    "x_metric_id": "energy.usage_per_person@1",
    "y_metric_id": "energy.usage_per_sqm@1",
    "dimension": "child_scope",
    "comparison": "selected_period"
  },
  "presentation": { "preset": "quadrant", "show_labels": true }
}
~~~

为此增加受控 `Analysis Spec`：只允许引用已发布 Metric/Rule，并使用白名单算子描述 `group_by`、time grain、comparison、normalisation、ranking、share 和 operating/off-hours slice。它由确定性查询模块编译执行，不允许任意 SQL。图表数字由计算模块产生，Agent 负责提出问题、选择组合和解释结果。

Agent 的创造力分三层：

| 层级 | Agent 能做什么 | 是否需要开发新代码 |
| --- | --- | --- |
| L1 模板编排 | 选择、排序、布局、标题和已允许 preset | 否 |
| L2 分析组合 | 将通用模块绑定到合法 Metric、Dimension、Grain、Comparison 和 Filter | 否；需要先实现 Analysis Spec Compiler |
| L3 新能力发明 | 新图形语法、新算法、新 Metric 或新 Renderer | 是；Agent 只能形成开发建议，不能进入 Published Template |

这样 Catalog 仍然可控，但几十个 Metric、多个 Dimension、时间粒度、比较方法和约 8 类通用模块可以形成大量有效组合，不需要为每张图手写一个 Component。

## 为什么这样不与“项目专属”冲突

Project 专属决定哪些 Tier、指标、规则、组件和参数可用；Tier Template 解决不同粒度不应使用同一页面的问题。Room、Floor、Block 不靠名称分配模板，而是按该 Project 的 Tier Definition 分配。

管理员无需为每个节点重复编辑，同一 Tier 的全部节点共用结构，但数据和 Evidence 根据 scope_id 运行。

## AI Analyst 如何打通

AI Analyst 分成两条能力链，不能混为一谈。

### A. 可信问数链：已经部分接通

~~~mermaid
flowchart LR
    O["Overview / Explorer"] --> R["project + scope + period request"]
    R --> C["Server resolves authoritative Energy Query Context"]
    C --> D["Workspace-scoped DuckDB view"]
    D --> A["DataFoundry AI Analyst"]
    A --> E["Answer + chart + Evidence + Trace"]
~~~

浏览器只提交 Project、Scope、Resource 和 Period 请求。服务端重新校验 Workspace/Membership，并固定 Hierarchy Revision、Meter Formula Revision、Data Snapshot、Metric、Calendar 和 Tariff 版本；Agent 只能查询该上下文生成的受限数据源。浏览器传入的名称和 workspace_id 不能成为授权依据。

### B. 模板修改链：目标设计，尚未实现

~~~mermaid
flowchart LR
    U["Admin asks AI to change template"] --> G["Read published revision + catalog + project capabilities"]
    G --> P["Structured Template Change Proposal"]
    P --> V["Schema + permission + reference + readiness validation"]
    V --> D["Diff and fixed-snapshot preview"]
    D --> H{"Admin approves?"}
    H -- No --> P
    H -- Yes --> N["New immutable Template Revision"]
    N --> O["Overview uses the same Renderer"]
~~~

建议给 Agent 暴露三个窄 Tool：

1. `get_energy_template_context`：读取当前 Published Revision、Component Catalog、项目可用指标/规则/元数据和模块 readiness；
2. `propose_energy_template_change`：只返回带 `base_template_revision_id` 的结构化 Patch；
3. `preview_energy_template_change`：在固定 Data Snapshot 上运行校验和同一 Renderer Preview。

不把 `publish` 作为 Agent 自主 Tool。CopilotKit 的 Human-in-the-loop 负责展示 Diff、缺失数据和 Preview，并收集管理员确认；真正发布仍由服务端 endpoint 校验 admin 权限、base revision、并发冲突和所有引用，然后生成不可变 Revision。CopilotKit 是交互层，不是安全边界。

Proposal 首期只允许以下操作：

- `add_placement`、`remove_placement`、`move_placement`；
- `set_section`；
- `update_layout`；
- `update_presentation`；
- `set_interaction`。

校验至少包括：Schema 版本、Component target、Metric/Rule/Query 引用、项目 metadata/readiness、允许的 visual preset、数据质量、操作者权限和 `base_template_revision_id` 是否仍为最新。失败返回结构化原因，不进行半发布。

user/FM/Boss 当前只能问数和改变 Interactive Analysis 的临时视图；不能发布模板。未来若开放客户建议，可以先保存为个人临时视图或提交 Proposal 给 admin，仍不直接修改 Workspace Published Template。

### 当前实现与下一步

当前已经存在：

- `EnergyIqComponentRevisionRecord`、Project/Tier Template Draft 和不可变 Template Revision 存储；
- `EnergyIQ Template Schema v2` 已进入持久化契约：Template 包含有序 Section，Placement 包含稳定 `placement_id`、`section_id`、12 列 `span`、受控高度及 Presentation；
- Admin Draft Preview 与客户 Overview 已统一使用 `buildEnergyTemplateRenderPlan → EnergyTemplateRenderer`；
- Admin 可配置模块 Section、宽度、高度、受支持的 visual preset、密度、tone、显示标题、Top N 和图例；
- 客户 Overview 通过 customer-authorised `GET /api/v1/energy/projects/:id/published-template` 获取发布模板和 Catalog，并与确定性 Scope Analysis 组合；
- 旧版 Placement-only Draft 会在读取/保存时补齐 v2 默认值；尚无 Template Revision 的历史 Published Project 使用明确标记的 `compatibility-default`，不会读取可变 Admin Draft；
- AI Analyst 复用 `DataTasksApp`，并由服务端解析可信 `Energy Query Context`、创建受 Scope 限制的数据源；
- Recharts 与 CopilotKit 已安装。

当前尚未完成：

- 当前本地 Ngee Ann 与 Preschool 是早于 Template Revision 发布闭环的历史 Published Project，数据库中还没有正式 Template Revision；需经 Admin Review & Publish 重新发布后，客户页才从 `compatibility-default` 切到固定 Revision；
- Renderer 仍用 `view_key` switch，已形成 Render Plan Compiler，但尚未把 switch 深化为独立 Renderer Registry；
- Catalog 已把每个组件的 `allowed_presentation` 持久化为服务端能力表，Admin 选项和存储层校验均以它为准；受控输入槽位与 Interaction 仍未加入；
- Section 名称/顺序当前来自受控默认协议，尚未提供完整 Section 编辑器；
- Charles/Ngee Ann 的 Heatmap、Quadrant、Distribution、Recommended Actions 等通用模块仍需分批进入 Catalog；
- 尚无 Template Change Proposal 的 Tool、Diff、Preview 审批和发布链；
- ECharts 与 React Grid Layout 尚未安装。

因此后续开发顺序为：

1. 用 Admin Review & Publish 为 Ngee Ann 生成正式 Template Revision，并完成客户 Overview 的固定 Revision 验收；
2. 按已确认 Ngee Ann Preset 将 Heatmap、Recommended Actions 等缺口拆入 Component Catalog；
3. 在现有 `allowed_presentation` 基础上补输入槽位和 Interaction；组件实现真正出现第二种图表引擎或明显增长时，再形成 Renderer Registry；
4. 建立 Analysis Run、Query Receipt、Rerun 和历史结果；
5. 再把三个模板 Proposal Tool 接给 AI Analyst；
6. 真实出现复杂热力图或拖拽布局需求时，分别局部接入 ECharts 或 React Grid Layout。

## 决策型输出

图表用于佐证决策，不是装饰。每条优先建议必须包含：

1. Fact；
2. Baseline；
3. Impact；
4. Possible Cause，明确是待确认假设；
5. Recommended Action；
6. Evidence，包括范围、时间、指标、查询、批次、版本和质量。

不能仅凭电表说“灯没关”。可以说某 Scope 的 light 在配置的非营业时段持续高于自身历史，并建议 FM 核查。

## Project Overview 推荐模块

吸收 Charles 的分析意图，但按项目数据条件启用：

| 模块 | 回答的问题 | 条件 |
| --- | --- | --- |
| Executive Action Summary | 先处理什么 | 有可信 Fact/Rule |
| Consumption Overview | 用了多少、何时最高 | 有 Interval Fact |
| Benchmarks | 相对自身/同级表现 | 有历史或可比节点 |
| Standby / Off-hours | 非营业时段浪费多少 | 有 Calendar |
| Operating Pattern | 工作日、周末、小时模式 | 有完整时间覆盖 |
| Exceptions & Evidence | 哪些异常需要核查 | 规则与质量达到门槛 |
| Forecast Preview | 下一周期可能怎样 | 历史和回测不足时仅 Preview |

费用只在 Tariff 确认时显示。Carbon 仅预留。

## Tier Template 推荐模块

- 当前 Scope 摘要与数据质量；
- 直接子 Tier 排名；
- 当前 Scope 自身历史；
- load / aircon / light / other 构成；
- 时间趋势与小时热区；
- 直接挂载总表、分表和虚拟表；
- 异常、建议与 Evidence；
- Investigate with AI。

若当前 Tier 下没有更低层，展示 Meter/Circuit 组成；若存在两个以上可比较 Tier，可生成 Tier × Tier 或 Tier × Time 切片。

## 比较基线

优先级：

1. 同 Scope 自身历史同类时段；
2. 已配置目标或规则；
3. 元数据可靠时的 kWh/m² 或 kWh/person 同级比较；
4. 同级绝对量只做描述。

四象限可用 X = kWh/person、Y = kWh/m²。Bell curve、分位数和热力图不是所有 Tier 必备，必须有足够样本和可比性。

## 数据条件与降级

| 缺口 | 行为 |
| --- | --- |
| 无面积 | 隐藏 EUI，不以 0 代替 |
| 无人数 | 隐藏 per-person |
| 无 Tariff | 隐藏费用 |
| 无营业时间 | 不宣称 standby/off-hours |
| 历史不足 | 不发布自身历史异常或 Forecast |
| 同级样本少 | 不发布分布结论 |
| 数据部分缺失 | 标明覆盖率，降低结论或隐藏 |

## 复跑与变更

- Template Revision、Metric/Rule、Hierarchy、Formula、Calendar、Tariff 与 Data Snapshot 都进入 Run；
- 相同输入得到相同结果；
- 新数据创建新 Run；
- 模板变化产生新 Revision；
- 历史 Run 不被新模板重算覆盖。

Forecast 正式上线至少需要约 3 个月完整历史和回测，最好 6–12 个月。当前样板中的 mock/provisional 数据必须显式标注。
