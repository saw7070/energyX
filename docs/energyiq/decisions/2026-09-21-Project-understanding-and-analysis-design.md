# 以项目理解与分析成果为核心的报告及行动设计

## 1. 状态、目的与用户纠正

本文记录侧会话确认的产品方向，并提出可实施的技术设计。方向已由用户认可；字段、状态机、工具名称和实施顺序是建议，主 Agent 应结合最新代码落实。本文不声称相关能力已经实现、合并或部署。

**重要纠正：用户认同的是“展示和管理的数量限制不能限制分析成果”，不是重新确认固定的六个行动槽位、首页三条。**已有六/三配置可作为迁移期兼容策略，但不是知识模型的容量，也不是必须产出的数量。首页目标简洁、有价值，确切数量可调整；不足时不编造发现补位。

目标：持续理解项目，保存可信认识，并转化为用户能理解、有价值的报告和行动。用户不需要理解材料库、版本或 Harness；他应看到明确的问题、证据、能做什么、预计价值，以及后续效果。

## 2. 为什么选择这一结构

| 方案 | 优点 | 主要问题 |
|---|---|---|
| Report 为核心 | 完整叙事、灵活 HTML、容易交付 | 知识埋在报告里，跨期复用和行动追踪困难 |
| Insight & Action 为核心 | 易管理行动、去重和首页展示 | 报告容易退化成少数建议的扩写；无直接行动的分析被遗漏 |
| 验证过的分析成果为知识核心 | 保留分析广度，支持多种交付物 | 需要管理证据、时效和更新，避免无序资料堆积 |

选择第三种，同时保留各自职责：**项目理解与分析成果是知识核心，Action 是执行核心，Report 是不可变的交付版本。**“第一公民”不意味着全部业务状态塞进一个文件或表。

不是先写完整 HTML 再反向解析全部知识，也不是只允许选中的行动进入报告。Agent 先探索、计算和形成有证据的分析，再编写完整报告；写作需要补证据时可以返回分析阶段，补充并重验材料。

## 3. 总流程

```text
发布的项目配置 + 可用数据快照 + 用户反馈 + 当前有效认识
                         ↓
                 构建本次分析上下文
                         ↓
          探索与计算 → 分析材料草稿 → 证据检查
                         ↓
                已验证的分析成果版本
                   /              \
         完整报告编写              发现与行动对比更新
         + 视觉呈现                 + 用户状态保护
                   \              /
                  一致性检查与发布版本
                         ↓
          Report / Insight & Action / Key Points
                         ↓
             用户确认、执行记录、新读数
                         ↓
           效果分析 → 更新认识与后续建议
```

报告与清单同源，但互不穷尽。Key Points 是当前有效、对用户有价值的发现/行动/进展的精选视图；从已协调的项目清单选择，而不是只从本次新发现选择。报告可以包含未进入行动清单的有用分析。

分析范围默认允许使用全部可用历史；每个比较、发现和估算仍必须明确自己的证据时间窗。全部数据不等于所有指标跨全历史平均。周报/月报的汇报期与分析可访问范围分开：前者决定讲什么时期的变化，后者支持历史基线与探索。

## 4. 项目资料分四类维护

### 4.1 项目事实：项目是什么

设备/回路名称、空间和计量拓扑、正式聚合口径、营业时间、电价、学校校历、设备必要运行条件，以及用户确认的信息。

- 继续使用现有 Project Configuration 及其发布机制，不能复制一份独立配置成为第二真源。
- 使用稳定 meter_point_id/scope_id 关联，显示名由统一配置解析；资料中的原始别名保留为来源，不作关联键。
- 每条可变事实标记来源、确认方式、生效时间与配置版本。AI 推断的用途不能自动成为已确认事实。
- 用户纠正通过现有配置工具形成更新；对历史报告仍使用当时的配置版本。

### 4.2 分析证据：本次怎么算出来

每次分析形成可复查的 Analysis Package（工作名，需映射现有 Analysis/Run/Artifact，不要求新建同义平台对象）：

| 内容 | 最小要求 |
|---|---|
| manifest | schema_version、运行/项目身份、数据与配置版本、模型及实际 Skill 版本 |
| scope | 可用历史范围、汇报期、实际计算的各时间窗、时区 |
| evidence | 指标、单位、样本量、覆盖情况、图表数据、来源与计算产物引用 |
| analysis brief | 面向 Agent/人的完整可读分析，包括背景、变化、对比、解释、未知与限制 |
| findings | 带 evidence_id 的发现记录；观察、解释假设、待确认问题分开 |
| candidates | 候选行动及条件估算；可以没有行动 |

数值用结构化数据，解释用 Markdown，脚本与图表数据以文件/Artifact 引用保存。原始大量读数仍在数据底座，不拷贝进长期记忆。

建议逻辑结构，不限定实际磁盘布局：

```text
analysis package
  manifest.json
  analysis-brief.md
  findings.json
  evidence/（指标、图表数据、可复算脚本与来源引用）
```

草稿可修订；验证通过的版本不可原地覆盖。重新分析建立新版本并记录替代关系。

### 4.3 当前认识：现在认为项目是什么状态

这是可更新的项目记忆，而非全部历史聊天摘要。每条认识包含：稳定 ID、对象、问题类型、简短主张、证据引用、适用时间、确定程度、状态、首次/最近支持时间、复核触发条件，以及替代关系。

建议确定程度：observed（数据观察）、hypothesis（解释待确认）、confirmed（有明确确认来源）。建议状态：active、needs_review、superseded、archived。这两组含义独立，不能把“当前有效”误当“因果已确认”。

示例：

```json
{
  "finding_id": "finding-001",
  "revision": 2,
  "subject_ids": ["meter-point-example"],
  "claim": "周末晚间持续出现照明负荷",
  "certainty": "observed",
  "explanation": "用途尚未确认，不能认定为浪费",
  "evidence_refs": ["analysis-run-example/evidence-01"],
  "status": "active",
  "review_trigger": "新的周期分析或运行安排变更"
}
```

示例不是生产记录，实际契约还须有 workspace/project、证据时间窗、来源版本及审计字段。用户确认“周末有保洁”后，记录事实并更新解释；保留原始观察，不继续重复询问已回答的问题。

### 4.4 行动与经验：做了什么、结果如何

沿用现有 Action、执行反馈、模拟及结果记录。区分：建议值得做、用户计划做、已执行、等待读数、观察到变化、已验证效果。这些不能互相替代。

- 当前产品继续按一个可执行 Insight 对应一个主要 Action 展示；全面分析中的普通发现无需强制生成 Action。
- 一个 Action 可关联多个 meter_point_id；父子总分表不能简单相加。
- 同一设备不同措施是不同 Action；同一措施不同措辞可以合并。设备集合本身不是去重键。
- 多份报告可引用同一条 Insight/Action；引用保留报告版本、证据与当时描述。
- 用户执行状态只能通过授权操作更新，模型不能因报告重跑重置状态。
- 经验保存“什么措施、适用条件、观察结果、证据与限制”；不是每次自动把结果写进 Skill。

## 5. 去重、更新、时效与记忆读取

### 更新已有认识

每次新材料与当前认识比较，形成 proposed changes：新增、补充证据、修改解释、标记待复核、替代、归档。服务端验证后提交。

候选匹配先按同项目权限范围、对象集合、问题类型、时间条件筛选，再由 Agent 比较语义；不同动作的机制/目标/运行条件不能仅因名称类似而合并。拿不准先标记待复核，不能破坏性合并用户的执行记录。

未在本期报告中选中，不代表问题已解决。低优先级可退出推荐位但仍可查询。已执行行动退出“待做建议”后仍在效果跟踪中；实际效果经验证后形成结果和经验，再归档处理完成的问题。

### 复核规则

| 对象 | 默认触发 |
|---|---|
| 名称、设备归属 | 配置/资料/用户确认变化 |
| 运行规律与未解决发现 | 下次周期分析、新数据覆盖相关窗口 |
| 收益估算 | 电价、运行条件、设备范围或重要数据变化 |
| 已执行行动 | 达到该行动定义的观察窗口和数据完整性条件 |
| 已解决问题 | 后续监测发现复发，建立新事件并关联历史 |

不统一硬编码“三天有效”或“七天就有结论”。执行后的比较要考虑同类工作日、学校阶段、天气等相关条件；样本不够时显示等待/无法可靠判断，而非自动宣称节省。

### 控制记忆规模

每次装配：必要配置 + 当前相关认识 + 未完成行动/反馈 + 相关历史证据引用 + 数据访问工具。长期证据按需读取，不把全部文件直接塞入 prompt。

事实/证据有来源和版本，摘要可重建。旧证据归档，仍被已发布报告引用的证据按保留策略保存；不能为节省存储破坏溯源。只有明确的用户反馈或验证结果能改变相应事实与效果状态。

## 6. 五项 Skill 职责与 Harness

| Skill 职责 | 输入 | 输出 | 边界 |
|---|---|---|---|
| 全面项目分析 | 数据、配置、历史认识及反馈 | 分析材料与证据 | 既看可行动问题，也保留有价值的背景/对比 |
| Insight & Action 管理 | 验证材料、现有清单 | 带理由的清单变更提案 | 不覆盖执行事实，不因槽位限制分析 |
| Key Points 筛选 | 当前清单、效果进展、用户关注点 | 排序及精选引用 | 数量是展示策略；初期可并入管理 Skill |
| 报告编写 | 完整材料、相关行动/结果、汇报目标 | 报告叙事和图表选择 | 不是只扩写首页选中的建议 |
| 视觉呈现 | 报告内容、项目风格版本 | HTML 与可视化 | 视觉自由，数值及主张可溯源 |

以上是逻辑职责，不强制五次模型调用、五个 Agent 或五套会话。可在现有 Run 中分阶段执行并记录阶段产物。复用已存在的分析、呈现、审阅、Skill Creator 能力，先检查最新 Skill 再改，不重复创建近义 Skill。

Harness 负责身份/权限、上下文装配、工具能力、产物与状态契约、校验、幂等/恢复、发布和版本追溯。Skill 负责分析与表达方法；Skill 不能代替服务端权限或状态校验。

工具建议按现有能力扩展：读项目上下文、查询证据、提交分析材料、提出认识变更、提交授权变更、记录执行反馈、请求效果分析。人点击和 Agent 工具调用走同一业务服务，服务端解析用户身份，项目私有/公共范围保持隔离。

### Skill evolve

设备用途等具体事实进配置；拒绝原因和执行结果进行动记录；经多次验证有效的分析方法才形成 Skill 候选新版本。保留版本、变更理由和验收案例，离线/隔离对比后推广，任务固定实际加载的版本。一次用户评价或一次模型自评不自动修改公共 Skill。

## 7. 发布、一致性与失败恢复

1. Run 开始固定数据截止、配置版本、当前清单 revision、Skill 版本。
2. 保存并验证材料，模型输出的引用、数字和范围必须可核验。
3. 形成清单变更提案；对比运行期间的新用户反馈和 revision 冲突，重新协调，避免覆盖。
4. Report 引用完整材料与选择后的行动版本；Key Points 引用协调后的当前清单。
5. 发布同一 edition 的报告/推荐选择及其引用关系；用现有事务或可恢复的发布状态实现，避免半成品成为当前首页。

分析知识可独立验证保存；报告失败不抹掉已验证证据，但客户发布版保持上一成功版本。用户记录的行动反馈独立即时保存，不被报告发布失败回滚。

以 run_id + 操作标识实现幂等。重试只补失败阶段，若输入变化需新修订；不重复新增 Action，不重复发送结果通知。当前首页可根据后续执行状态失效或降级相应卡片，历史报告内容保持不变。

## 8. 客户呈现及质量门槛

- Key Points：问题一句话、设备有意义的名称、能做什么、条件收益或安全价值；详情再展示证据和限制。
- Insight & Action：清楚展示依据、下一步、预期效果、执行反馈及结果。
- Report：结论前置，同时按项目需要展开总量、结构、趋势、时段、同类日/学校假期比较、异常、行动与效果。不是每次填满固定章节；有分析价值就展开。
- 钱由 Agent 定义场景和假设、脚本计算并验证；年化是条件估算，有对应范围、时段、电价和不确定性，不作为已实现节省。
- 安全只能依据可观测证据提出风险或排查建议；持续用电不能推断漏电，没有安全发现就如实说明监测边界。
- 正常分析可以得出“暂无值得执行的新建议”，报告仍可解释运行变化；不为凑推荐数量制造内容。

## 9. 初期范围与后续边界

第一版建立可验证材料包、当前认识更新、现有报告/行动/首页同源消费及最小反馈复用。现有 UI 保持稳定，只做必要的来源和状态呈现。

暂不建设通用知识图谱、向量数据库平台、任意自主 Skill 改写、自动设备控制或全新多 Agent 编排。只有检索规模/准确性证明现有方式不足时，再评估检索基础设施。

代价是材料存储、校验和阶段恢复更复杂。若材料整理导致延迟大幅增加却未改善报告广度、建议价值或反馈复用，应缩减契约和模型阶段，而非持续增加中间文档。

## 10. 验收原则

同一数据与版本的数值在报告、清单、首页一致；完整报告有被证据支持的广度；用户回答可复用；旧反馈不被重跑覆盖；不存在行动也可完成有价值的分析；所有已发布结论可追溯到证据。自动测试、真实模型、网页验收、生产运行和客户认可分别记录，不能互相替代。

详细任务与验收清单见关联 handoff。本文是结构设计的主文档，handoff 只维护开发次序与执行证据。
