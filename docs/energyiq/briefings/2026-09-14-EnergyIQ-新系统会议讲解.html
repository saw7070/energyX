01 / 产品重心

把一次好报告，
变成可以持续复用
的工作方式。

让 Charles 在网站里与 AI 一起完成第一份报告；系统保存项目资料与分析方法，之后结合持续更新的数据，生成新的英文 HTML 报告。

DATA数据持续进来自动取数，统一项目数据
CONVERSATION对话做出好报告探索、计算、预览、修改
SKILL保存有效方法把经验变成可复用的指引
AUTOMATION新数据产生新价值周期复跑，跟进问题与行动

我们交付的核心不是一张固定看板。它是一个接入项目数据的云端 Agent 工作台：用户提出问题，Agent 用文件和代码完成分析，报告成为可保存、可阅读、可持续改进的成果。

本次会议的目标：讲清楚这个工作方式，演示已验证的链路，并请 Charles 判断报告的价值与使用体验。传统 BI、更多工具市场和大规模平台扩展暂时不作为本次重点。
可以这样开场：“过去我们更多在复刻一份报表。现在，我把产品重心调整成让您在系统里做出满意的报告，再把这套工作方法保存下来，交给系统持续执行。”

说明范围：截至 2026 年 9 月 14 日 13:20（新加坡时间）的代码、生产运行记录与网页验收。页面中的耗时、并发数是本次实测或当前配置，不是服务承诺。

02 / 业务闭环

第一次有人协作，
之后让经验和新数据一起工作。

01准备项目

接入数据与资料，建立电表、空间、营业时间等配置。

02完成第一份报告

Charles 对话提出需求，查看 HTML，继续反馈与修改。

03保存报告方法

Skill Creator 提取有效步骤，审看后绑定为项目默认方法。

04按周期生成新报告

读取新数据与已选 Skill，重新分析、审阅、保存到 Reports。

短周期反馈：本期的新发现、旧问题与行动进展进入下一期分析，报告持续回答“什么变了、为什么值得关注、下一步做什么”。
长期方法反馈：经过验证的改进进入 Skill 候选版本 → 复跑比较 → 再启用。每期的新现象不直接改写公共方法。
分工负责什么为什么这样分
Charles / 管理员提供项目真实信息、提出目标，判断报告是否有用；补充 AI 无法确认的事实。使用价值、现场原因和业务决策仍需要人的判断。
我们的系统项目权限、数据同步、配置版本、任务执行、文件保存、报告展示与周期调度。这些事情要持续、稳定、有记录，不依赖某次聊天记忆。
系统内的 Agent阅读资料，使用脚本探索数据，提出分析，生成与修改 HTML，提取 Skill。让模型发挥分析与制作能力，不把它限制成模板文案填充器。
强调两个闭环：一个是报告按周期持续产生；另一个是人的有效经验逐步变成 Skill。新项目自动匹配成熟方法是演进方向，现在仍需要真实项目验证与人的反馈。
03 / 数据底座的自动化更新

用户不必反复传基础 CSV。
Explorer 和 Agent 使用同一份项目数据。

遇到的问题

数据分散，边界不清。

Explorer 查询数据库，报告又依赖手动上传 CSV，两边可能截止日期不同；累计电表读数采样不规则，午夜附近缺少后续读数时，昨日能耗也容易不完整。

我做了什么 · 为什么

统一数据来源，修复取数与计算边界。

保留原始记录，统一生成分析事实与数据快照；涂鸦改为每天 02:00 自动取数并重叠回拉。报告所需 CSV 由同一快照自动导出，不让用户维护两套基础数据。

SOURCEAPI / CSV / Excel

通过已支持的适配器接入，保留原始记录与导入批次。

PROCESS标准化与质量处理

识别时间、电表、单位，处理累计读数并标记异常或缺口。

FACTSSnapshot + DuckDB

把读数、项目映射和版本对应起来，统一查询与聚合。

CONSUME同源两种使用方式

页面查询趋势；Agent 获得授权范围内的分析文件。

Project Explorer

网页 → 受权限控制的后端 API → DuckDB 查询 → 指标 / 曲线 / 热力图。

AI 报告

项目 + 时间范围 → 同一快照导出 CSV → Agent 用脚本读取、计算和绘图。

组件具体职责不是用来做什么
原始数据归档保留来源记录、导入批次，便于排查和重新处理。不直接等同于最终的区间能耗。
DuckDB嵌入式分析数据库，保存分析事实，执行筛选、聚合与 CSV 导出。不只是一个文件仓库，也不直接暴露给浏览器。
SQLite保存项目、账号权限、配置引用、会话、运行任务与报告等业务元数据。不承担大量时序数据的主要分析工作。
CSV / 压缩 CSV作为导入格式，或从统一数据底座导出的、适合 Agent 读取的分析文件。不要求用户再上传一份来“绑定”项目基础数据。
技术细节：为什么是凌晨 02:00，为什么仍要标记缺失？
  • 累计读数需要区间两端。例如累计电量从 1200.0 到 1200.4 kWh，差值为 0.4 kWh。午夜前后没有可用读数，不能凭空确认最后一个区间。
  • 取数窗口到当天 02:00；昨日统计仍截止当天 00:00。多取两小时是为了获得边界附近的后续累计读数，不是把凌晨两小时算进昨天。
  • 每天重叠回拉。根据上次同步水位及配置的重叠窗口回取，吸收延迟到达的记录；再标准化与去重。水位表示已请求到哪里，不代表每块电表都完整到那里。
  • 15 分钟数据包含重采样处理。对累计读数做分段线性边界插值，再计算区间差值；质量规则记录异常、边界和重采样信息。插值得出的区间值不能说成每 15 分钟都独立实测。
  • 缺失不补成零；主表与子表不重复相加。官方总量按计量角色与有效质量筛选。未采到数据，和实际读数不变，是两件事。
技术细节：如何保证 Explorer 与报告的数据一致？
同一项目 + 同一 Snapshot + 同一时间窗 + 同一计量映射
    ├─ Explorer：后端查询 → 数值 / 趋势
    └─ Report：DuckDB COPY 导出 → CSV → Python / 脚本分析

报告准备输入时检查数据快照版本，导出期间若版本发生变化则拒绝混用。CSV 与数据库不需要是同一种文件格式；需要统一的是来源、版本、时间边界、单位和计量口径。

已验证 · 生产

9 月 14 日 02:00 自动取数成功，约 10 秒完成。9 月 7–13 日，同口径的报告输入合计 647.0380947 kWh，Explorer 显示 647.0381 kWh。

该窗口导出 10,781 行，未发现重复；官方汇总使用其中符合计量与质量条件的 4,504 行，不能把所有行直接相加。
仍需区分：同步成功不等于每块电表都完整。DB1 Lighting 在该 7 天窗口的覆盖率仍为 70.2%，需要继续确认源端缺口。Preschool、Ngee Ann 的静态文件可以反复分析，但没有新上传或 API 时，不会自动产生新读数。
用一句话解释：“DuckDB 是我们统一查询和计算的底座，CSV 是从这份底座给 Agent 准备的工作材料。两边读同一本账。”
04 / AI 对话生成报告

把 Charles 与 Coding Agent 的工作方式，
搬进我们的网站。

遇到的问题

固定模板难改，分析容易变成描述数字。

单纯让模型回答文字，缺少文件、计算与成品预览；开发者手工复刻 HTML，也不能替代 Charles 与 AI 反复探索后得到的分析质量。

我做了什么 · 为什么

让 Agent 完成分析与 HTML 制作。

沿用账号、项目与数据能力，接入 Pi 执行链路。用户自然提问，Agent 自己选择读取、计算、绘图和生成文件；用户看到过程、成果与修改版本。

REQUEST网站对话

选择项目与日期，提问或要求制作报告，也可以补充附件。

RUNPi + 云端工具

在隔离工作目录中读取资料，运行脚本，生成 HTML。

REVIEW审阅与修订

同一会话内检查数字、措辞、日期与页面，再修正问题。

DELIVERY预览与 Reports

点击文件在右侧阅读、放大；完成后保存报告与版本。

模型拿到哪些信息？

上下文内容作用
项目资料配置 JSON、可读项目说明、空间与电表层级、可用位置图与来源。知道电表代表什么，避免每个 Session 重复解释项目。
数据文件所选时间窗、可用比较历史、单位和质量信息。用脚本算出证据，而不是在长聊天里猜数字。
Skill分析方法、项目风格、通用呈现与审阅规则。保留有效经验，同时让 Agent 继续探索。
本次要求Charles 的问题、关注点、补充资料与修改反馈。决定这一次真正需要回答什么；普通提问不必强行生成 HTML。
技术细节：Pi、模型、Session、Docker 分别负责什么？
层次当前实现
网页与服务React / Next.js 界面；Node.js / TypeScript API 管理身份、项目、会话、任务和产物。
Agent 与模型Pi Coding Agent 负责工具循环与内部会话；Pi 模型运行层统一调用。当前生产模型 ID 为 deepseek-flash，通过配置的 OpenAI 兼容接口调用。不能据此称为已确认的 V4.1。
计算工具读取、搜索、编辑和写入文件，执行 Bash / Python 等脚本；Python 是数据计算工具之一，整个服务后台并非都用 Python 编写。
隔离执行每个活动 Run 使用临时 Docker 容器，非 root、只读根文件系统、限制 CPU / 内存 / 进程数，不向 Agent 开放宿主机目录或 Docker socket。
模型请求桥接隔离容器通过标准输入输出的结构化消息与宿主服务交换请求、流式事件与产物。宿主服务访问已配置模型；模型密钥不交给容器。
用户与会话系统 Session 绑定用户与项目；一个 Session 内有多个 Run。内部 Agent 会话状态可保存续接，任务结束容器销毁，不等于聊天记录丢失。

Pi 提供 Agent 能力；多用户权限、排队、资源限制、文件保存和网页交互仍由我们的系统负责。报告生成任务也不自动获得修改项目配置的权限。

技术细节：生成后怎样审阅，是否要再开一个聊天？

不需要用户另开聊天。同一个 Agent Session 内先生成草稿，再进入明确的审阅步骤，有具体问题则修订，随后检查最终产物。

  1. 模型审阅：检查数字依据、缺失数据的表述、因果推断、行动建议与正文一致性。
  2. 程序检查：统一提供日期标签，校验支持格式的星期与日期对应关系；检查最终 HTML 与审阅回执的哈希是否对应。
  3. 浏览器检查：查看桌面 / 手机尺寸下的溢出、JavaScript 错误，并执行报告特定的交互检查。
  4. 交付：阻断性检查未通过时不把草稿当成完成报告；通过后保存可追溯的成品。

这个环节能减少错误，但不是所有事实都能由程序证明；现场原因、缺失数据影响和建议合理性仍需要业务反馈。

已验证 · 真实生成

最新生产验证完成了全英文报告 → 对话修改 → 新版本保存，包含项目独立风格、位置示意与跨期跟进。一次完整报告约 8 分钟，一次修改约 4 分钟。

本次审阅曾修正覆盖率表述、图表组成与绝对化措辞等问题。耗时取决于模型、任务复杂度和排队情况，不能承诺即时完成。
可以现场说：“您仍然是通过对话做报告，只是现在不需要在本地装 Coding Agent。计算、文件和报告都在我们的服务器里完成，也能留在项目里继续使用。”
05 / Skill 的提取

保存的是做出好报告的方法，
不是复制一段越来越长的聊天。

遇到的问题

经验留在外部对话里，难以复用。

每次重新解释，容易遗漏；每个聊天都生成一个新 Skill，又会让方法库膨胀。项目事实、分析方法与视觉风格混在一起，还可能互相污染。

我做了什么 · 为什么

在产品内提取，按职责保存与版本化。

把 Skill Creator 做成系统能力，从报告与反馈中形成方法候选；优先更新已有方法版本，试跑有效后再启用，避免一次对话改变所有后续报告。

信息应该放哪里例子如何更新
项目资料 / Configuration面积、电价、营业时间、电表归属、平面位置图。根据资料与确认结果更新项目配置，不硬写进通用方法。
分析 Skill怎样寻找非营业时段负荷、比较同类日期、判断变化是否值得行动。经过验证的分析经验形成方法新版本。
项目风格 SkillTuya 的配色、字体、章节版式与参考样式。绑定项目自己的风格版本，其他项目不会自动继承修改。
通用制作与审阅 Skill英文报告、结论前置、可读图表、手机适配、审慎措辞。作为共用能力受控更新，记录运行时加载版本。
每期分析记录本期新发现、旧问题进展、暂不纳入报告的候选。随报告更新，不因为每期有新发现就新增一个 Skill。
INPUT满意的报告与反馈

选取已经验证有效的讨论、成果和修改要求。

CREATOR提取报告方法

保留步骤、判断标准与内容组织；分离项目事实。

VERSION保存候选版本

在已有方法下形成新版本，查看内容并复跑验证。

ACTIVATE设为项目默认

明确启用后，新任务采用这个版本；旧任务保持原记录。

技术细节：如何防止 Skill 膨胀、误用和跨项目污染？
  • 稳定的 Skill 标识 + 多个版本。一套报告方法不因每次提取变成独立卡片；版本记录保存在配置资源中，可查看变更与历史。
  • 保存、查看、启用是不同操作。保存候选不改项目默认；打开旧版本也不会切换正在使用的方法。
  • 任务排队时冻结加载信息。记录实际 Skill ID、版本、内容与哈希，后续编辑不应影响已排队任务。
  • 区分公共与个人范围。项目公共方法由有权限的管理员管理；用户的个人方法不能通过一次聊天覆盖公共默认。
  • 来源 Session 用于追溯。Skill 可以来源于某次对话，但适用范围由用户 / 项目绑定决定，不被锁死在那次 Session。
报告分析方法（同一个 Skill）
    v1：当前项目默认
    v2：候选，等待复跑
    v3：候选，继续调整

查看 v2 ≠ 启用 v2
保存 v3 ≠ 自动替换 v1
已开始任务：保持它实际加载的版本
已验证 · 产品内

生产链路已经验证：从对话提取 → 保存候选 → 临时启用 → 新时间窗复跑。Tuya 与 Preschool 的项目视觉风格已分开绑定。

用户操作路径：Save report method → Review and save version → Skills & Tools → Set as project default。完成验证后可恢复原默认，测试不应悄悄改变正式计划。
未来的数据飞轮：把多个真实学校、办公室、幼儿园项目中有效的分析方法提取为建筑类型方法。共享方法与适用条件，保留各项目私有资料。自动匹配新项目、无需首轮人工调教，是后续目标，不是目前已全面验证的能力。
“我们不希望每月长出一个新 Skill。我们希望一套方法越来越好，知道它改了什么、是否经过验证、哪个版本正在被使用。”
06 / 报告的自动化生成

自动化不是替换日期和数字。
每期都重新分析，再决定哪些内容值得保留。

遇到的问题

人工重复执行，报告容易失去新意。

每周都要求 Charles 再点一次、传一次，不可持续；只沿用初始角度，会忽略新变化。调度失败或重复触发，也会造成漏报、重复报告和资源占用。

我做了什么 · 为什么

复用同一执行链路，加入跨期记忆。

调度器创建新的 Run，提供本期数据、选定方法及可访问的上一期成果。Agent 重新计算与探索，审阅通过后保存报告；报告可持续跟进，Skill 不每期自动改写。

02:00 SGT数据同步涂鸦 API 每日取数
例如 03:00 SGT报告计划用户选择频率与当地小时
NEW RUN分析与审阅使用本期数据及既有方法
REPORTS保存新成果历史版本可阅读与比较
周期默认分析窗口对用户的含义
每日前一个完整自然日。查看昨天的能耗与值得关注的变化。
每周前一个完整周，周一至周日。比较一周运行规律、异常与行动进展。
每月前一个完整自然月。形成较完整的管理报告与改进优先级。
对话自定义用户选择的时间范围，并提供可用的比较历史。探索具体问题；不必把全部历史数据塞进每次报告。
技术细节：调度、去重、失败恢复和跨期引用
  1. 计划计算：按项目时区、频率与执行小时确定当前到期窗口，调度器约每 30 秒检查一次。启用计划后，已到期窗口可能被补触发，不是只在某一秒执行。
  2. 避免重复：用“项目 + 频率 + 时间窗”作为计划标识，并在存储层限制重复；修改设置不应让同一期重复生成。
  3. 统一执行：自动报告与网页报告复用输入准备、Pi 执行、审阅与产物保存。任务有持久化状态；恢复按新任务续接，不宣称恢复到容器内的某条指令。
  4. 冻结输入：排队时固定选定方法与配置；准备数据时固定快照，完成记录保留实际版本。
  5. 跨期上下文：选择相同授权范围内、早于本期的已完成成果，提供 previous-report.html 和可用的 previous-followup.json。不把其他用户的私有聊天拿来参考。
  6. 内容更新：识别新发现、持续问题、需确认、已解决或应淘汰的内容；没有现场行动证据时，不把“建议已提出”写成“问题已解决”。跟进记录仍由 Agent 生成，需要继续检验稳定性。

09 / 备查

会上可能会问的技术问题。

电表越来越多，CSV 会不会把模型上下文塞满？

文件在 Agent 工作目录中，不是整份贴进提示词。模型先读取清单、字段和统计摘要，再让脚本筛选、聚合和绘图。报告输入按项目、时间窗和比较范围准备；较大的 CSV 可以压缩，现有处理在超过 16 MiB 时使用 gzip，避免因为文件大就丢弃行。

数据增长后，可以继续优化分区与查询接口；大数据可访问，不等于一次把所有数据发给模型，也不依赖百万 Token 上下文才能成立。

项目信息究竟是 JSON 还是 Markdown？能让 AI 改吗？

结构化关系由配置 JSON 表达，辅助背景用可读文档保存。页面解析为用户看得懂的电表、层级、营业时间等界面。Agent 使用受权限和校验约束的工具修改配置并形成版本；草稿、发布与当前生效配置是不同状态。

未知字段或任意文本不会自动变成新功能。渲染界面对应约定结构；需要扩展结构时仍要增加支持。位置图属于项目资料与附件，风格 Skill 说明如何呈现它，不应从其他项目“借事实”。

报告是改旧 HTML，还是重新生成？

同一报告的对话修订可以基于已有成果形成新版本。周期报告创建新任务，重新读取本期数据计算；上一期 HTML 与跟进记录用作参考，帮助追踪旧问题，并不是只替换数字。

主线可以稳定，但需要重新挑选重要内容。新发现优先进入本期报告与分析记录；反复证明有效的方法才进入 Skill 新版本。

用户多了，是否每个人都常驻一个 Agent？

不是。Session 是持久化的业务会话；只有活动 Run 才占用执行容器。当前生产是一个 API 队列拥有者，全站最多 2 个任务、每账号最多 2 个任务，同一 Session 顺序执行。交互任务优先，自动任务受额外并发限制，为人工使用留容量。

调整额度要看 CPU、内存、模型限流及实际报告负载。每个 Worker 配有 1 GiB 内存上限。跨服务器扩容还要共享队列、任务租约与文件存储，不能只多启动几个 API 进程就认为能安全扩容。

为什么暂时保留原有系统的一部分？

账号、项目权限、数据接入与 Explorer 已有价值，直接复用能更快验证核心目标。报告通过新 Pi 链路制作；旧版 Overview / AI 分析不是本轮验收主线。这样先证明新报告的价值，再决定进一步重构和 BI 扩展，避免为了平台完整度延迟 Charles 试用。
