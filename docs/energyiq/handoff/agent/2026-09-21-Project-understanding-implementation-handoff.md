## 4. 分阶段交付

### T1：最小分析材料契约

- [ ] 为现有分析产物增加 manifest、evidence refs、结构化 findings，保留可读 brief。
- [ ] 固定数据截止/版本、配置/映射版本、时区、各计算窗口及实际 Skill 版本。
- [ ] 保存计算输出与图表数据引用，不将全量原始数据复制为 memory。
- [ ] 用 schema 校验缺引用、错误项目、无效单位/范围和悬空关联。
- [ ] 明确草稿、已验证、发布关联及失败状态。

完成证据：一个隔离项目能保存并重新读取材料包，报告数字可追溯到计算产物。

### T2：全面分析真实生成

- [ ] 改现有分析 Skill/任务输入，让全面探索不受推荐条数限制。
- [ ] 保留“无 Action 的有用发现”，包括正常运行、学校阶段/时段差异、业务约束和未确认原因。
- [ ] 先验证证据再让下游消费；补算后形成一致修订。
- [ ] 与旧报告在相同冻结输入下对比分析广度、证据质量和可执行价值。

完成证据：真实模型产物含全面 brief 和可核验数据；不是手改 HTML 或只写额外说明。

### T3：项目认识、去重与状态保护

- [ ] 为当前认识建立稳定身份、revision、证据支持、待复核/替代关系；优先扩展现有 Insight store。
- [ ] Agent 提出变更，业务服务校验授权、revision、幂等并提交。
- [ ] 同义发现追加证据与报告来源；同设备不同措施分别保留；多电表集合与正式聚合口径正确。
- [ ] 候选不确定时不破坏性合并；已执行/拒绝反馈不被新报告覆盖。
- [ ] 在无新发现情况下复核已有认识，而非每次增添记录。

完成证据：同一分析重放不增加重复 Action，用户在运行期间的反馈仍保留；推荐展示淘汰不会删掉历史证据。

### T4：完整报告、行动清单与首页

- [ ] Report 输入包含完整材料，而非只传首页精选。
- [ ] Insight/Action 与 Report 引用同一已验证材料版本；Key Points 从协调后的当前清单选取。
- [ ] 图表允许 Agent 自主选择，指标引用可核验，不把 HTML 固定为机械模板。
- [ ] 报告版本、清单 revision 和首页选择形成可追溯发布记录；失败保留上一成功客户版本。
- [ ] 设备名称统一解析；历史报告仍可查当时名称及配置。

完成证据：增加一个未入选 Key Points 的有效分析发现后，报告仍能合理展开；修改展示数量不改变材料容量。

### T5：反馈复用与经验

- [ ] 用户确认事实进入授权配置更新；Action 采纳/拒绝/执行及原因进入已有记录。
- [ ] 下次分析读取这些状态，不重复问已确认问题；条件改变时可说明理由重新复核。
- [ ] AI 模拟、用户执行、读数观察、效果判断分别保存，模拟结果不能当真实结果。
- [ ] 证据不足则等待/不确定；具备对比条件再生成效果报告。
- [ ] 有效经验带适用条件与来源；Skill 更新作为单独候选流程，不自动改公共版本。

完成证据：两轮连续分析能体现第一次用户反馈，并保持历史版本不变。

## 5. 必过验收案例

| 案例 | 预期结果 |
|---|---|
| 有价值的学校假期差异但无动作 | 可进入完整报告，不强制制造 Action |
| 同一发现换措辞再次生成 | 沿用身份、增加证据与来源，不重复建行动 |
| 同一电表的不同措施 | 不误合并；可分别跟进 |
| 用户已拒绝措施并说明原因 | 后续遵守，除非新条件支持重新提出并解释变化 |
| 用户确认周末保洁需要照明 | 保存事实，后续不重复问，不把这段用电直接算浪费 |
| 用户反馈与后台报告同时完成 | revision 冲突重协调，执行记录不被覆盖 |
| 生成/发布失败后重试 | 不重复登记；上一版 Report/Key Points 可继续读取 |
| 更新展示条数 | 不截断分析材料，不强制补齐不足数量 |
| 新数据推翻旧推断 | 当前认识更新，旧证据和历史报告仍可追溯 |
| 多表场景含父子表 | 避免双计，设备关联可查看 |
| 缺营业时间/用途等关键事实 | 提出必要问题，不能保存猜测为确认事实 |
| 执行后暂无足够读数 | 等待观察，不能给出已实现节省 |
| 私有会话/反馈 | 不越权写入项目公共记忆，其他租户不可读 |
| 静态历史数据复跑 | 明确历史范围，无新数据也不伪装为新的实时发现 |

自动化检查覆盖状态/契约/权限/幂等；真实模型验收覆盖广度、证据和反馈复用；浏览器验收覆盖用户可理解的页面与链接。生产定时执行另验，客户满意另记。

## 6. T6 真实验收路径

1. 冻结一个项目的数据与配置，保存基线报告。优先使用已有 Ngee Ann 或 Tuya 验收材料，确认最新来源。
2. 正常入口启动真实模型全面分析，保留 brief、证据与 Skill 装载记录。
3. 生成完整报告、清单和首页，检查相同主张和收益表达一致，且报告不局限于精选内容。
4. 提交一条“事实确认”和一条“拒绝/执行反馈”，再跑一次正常流程。
5. 验证反馈复用、去重、旧版不可变与当前选择变化；使用 mock 执行数据时明确隔离，不污染真实经验和客户收益。
6. 通过现有定时复跑入口重复验证范围、版本和发布。手动触发 scheduler 路径与真正到点执行分别记录。
7. 输出验收记录：命令/测试、run/报告 ID、关键数值复核、界面证据、真实模型限制、仍待客户确认点。

## 7. 集成与发布交接

本侧会话不发布。主线程在本地验收后，按已有部署授权处理 main/远程/生产，核对当前服务器和发布机制。

历史报告保持原样；已有 Insight/Action 保持 ID 和反馈。缺少证据的旧材料标为 legacy/待复核，不强制重新生成所有历史报告，也不冒充新契约验证通过。新增结构做增量迁移，发布前备份并预演回滚。

生产验收必须重新确认实际加载的 Skill、当前数据、报告生成路径、清单/首页一致性和调度记录。不能用本地报告截图代替线上验收。
