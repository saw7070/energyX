# 新版报告端到端与多用户运行边界

## 当前编排（源码与实际运行核实）

后端为 Node.js/TypeScript，容器内为 Pi coding agent；Python/pandas/DuckDB 是 Agent 的分析工具，不是调度底座。模型通过后端代理访问远端服务，无需本机加载模型权重。

User + Workspace + Project → 持久 Session → 每条执行请求一个 Run → SQLite 队列 → 临时 Docker 容器 → 归档 HTML、输入和 Pi 状态 → 删除容器。

- Session 是逻辑对话记录，不常驻容器。一次 Run 创建一个 Pi 实例；续聊可恢复该 Session 最近成功 Run 的 Pi 状态。
- ReportService 的 active 标志保证当前单 API 实例一次执行一个 Run。其他请求 FIFO 排队；周期报告与聊天共用队列。
- claim 使用条件更新防止同一个任务重复领取，但 recoverInterrupted 会处理所有 running 任务。因此当前不能直接复制 API 实例来增加 Worker；还需任务租约、心跳、实例归属和恢复规则。
- 当前 AI 对话仍是 admin-only；共享报告的阅读权限与作者私有 Session 权限不同。

## 隔离与限额

- 服务端检查用户、Workspace、Project；Session/父 Run 绑定作者，附件逐个授权，数据按项目/窗口导出，接受产物前再次检查项目访问权限。
- 每次 Run 使用独立目录和容器；无 host bind mount、Docker socket 或模型密钥传入；worker network=none，非 root UID1000，只读根文件系统，cap-drop ALL、no-new-privileges。
- 实际 docker inspect：memory 2147483648 bytes，NanoCpus 2000000000，network none，ReadonlyRootfs true，UID1000:1000。这是上限，不是启动即预留 2GB。
- tmpfs：workspace768MiB、tmp256MiB、home128MiB，临时写入消耗内存，不是额外免费磁盘；进程数128。输入文件包上限100MiB，恢复状态32MiB，回收输出/状态48MiB。输入打包在 API 进程中会产生额外内存开销，不受容器内存限额覆盖。
- 容器边界不是独立虚拟机；当前验证不是渗透测试或多租户生产容量认证。

## 小规模多人试用前的优先项

1. 保持一个报告Worker，显式显示排队/取消状态；不要按登录人数创建常驻Agent。
2. 增加每用户排队数量、任务时长与调用预算，区分交互聊天和后台周期报告，避免一个长报告阻塞所有用户。
3. 建立归档保留期、磁盘预警与项目配额；输入快照可做去重，不能随意删除仍被报告引用的证据。
4. 用真实大项目测峰值内存、API响应与等待时间，再决定扩容和并发。当前2核约4GB服务器先维持单Worker。
5. 扩并发前完成worker租约/恢复与多账号端到端隔离测试，不能仅修改active布尔值或起多个API。

## 用户确认的并发目标（本次后续反馈）

单槽串行只是当前实现，不是最终产品要求，也不是Pi的限制。目标为约5用户同时使用，不同Session并行，同Session顺序执行；交互任务与自动化长报告保留各自容量，设置平台/用户并发及队列上限。是否需要排队取决于实时容量，不能承诺任意负载下零等待。本次未实现并发改造；上述单Worker建议仅用于当前服务器在改造验收前的安全运行。

生成/审阅可使用两类Skill，同一用户Session背后执行多个内部阶段，审阅采用独立上下文接收报告、事实和必要数据。通过则交付；需要修改则返修再检查，不能认为两轮必然合格。无需用户另外开聊天。

## 报告审阅的含义

未来可采用“生成草稿 → 新模型上下文审阅事实/证据/措辞 → 原生成器依据具体问题修订”。可以使用同一个Pi实现和同一模型，不需要用户另开聊天或常驻第二个Agent。每阶段是内部任务，限制修订次数；未解决的实质问题保留为草稿/待复核。这是建议设计，当前未实现自动独立审阅。
