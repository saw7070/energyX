## 1. 目标与范围

### 1.1 用户关心的问题

用户主要关心两种审核：

1. **线上运行时审核**：模型每次生成 Summary、Insight、Key Finding 或 Additional Insight 后，服务器如何判断它能否保存和展示；
2. **Stage 3 质量审核**：三次独立生成、机器门、盲评与人工批准如何判断内容是否真正有价值、能否沉淀为 Method/SOP。

用户重申的产品原则是：

> 审核的目的不是破坏、删除或压平 Agent 输出，而是规范输出的诚实性、可追溯性和风险表达，从而帮助模型更好发挥能力。

用户明确反对以下倾向：

- 把所有没有直接证明的内容当作错误；
- 删除 What-if、反例、原因猜想、低风险实验或探索性建议；
- 用 `may`、`might`、`could`、`recommend` 等关键词决定整条 Insight 是否可以存在；
- 把 AI Interpretation 退化为确定性数据复述器。

### 1.2 本文不做什么

- 不修改生产代码、Prompt、Schema 或 Artifact identity；
- 不宣称已经完成真实 Provider、浏览器或人工价值验收；
- 不预先决定是否必须采用结构化 Claim；
- 不替主 Agent 决定关键词规则应全部删除还是保留为软提示。

## 3. 当前实现的只读观察

以下观察基于本地 `main@5ee20f9` 的源码快照。主 Agent 复核时必须先确认当前执行分支、HEAD 与后续 WIP，不能假定行号和行为仍完全相同。

### 3.1 线上运行时审核

当前大致链路为：

```text
模型输出结构化 JSON
→ Schema/形状检查
→ 当前 Workspace/Project/Snapshot/Release/Profile 身份检查
→ Evidence ID 存在性检查
→ 数字、单位、Centre、日期、Metric 关系检查
→ Epistemic Status 校准
→ Candidate 局部接受、修复、降级或拒绝
→ 发布 Artifact
```

当前合理的硬边界包括：

- Evidence 必须来自当前 Section Pack 或当前 Evidence Catalog；
- `Observed` 中的具体数字、单位、Centre、日期不能编造；
- Tool Audit、Method、Artifact identity 和租户归属必须可恢复、可追溯；
- Alert 不得把漏水、短路、火灾等可能性冒充成确认事故；
- 一个坏 Candidate 不得删除其他有效 sibling。

当前需要重点复核的实现包括：

| 路径 | 当前机制 | 待验证风险 |
| --- | --- | --- |
| `preschool-section-interpreter.ts` | 收集被引 Evidence 中的数字、日期、单位和 Centre，再对叙事做支持性检查 | Layer 2 部分数字检查仍可能停留在“值存在”，需要确认能否准确绑定 Metric、实体、时间和字段 |
| `energyiq-ai-claim-validation.ts` | Typed Evidence/SQL cell 同时检查数值、字段语义、单位和 Centre 维度 | 是否可复用到 Layer 2，避免继续增加专用关系补丁 |
| `preschool-section-interpreter.ts` | 发现特定推断词时，将 `Observed` 自动降为 `Inferred` | 正则可能漏判、误判，且模型表达被迫迎合关键词 |
| `preschool-executive-synthesis.ts` | 来源为 `Inferred/Speculative` 时，要求每个句子出现限定词 | 可能形成关键词监狱，拒绝语义正确但措辞不同的表达 |
| `preschool-additional-ai-insights-workflow.ts` | 用 causal/action/external-benchmark 关键词辅助判断 Epistemic Status，部分情况拒绝 Candidate | 可能把创造性假设或建议当成非法确定事实，而不是降级或要求修复 |

### 3.2 Stage 3 质量审核

当前 Stage 3 evaluation 为同一目标预留三个独立 attempt。每个完成 Artifact 先经过机器门，机器门检查：

- `contract-boundary`；
- `fact-boundary`；
- `provenance`；
- `duplicate`；
- `expression-length`；
- `restore-completeness`。

机器门通过的结果进入盲评。Blind review 隐藏 Provider attempt identity，分别展示 Summary 与 Finding，并记录：

- Summary usefulness；
- 每条 Insight usefulness；
- 综合人工分数；
- 是否通过。

Pass@3 当前要求至少两个 machine-passed attempt，并且至少两个通过人工评审。批准后仍只是 `publication-candidate-only`，不是绕过治理直接发布。

讨论中的核心分工建议是：

| 审核层 | 应负责 | 不应负责 |
| --- | --- | --- |
| 运行时审核 | 身份、事实、引用、租户、安全、Alert、可恢复性 | 用关键词判断内容是否有价值；要求猜想已被直接证明 |
| Stage 3 机器门 | 合同、Evidence lineage、来源、重复、可恢复性 | 代替人工判断新颖性和启发性 |
| Stage 3 盲评/人工批准 | 新颖性、相关性、启发性、可读性、决策价值 | 通过修改事实边界来“救”错误输出 |

## 4. Evidence 的目的与当前风险

### 4.1 Evidence 应解决的问题

Evidence 不是为了禁止模型提出新想法，而是解决五类问题：

1. **防止伪造事实**：具体数字、日期、Centre、设备和单位需要有来源；
2. **防止错借数值**：总能耗的 `12%` 不能证明峰值变化也是 `12%`，Centre count 的 `12` 也不能证明 energy ratio；
3. **支持用户追溯**：用户可以从 Insight 返回对应 Section、指标、时段和图表；
4. **区分依据与证明**：Evidence 可以为推断或猜想提供背景，不等于直接证明原因；
5. **支持 A→B 复跑**：新 Snapshot 到来时可以判断结论是 New、Changed、Still supported 还是 Resolved。

### 4.2 建议主 Agent 重点验证的 Evidence 语义

```text
Observed
→ Evidence 需要直接证明 Claim

Inferred
→ Evidence 需要支持基础信号
→ 新关系本身不必已经写在 Evidence 中

Hypothesis / Speculative
→ Evidence 用于锚定当前问题和相关性
→ 不要求 Evidence 直接证明可能原因

Experiment
→ Evidence 说明为什么值得尝试
→ proposed parameter 不是历史事实
```

### 4.3 Layer 2 是否需要优化

讨论中的初步判断是“需要”，但主 Agent 必须独立验证。目标不是放宽事实边界，而是把当前可能粗粒度的：

```text
本卡 Evidence 中出现过这个数字
```

升级为：

```text
Claim
→ Fact ID
→ Metric/field
→ Entity
→ Time
→ Value
→ Unit
```

需要优先判断能否复用 `energyAiNarrativeClaimsSupported` 的 Typed Evidence 能力，而不是继续给 Layer 2 添加 `hasMislabeled...` 一类专项关键词补丁。

## 5. Epistemic Status 与关键词风险

### 5.1 Epistemic Status 的产品含义

- `Observed`：Evidence 直接表达的事实；
- `Inferred`：模型从一个或多个 Evidence 推导出的关系；
- `Speculative/Hypothesis`：值得继续探索、但尚未证明的可能原因或角度；
- `Experiment`：低风险、可逆、带验证指标的尝试。

Epistemic Status 不是模型自报的可靠“信心分数”。模型可以标错类型，服务器仍需要验证 `Observed` 的事实边界。

### 5.2 关键词是否需要存在

讨论中的初步判断：

- **不应作为硬接受/删除门**：`may/might/could/recommend/likely` 不应该决定整条 Candidate 是否存在；
- **迁移期可作为软提示**：例如提示一个 `Observed` 可能应降为 `Inferred`，但不能因为没有命中关键词就升级为事实；
- **事实提取和安全扫描可保留**：提取数字、日期、单位、Centre，禁止内部 Prompt/SQL/危险 HTML，识别高风险 Alert；这些不是在限制思想内容。

主 Agent 需要独立判断：

1. Layer 2 自动降级关键词是否保留为 fallback；
2. Layer 1 “每句话必须出现限定词”的门是否应删除；
3. Stage 3 causal/action 关键词是改为软诊断、自动降级、repair request，还是继续局部拒绝；
4. 是否存在可以不用关键词、又不允许不确定结论冒充事实的更深接口。

## 6. 结构化 Claim 方案与潜在问题

对话提出的候选方向是让模型输出少量结构化 Claim，例如：

```ts
{
  kind: "observation" | "inference" | "hypothesis" | "experiment",
  text: string,
  evidenceRefs: string[],
  verificationQuestion?: string,
  proposedParameter?: { value: number; unit: string }
}
```

这只是待验证设计，不是既定方案。潜在问题包括：

1. **Schema 过重**：模型花精力填表，反而减少发现新角度的能力；
2. **模型自报类型不可靠**：模型可能把原因猜想标成 `observation`；
3. **一句话包含多个 Claim**：Observation、Hypothesis 和 Experiment 混在一段时需要拆分，但前端仍要恢复自然表达；
4. **实验数字被当成历史事实**：如“尝试提前 30 分钟关闭”，`30` 是提议参数，不是 Evidence 中已发生的数字；
5. **用不确定措辞绕过事实校验**：`Centre L 可能用了 7.8 kWh` 中的具体历史数字仍必须验证；
6. **Artifact 兼容**：合同变更可能需要 identity revision 旋转，旧 Artifact 只能历史只读；
7. **Claim 数量和页面长度**：过度拆分会使页面机械化；底层结构化不等于前端展示为表格；
8. **质量判断仍不能完全代码化**：新颖性、启发性和行业价值仍需要 Stage 3 盲评、人工判断或非权威的 judge 辅助。

主 Agent 需要比较至少三个选项：

| 选项 | 优点 | 风险 |
| --- | --- | --- |
| 保持当前 Card + 关键词校验 | 改动小 | 继续积累正则补丁和误伤 |
| Card 内增加轻量 `claims[]` | 事实、推断、假设可分开验证 | Schema 与迁移复杂度增加 |
| 保持自由 Card，只对明确事实创建 typed claim binding | 对创造性限制最小 | 混合叙事和局部修复接口更难设计 |

## 7. 建议红测矩阵

主 Agent 应先补或复核以下反例，不应从本文结论直接进入 GREEN：

| Case | 期望 |
| --- | --- |
| `Observed` 写具体数字，但没有对应 Metric/Entity/Time Evidence | 局部拒绝或 repair，不发布为事实 |
| Evidence 有同样数字，但属于 total energy；Claim 说 peak change | 拒绝错误事实绑定 |
| 基于多个 Evidence 提出新关系 | 保留，并允许/归一为 `Inferred` |
| `If/may/might` 提出清洁活动或 manual override 假设 | 保留为 `Speculative`，不要求直接原因 Evidence |
| 建议试行提前 30 分钟关闭设备 | 将 30 分钟视为 proposed experiment parameter，不当作历史事实 |
| 一张卡同时有错误事实句和有价值假设 | 优先修复/降级事实句，保留核心 Insight |
| 推断表达没有命中当前谨慎词列表，但结构化状态和 Evidence 正确 | 不应仅因措辞被删除 |
| 使用 `可能` 包装伪造的 7.8 kWh 历史数字 | 仍拒绝具体伪造事实 |
| 一个 Candidate 错误 | 不影响其他 Candidate、Section 或确定性 Overview |
