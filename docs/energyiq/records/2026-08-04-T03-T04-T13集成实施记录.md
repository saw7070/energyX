# EnergyIQ T03/T04/T05/T13 集成实施记录

本记录描述 `codex/t01-integration` 相对 `74faf83` 的新增公开契约。它区分“代码已接通”“自动化已验证”和“仍需真实产品验收”，不能把其中一类证据替代另一类。

## T03：Tariff 与 Operating Calendar

`executeEnergyScopeAnalysis` 通过同一 Published Project Release 固定的 `tariffScheduleVersion` 和 `businessCalendarVersion` 调用现有 operational policy store。Cost 按区间有效费率计算并返回币种、Tariff 版本和 allocation；Operating/Standby 使用 Project timezone、Calendar 版本和 Interval Fact。缺版本、缺有效覆盖、币种冲突或缺事实均返回带 code/message 的 `Unavailable`，不再使用固定 SGD 单价或旧 `is_operating` 默认值。

Saved Analysis 的 POST 和 rerun 均先调用 `ProjectAnalysisResolver`，只持久化 ready Snapshot 的 `analysis`，并固定发布的 Template Revision。旧记录不会因当前 Project 配置变化而重算。

Admin 已新增 `Tariff & Hours` 入口和以下 Project-scoped API：

- `GET /api/v1/energy/projects/:projectId/operational-policies`：同时返回当前 Published Release pins、待发布 pins 和不可变修订历史；
- `POST /api/v1/energy/projects/:projectId/operational-policies/tariff`：发布 Project/Scope 费率窗口；
- `POST /api/v1/energy/projects/:projectId/operational-policies/calendar`：发布 Project/Scope 周时段与日期例外。

Tariff/Calendar 发布只创建不可变修订并更新 pending binding，不再提前改写 `energyiq_projects` 中代表客户 Release 的 policy versions。只有 Project `Review & Publish` 在同一事务内解析 pending binding、更新 Project pins 并创建 Template Revision，客户 Resolver 才能读取新策略；发布失败会整体回滚。

随后 #23 完成 Ngee Ann 四工作簿权威 Mapping/materialization，#24 完成 Meter Attachment 与 Official Aggregation Route 分离，原有 Publish 门禁已解除。#4 的机制验收已关闭：acceptance-only v1/v2 分别通过 pending → Project Publish 进入不可变 Template Revision，Cost 与 Operating/Standby 数值随固定 Tariff/Calendar pins 变化；Saved v1 保持冻结，rerun 创建 v2 而不覆盖 v1。上述本地 revisions 仅证明机制，不是客户确认的费率、营业时间或例外；正式业务值仍须以新的不可变 revisions 发布。

## T04：Area、Headcount 与有效期

Project Analysis Resolver 按分析的半开 Period、timezone 和发布的 hierarchy revision 解析 selected Scope 及每个 comparison Scope 的 Area/Headcount。EUI 与 Per-Pax 仅在对应 metadata 有效时产生；`confirmed`、`provisional`、`missing`、具体 guidance 和 Evidence 进入 Snapshot。

`snapshot.analysis.summary` 和 `childScopes` 中的兼容字段由 Period-effective metadata 投影覆盖；旧的静态 hierarchy 数值不会与新 metadata 旁路并存。Overview 显示当前 Snapshot，Saved Detail 只读冻结的 `analysis.metadata`。

## T05：Overview Primary Period

Overview 的 `Previous week` 与 `Previous month` 已接入同一 server-authoritative Primary Period 链：浏览器只保存 canonical Period 参数，API 依据 Project timezone 和单次 server `now` 解析半开区间，再把相同 Period 传给 Project Analysis Snapshot、Energy Query Context、AI run input 和 Agent Runtime。

- `Previous week` 为 Project timezone 下上一完整周；
- `Previous month` 为 Project timezone 下上一完整自然月，覆盖跨年、闰年和 DST 月份；
- Scope 切换、冷 URL hydration 与 reload 保留 Period，不静默改回默认值；
- 无数据时保持所选 Period 并返回明确 coverage/Data Status，不自动改查另一个日期范围。

自动化已覆盖 URL/parser、公共 resolve HTTP、ready + zero coverage、快速 Period → Scope 切换、单次 server month boundary 和 `America/New_York` 跨 DST 的 743 小时自然月。Chrome 已验收 `Previous week` 的 Project/Level Scope、reload 和零 console error；`Previous month` 的浏览器验收仍待执行。

## T05A：当前 Data Snapshot 与事实状态

#25 的代码已集成。`dataSnapshotId` 不再只进入 Context、签名和 Evidence：服务端从 Metadata 当前 Snapshot 解析精确 `source_sha256` manifest，并要求 Workspace、Project、Metadata pointer、DuckDB `energy_project_fact_state`、writer contract 与 manifest fingerprint 一致。Coverage、Overview 和 AI scoped datasource 复用同一 guard；旧 Context 在 pointer 漂移时返回 `ENERGYIQ_SNAPSHOT_STALE`，当前 Snapshot 的表、状态、行数或内容摘要缺失/损坏时返回 `ENERGYIQ_SNAPSHOT_FACTS_UNAVAILABLE`，不再把混合事实或损坏事实解释成 0 coverage。

Materialization 只保留 project-manifest writer：全部 active batches 与 canonical facts 在一个 DuckDB 事务写入，并在同一事务保存当前 canonical interval count 与覆盖指标/Evidence 字段的行序无关 SHA-256 digest；Metadata 随后用 expected previous/target Snapshot 做 CAS completion。旧 per-batch writer、Metadata per-batch prepare/complete 和 completion shim 已删除。Writer contract 为 `energy-fact-writer-snapshot-manifest-v3`。

当前部署仍是每个 DuckDB 仅一个 owning `apps/api` 进程，Project 级进程内 mutex 与两侧 CAS 是本票据边界。若未来允许多个 API owner 同时写同一事实库，必须先引入持久 lease/leader 或单 writer service。本轮没有增加历史 Snapshot 事实仓库、任意 replay、Query Receipt 或 CTA UI。

代码门禁已通过 12 个定向文件 79 tests、7 个跨层文件 56 tests、root typecheck/build 和 diff-check。#25 仍不能仅凭代码关闭：必须先停 API 做可恢复备份，再用正式 API 对 Ngee Ann 四份权威 Excel/SHA live rematerialize，并对账 Metadata pointer、DuckDB state、manifest、readiness、coverage、Overview、AI 与 Project/Level/Circuit Golden。

## T13：Workspace 默认模型

公开 API：

- `GET /api/v1/workspace-default-model-profile`：Workspace 成员可读安全代理；普通用户看不到 source profile id、secret ref 或 API key。
- `PUT /api/v1/workspace-default-model-profile`：仅 EnergyIQ admin；body 为 `{ "profileId": string, "expectedRevision"?: number }`。
- `DELETE /api/v1/workspace-default-model-profile`：仅 EnergyIQ admin；可用 `expectedRevision` 做乐观并发控制。

绑定保存在 `workspace_default_model_profiles`。Metadata Store 初始化时以 `CREATE TABLE IF NOT EXISTS` 建表；绑定只引用 Admin 已连接的 model profile，不复制密钥。绑定强制 `fallback_policy = disabled`。只要绑定存在，默认 Run 就固定选择 `workspace-default`；source profile 被禁用、断连或删除时明确失败，不会静默换用普通用户的另一个 Provider。

## Trusted text run input

受信 host 可在既有 Energy Query Context 中传递 allowlisted `trustedTextIntent`。服务端重新解析 Workspace/Project/Scope/Period、建立半开区间 scoped datasource，并从 Project Analysis Snapshot 编译固定 Metric、Data as of 和 Evidence 的 contract。浏览器提供的事实或 SQL 不会进入 contract。

当前 T13 仍未达到产品验收：

- Web 尚未把普通用户 Golden Question 映射为 `trustedTextIntent`；
- 正式 Snapshot 尚缺 historical baseline 和 day-type profile 两类 Golden fact；
- 通用 Agent 生产路径尚未把最终模型输出接入 `executeTrustedEnergyText` 的结构化 claim 校验和 canonical answer envelope；
- DeepSeek V4 Flash fallback-off 的真实连续 10 问、普通用户浏览器角色验收和 live 输出信封均未完成。

因此离线 10/10 只证明投影/校验器测试，不是 live Provider acceptance，#14 必须保持 OPEN。
在验证执行器接通前，带 `trustedTextIntent` 的 Run 明确返回 `TRUSTED_ENERGY_TEXT_VALIDATED_EXECUTOR_REQUIRED`；系统不会把通用 Agent 文本标记成 trusted answer。
