# 2026-08-01 开发记录：Admin 与 Tier 批次 0–1

## 1. 目标与范围

本批将已确认的 Project/Tier/Node 模型落实为管理员可操作的交付链：可创建 Project、编辑 Draft、校验、发布不可变 Hierarchy Revision，并让客户页面只读取 Published 配置。

本批没有实现 Meter Point 分表、Excel/API Adapter、虚拟表、Metric/Rule/Template Registry 或 Analysis Run；这些仍属于批次 2 及以后。

## 2. 代码改动

### 2.1 领域与持久化

- Project 保持在空间 Tier 外，作为配置、汇总和权限根；
- Tier 计算使用稳定 ordinal，界面展示 admin 配置的 alias；
- Draft 是可变配置，保存采用 optimistic revision；
- Publish 校验后一次性生成不可变 Hierarchy Revision，再原子物化运行时 Tier/Node；
- Node Metadata 支持 provisional/confirmed、面积、代表人数、生效时间和独立业务意义；
- 已发布项目重启时不会再被 bootstrap 覆盖。

新增或扩展的主要持久化对象：

- `energyiq_project_setup_drafts`；
- `energyiq_hierarchy_revisions`；
- `energyiq_tier_definitions`；
- `energyiq_node_metadata_revisions`；
- `energyiq_projects` 与 `energyiq_project_nodes` 的发布、Tier 和 Metadata 字段。

### 2.2 API

新增 Admin 路由：

| Method | Route | 用途 |
| --- | --- | --- |
| POST | `/api/v1/energy/projects` | 创建 Project Draft |
| GET | `/api/v1/energy/projects/:id/setup` | 读取 Draft、Published 和校验状态 |
| PUT | `/api/v1/energy/projects/:id/setup/draft` | 按 revision 保存 Draft |
| POST | `/api/v1/energy/projects/:id/setup/validate` | 服务端校验 |
| POST | `/api/v1/energy/projects/:id/setup/publish` | 发布不可变 Revision |

每次管理写操作都会重新解析当前 user、role 和 active workspace；非 admin 或跨 Workspace 请求不会只依赖前端隐藏按钮。

### 2.3 Admin UI

`/energyiq/admin` 现在包含：

- Project list 与 lifecycle 状态；
- New Project；
- Project Profile；
- 通用的 Tiers & Nodes 配置器；
- 自底向上的 Add parent tier，支持 1–7 ordinal，主要面向 2–4 Tier；
- Tier alias/说明、Node 父级、面积、人数、生效期、provisional/confirmed 和独立意义；
- Save Draft、Validate、Publish、View as user；
- 对 Meter Mapping、Data Imports、Metrics、Templates 的 planned 状态提示。

层级浏览器不为 Room/Floor/Block 写专用组件，而是按 Tier Definition 渲染任意深度；每列只展示当前选中父节点的直接子项，避免一次铺开数百个 Circuit。

### 2.4 样板迁移

- Ngee Ann 升级为 `Project → Tier 2 Level → Tier 1 Circuit`，删除历史 `Block Test`，保留 2 个 Level 和 18 个 Circuit；
- Preschool 保持已确认事实 `Project → Tier 2 Centre → Tier 1 Circuit`，保留 30 个 Centre 和 270 个 Circuit；
- Preschool 面积和人数继续明确标记 provisional；
- 没有依据 Charles 的文案自动虚构 Block/Room。

## 4. 问题与取舍

1. 本地 API 使用进程级 DuckDB handle；Windows 下服务运行时，另一个测试进程不能同时写同一事实库中的 Scope View。处理方式是本地跑 golden 测试前短暂停 API，测试完成后立即重启。CI 没有并行 dev API，不受影响。
2. Project Setup 已支持 1–7 ordinal，但当前 UX 只承诺打磨 2–4 Tier；不开放跳 Tier，避免模板与比较语义提前爆炸。
3. 单节点且无独立属性的 Tier 允许保存 Draft，Validate 给 warning；当前允许管理员带说明发布，不把未完成配置直接判死。
4. Meter 仍兼容存在于旧 Node 读取模型中；正式空间与计量分离留给批次 2，避免本批同时改动事实链和层级链。

## 5. 复现与排查

前置条件：本地 Web `http://127.0.0.1:3001`，API `http://127.0.0.1:8787`；不要在文档写入密钥。

若 Admin 无数据：

1. 确认 API 8787 正在监听；
2. 确认当前账户为 admin 且 active workspace 为 `default`；
3. 检查 `GET /api/v1/energy/projects/:id/setup`；
4. 检查 `storage/metadata.sqlite` 的 migration 是否包含 `0019_energyiq_project_setup_schema`；
5. 不要通过重跑 bootstrap 修复已发布结构，因为 bootstrap 对已有 Revision 是非破坏性的。
