# EnergyIQ 领域模型

## 1. 聚合边界

### Workspace

客户组织的数据与权限边界。通过 Membership 连接 User。Workspace 下包含多个 Project。

### Project

独立配置、发布和分析的聚合根，至少包含：

- project_id、workspace_id、name、timezone、status；
- 当前已发布 hierarchy_revision_id；
- 当前 Data Snapshot 和默认 resource；
- 生命周期状态与审计字段。

Project 不属于空间 Tier。多个顶层空间节点直接由 Project 汇总。

## 2. Tier 与节点

### Tier Definition

每个 Project 自己定义，建议字段：

~~~text
tier_definition_id
project_id
ordinal              # 1 = lowest meaningful tier
alias                # Circuit / Room / Floor / Block / Estate
description
allowed_metadata_keys
status
~~~

同一 Project 内 ordinal 唯一。MVP 发布时要求父子节点通常连接相邻 ordinal；跳 Tier 只做模型预留。

### Project Node

Tier 的具体节点：

~~~text
scope_id
project_id
tier_definition_id
parent_scope_id      # null means directly under Project
display_name
external_ref
sort_order
status
~~~

display_name 是客户看到的名称，scope_id 是计算、导航、权限和 Trace 使用的稳定身份。

### Node Metadata Revision

保存有业务意义的属性：

~~~text
scope_id
key
value
unit
effective_from
effective_to
source
status               # provisional / confirmed
~~~

首期标准 key 为 comparison_area_m2、occupant_count、operating_schedule 和 usage_type。Project 默认值可继承，Node 覆盖必须可追溯。

### Hierarchy Revision

Tier Definition、Project Node、父子关系和校验结果的不可变发布快照。Draft 可以修改，Published Revision 不原地覆盖。

## 3. 计量模型

### Meter Point

独立于空间节点的逻辑计量对象：

~~~text
meter_point_id
project_id
resource_type
business_category
meter_kind            # physical / virtual
meter_role            # total / component / standalone
display_name
unit
status
~~~

Meter Point identity 不承担导航或上层汇总语义；这两种关系由已发布 Meter Mapping Revision 单独表达。

### Published Meter Attachment

表达某个 Mapping Revision 中物理 Meter 的导航挂载：

~~~text
mapping_revision_id
meter_point_id
navigation_scope_id
resource_type
business_category
~~~

每个物理 Meter 必须挂在已发布 Hierarchy Revision 中存在的 Scope。查询时禁止从 Fact 的旧 `scope_id`、名称或 Meter Role 回推挂载。

### Official Aggregation Route

表达每个分析口径的权威成员集合：

~~~text
mapping_revision_id
scope_id               # Project 使用保留根标识
resource_type
business_category
meter_point_ids[]
~~~

`scope_id + resource_type + business_category` 在一个 revision 内唯一。Circuit own-Scope route 保证每个物理 Meter 可独立查询；Level/Project route 只列入该层官方总表或明确选定且不重叠的 components。缺失、重复、悬空、跨 Resource/Category/Scope 的 route 必须 fail closed。

Mapping schema v2 的 fingerprint 同时覆盖 Meter identity、attachment 与 routes，并生成不可变 `meter_mapping_revision_id`。Published Project Release 必须 pin 该 revision。

### Source Binding

把 Physical Meter Point 与来源绑定：

~~~text
source_binding_id
meter_point_id
source_id
external_device_id
external_metric_code
source_label
effective_from
effective_to
~~~

Excel Device Name 和 Tuya device_id/DP 都通过 Source Binding 进入同一事实链。

### Meter Topology Edge

表达总分表或依赖关系，不用于客户导航：

~~~text
parent_meter_point_id
child_meter_point_id
relationship
coefficient
~~~

### Meter Formula Revision

虚拟计量点的不可变公式快照。首期只允许线性加减；必须无环、同资源同单位、输入完整。

## 4. 数据模型

### Source

Excel 或 Tuya API 的数据来源配置。API Connector 与 MCP 是不同概念。

### Import Batch

记录一次导入/同步的 source、文件 SHA 或请求窗口、开始结束时间、结果、质量摘要和重试关系。

### Raw Artifact

不可变保存上传文件或 API 原始响应的位置与校验值。

### Meter Reading

物理表的累计读数：

~~~text
meter_point_id
observed_at
cumulative_value
unit
import_batch_id
quality_status
source_row_ref
~~~

### Interval Fact

相邻有效读数差分：

~~~text
meter_point_id
interval_start
interval_end
usage_value
average_rate
unit
import_batch_id
quality_status
derivation_ref
~~~

同键重传必须幂等；冲突不能静默覆盖。

### Utility Fact

经 Mapping、质量校验、正式聚合和虚拟表公式后供产品使用的规范事实。它必须能回到 Interval Fact 和原始批次。

### Data Snapshot

某次运行固定可见的批次、事实版本和质量摘要。

## 5. 指标与规则

### Metric Definition / Revision

Metric Definition 给出稳定 metric_id；Revision 固定计算口径、单位、允许的粒度、输入字段、空值/质量策略和版本。

Metrics 大体分为：

- aggregate：total_kwh、average_daily_kwh；
- time-derived：peak_kw、peak_time、off_hours_kwh；
- historical comparison：change_vs_baseline；
- peer comparison：rank_within_tier；
- normalized：kwh_per_m2、kwh_per_person；
- quality：coverage_ratio、missing_interval_count。

Bell curve、四象限和热力图是分析/可视化方法，不应伪装成一个原始 Metric。它们引用一个或多个 Metric Revision 及比较范围。

### Rule Revision

异常检测的阈值、baseline 方法、最低绝对差、最低覆盖率、适用 category/tier 和输出严重度。

### Energy Query Context

后端解析的可信上下文：

~~~text
user_id
workspace_id
project_id
scope_id
tier_definition_id
resource_type
from
to
timezone
hierarchy_revision_id
meter_mapping_revision_id
meter_formula_revision_id
data_snapshot_id
metric_revision_ids
rule_revision_ids
business_calendar_revision_id
tariff_revision_id?
template_revision_id?
~~~

浏览器参数只用于请求和恢复显示，服务端必须重新校验 Membership、Project、Scope 与时间。

## 6. 模板与运行

### Component Catalog

受控组件定义，包括输入 Metrics、允许范围、数据要求、降级方式、视图类型和 Evidence 输出。

### Template Preset

跨项目参考，不直接运行。Charles Preschool 与 Ngee Ann Level/Circuit 都是 Preset 来源。

### Analysis Template

有两个 scope level：

- Project Template：Project Overview；
- Tier Template：某 Tier Definition 的节点分析页。

首期同 Tier 全部节点共用模板，不做 per-node override。

### Template Draft / Template Revision

Draft 可由 AI 辅助生成和 admin 编辑。Revision 是通过 Schema、数据、指标、权限和证据校验后发布的不可变版本。

### Analysis Run

固定以下内容后执行：

~~~text
template_revision_id
project_id
scope_id
analysis_period
data_snapshot_id
hierarchy_revision_id
formula/metric/rule/calendar/tariff revisions
result artifact
evidence bundle
status
created_by
~~~

相同输入应产生相同结果；新数据或新版本创建新 Run。

### Template Change Proposal

未来 AI 或人工对话提出的结构化变更。Proposal 不能直接变为正式模板，必须 Diff、校验、预览和人工发布。

## 7. 关系摘要

~~~text
Partner
└── Workspace
    ├── Membership
    └── Project
        ├── Hierarchy Revision
        │   ├── Tier Definition
        │   └── Project Node
        │       └── Node Metadata Revision
        ├── Meter Point
        │   ├── Source Binding
        │   ├── Meter Topology
        │   └── Meter Formula Revision
        ├── Import Batch
        │   ├── Raw Artifact
        │   ├── Meter Reading
        │   └── Interval Fact → Utility Fact
        ├── Metric Revision / Rule Revision
        └── Template Revision
            └── Analysis Run
                ├── Data Snapshot
                └── Evidence Bundle
~~~

## 8. 关键不变量

1. Project 不计入空间 Tier；
2. 计算用稳定 id/ordinal，展示用 alias/name；
3. Meter Topology 不等于空间树；
4. 累计读数不可直接求和；
5. 总表与其分表不可重复聚合；
6. 原始数据与 Interval Fact 都保留；
7. 模板、公式、指标、规则和运行均可追溯；
8. AI 不能越过服务端 Scope，也不能直接发布正式模板。
