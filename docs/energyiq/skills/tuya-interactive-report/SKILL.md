# Interactive office electricity report

Generate a new English self-contained HTML deliverable from the current manifest, published configuration, project context and CSV. This method transfers the NetZero Software Prototype's analysis and drill-down experience into a portable report; do not embed or rebuild the platform. Do not reuse the prototype's Ngee Ann/EliteIOT values, seeded mock scaling, simulated assistant replies or fixed anomaly outcomes. Apply the supplied energy-report-investigation reference for exploratory analysis when available.

## Data and evidence

Use published meter attachments and official-aggregation eligibility, never infer independent totals from meter magnitude or tree depth. Main meters define the total only where published as eligible; submeter and virtual-circuit breakdowns must reconcile without double counting. Preserve DB/space/category/device labels from current configuration. A category is not a physical room. Prefer known device name, otherwise circuit name, with stable IDs retained only in supporting evidence. Virtual residuals obey published formulas; do not reconstruct Other by subtracting every meter, add lighting into a power residual or turn missing inputs into zero. A parent DB can have multiple main meters and need not be a single vertical meter chain.

Read selected period and timezone once. Keep requested dates, observed coverage, latest interval and complete-day comparisons distinct. Include available partial intervals in observed totals as appropriate, but compare daily profiles on complete comparable days and disclose counts. Nonzero load does not prove occupancy; sustained zero is observed zero, while missing readings are unavailable. Group power requires simultaneous interval alignment; peak kWh for an hour is not peak kW unless duration and aggregation justify the conversion.

Resolve hours, workdays and holidays from published policies; state provisional operating-hour assumptions. Estimate cost only for intervals with applicable tariff entries, respecting currency, GST basis and effective dates. A benchmark tariff is an estimate, not a verified bill. Missing intervals and uncovered tariff dates are not zero cost. Do not invent area, occupants or peer/national benchmarks. Prefer within-project comparisons with an explicit basis. Candidate anomalies use a stated comparable baseline, sample count, relative threshold and material absolute difference. Small/no historical samples produce descriptive flags, not confident anomaly claims. Never silently remove flagged readings from official totals.

## Report structure adapted from the prototype

Use a compact title, project name, analysis period and coverage line, with horizontal section navigation. Keep 3–4 short decision findings near the top and a KPI strip (observed energy, comparable daily mean, aligned peak with unit, estimated cost if covered). Then use these connected analysis sections:

1. **Daily trends.** Daily energy chart with weekday/weekend/holiday switch and scope selector populated from actual project DBs. Default All days/All DBs. Show meaningful comparable-day baseline only if supported; distinguish in-window descriptive reference from earlier-history baseline. A candidate-day table links to real hourly details for that day. A day-type filter updates sample count, displayed subtotal, chart and related candidate table consistently; it does not redefine the official full-period header.
2. **Energy breakdown.** DB and device/category contribution bars or donut with an adjacent numeric ranking. Selecting a DB shows its own meters/circuits. A category selector filters only the labelled breakdown view. Explain unmetered/virtual residuals and incomplete decomposition. The sum of a main and its component meters is never a project total.
3. **Daily operating pattern.** Average 24-hour profiles by day type with operating window shading and complete-day counts. Provide a selected-day versus comparable-profile view and an hourly circuit heatmap when sufficient samples exist. Anomaly or peak selection opens a labelled detail panel with date, DB/device, observed kWh/kW, baseline, difference and limitations. Do not use the prototype's deterministic fake heatmap or synthetic curve generation.
4. **Actions and evidence.** Cluster related evidence into the strongest 2–3 decisions. Show issue, measured impact, next check and responsible role; potential savings only as a declared scenario with switchability and baseline assumptions. Expandable supporting circuit table shows observed zero, missing/unusable and usable channels separately. Keep official totals as primary, and optional anomaly-exclusion sensitivity as secondary, never "corrected" consumption.

An outlook/forecast belongs only when actual inputs justify it; don't carry prototype forecasts or generic benchmark cards merely for visual resemblance. A source-backed schematic may help explain DBs, but it must not invent floor plans or physical relationships.

## Visual and interaction specification

Transfer the prototype's hierarchy: clear section headers, compact filters above their chart, adjacent ranking tables, expandable detail panels and a coordinated daily/hourly investigation. Remove its app shell, sidebar, account controls, other utilities, pretend chat and placeholder action buttons. Keep Tuya's readable report identity: white/light neutral #f5f6f8 canvas, ink #17212b, navy #17324d headings, orange #e87722 for key attention, blue #3478b8 for measured series, muted red #b94b43 for candidate alerts. Prefer a 1200px content width, 24px gutters, 24px section padding, clear 16px body copy and 26–32px title. Two columns only where labels remain readable; stack at narrow widths. A small number of broad sections should carry the charts, not nested decorative cards.

Working controls are part of the deliverable: section collapse/expand (plus expand all); DB scope selector; day-type switch; selected day drill-down; device/category breakdown filter; reset. Use actual embedded computed data to drive every view. Give all controls visible labels and current selection. Disable unsupported choices rather than inventing a chart. No date picker outside the embedded data coverage; the report's saved analysis period is immutable. A filtered subtotal must be identified as such. Required offline event handlers must actually update data displays, not only button styles.

Treat a filter change as a dependent-view update: after selecting a day, switching DB must refresh its hourly detail for that DB or visibly clear the selection. Switching day type must clear a selected day that is no longer included. Changing category must refresh or clear incompatible device details. Reset clears every selected-day/device/detail state as well as resetting controls. Verify these multi-step sequences, not just each control in isolation. Never leave an old project-total detail below a newly DB-filtered chart without explicitly labelling it as an independent view.

Use inline SVG/HTML and small vanilla JavaScript, no network, CDN, external assets or iframes. One computed JSON payload is the shared source for all chart/table/filter states. Buttons and selects are keyboard accessible; dialogs close with Escape and return focus, tooltips have text/table alternatives. Keep tab focus visible and honour reduced motion. At 390px the document must not horizontally overflow; only a labelled table container may scroll. Set min-width:0 on every grid/flex child, use minmax(0,1fr) tracks, constrain charts/selects/table wrappers and collapse all splits, including peak/screening and hourly-detail panels. Check document scrollWidth after opening a detail, changing filters and expanding sections. Do not hide page overflow to clip evidence. Print mode expands important content and hides controls. Do not add dummy interaction or simulate persistence/actions requiring a backend.

Save outputs/report.html, computed facts and exploration notes. Verify default official total, DB-filter totals, day-type counts, selected-day curves and reset against independent computations. Check actual browser interactions and numeric consistency. Omit self-invented generation timestamps; the system supplies authoritative metadata. Preserve date/coverage limits and project assumptions near affected claims. New customers reuse this method with their own mapping, metadata, schedules and tariff; no Tuya-specific measured values belong in the Skill.
