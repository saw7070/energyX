# Release checklist: main as of 6 November 2026

This release takes production from the October code to `main` (the Phase 1 security and enterprise work, Start from
Tuya, the new-project fix and the Tuya daily-update fixes). Deploy it to **staging first**, then promote the same
artifact (see `staging-environment.md` and the release runbook in `../plans/`).

## Deadline

SKTC's meters were installed on 3 November and Tuya keeps about 7 days of readings. Start from Tuya fetches the last
7 days, so SKTC must be onboarded on the new release by about **10 November** or the first days are lost. The Tuya
office site has not updated since 27 October; its readings before about 30 October are already gone from Tuya.

## What changes for people

| Change | What to tell people |

## Before deploying

1. Take the usual pre-deploy backup and note the current release (`readlink -f /opt/energyiq-datafoundry/current`).
2. Build the artifact on the Build Host with the **same Node version as production** (v22.23.2 at the last release).
3. Confirm the API settings (EnvironmentFile on the server):
   - `DATAFOUNDRY_AUTH_MODE=password` (the API now refuses to start in dev mode on a deployed server).
   - `SECRET_MASTER_KEY` is set (needed for two-step verification, Tuya keys and SSO secrets).
   - `ENERGYX_ENVIRONMENT=production` (staging: `staging` plus `ENERGYX_STAGING_EMAIL_ALLOWLIST`).
   - Optional but recommended: `ENERGYX_OPS_ALERT_WEBHOOK_URL`, `ENERGYX_AUDIT_MIRROR_PATH`.
   - The DashScope default moved to the international endpoint (`dashscope-intl`). If `LLM_BASE_URL` or
     `EMBEDDING_BASE_URL` is not set and the key is a China-region key, set both to
     `https://dashscope.aliyuncs.com/compatible-mode/v1`.
4. nginx: set `X-Forwarded-For $remote_addr` and `X-Request-Id $request_id` (see `deploy/nginx.datafoundry.conf.example`
   and `observability.md`).

## Database changes (run automatically at API start)

- `0053_auth_audit_hash_chain`: chains every audit record (existing rows are backfilled once, which can take a moment
  on a large table) and adds database triggers that refuse audit records written without the chain.
- `0054_organisation_sso_and_scim`, `0055_auth_two_step_verification`, `0056_auth_session_idle_baseline`: new tables
  and a one-off reset of open sessions' idle clocks.

## Rollback: read before deploying

Migrations only go forward, and the deploy script's automatic rollback switches **code only**. After `0053`, the
older code cannot write audit records (the trigger refuses them), and its sign-in writes audit records, so **old code
on the migrated database cannot sign anyone in**.

- Preferred rollback: switch back to the previous release **and restore the metadata backup taken just before the
  deploy** (`--metadata-backup` of `deploy-release.mjs`). Changes made after the deploy are lost.
- Emergency rollback without restoring: with the API stopped, drop the trigger so the old code can write audit records
  again, then start the old release. The audit chain will then report a break, which is expected:

  ```sql
  DROP TRIGGER IF EXISTS auth_audit_events_chained_insert;
  ```

## After deploying

1. `/ready` returns ready; sign in (set up two-step); open Overview for one site.
2. Admin → **System health**:
   - **Tuya office** "Live sync (Tuya)": if it shows a failure, the code says why. `1114` means add the server's IP to
     the Tuya cloud project's allowlist; `28841…` means the project's IoT Core plan has expired or no app account is
     linked (renew it on iot.tuya.com); "Meters without a Tuya device" means re-match them in Facility → Live connection.
     Once the cause is fixed the daily update catches up by itself from the oldest readings Tuya still has; use
     Facility → Live connection → Fetch now to start at once.
   - Off-host audit copy and email delivery as configured.
3. Onboard SKTC with Start from Tuya → Paste your device list (`start-from-tuya.md`), after the SKTC app account is
   linked to the Tuya cloud project.
4. Tell people about two-step verification and the idle timeout.
